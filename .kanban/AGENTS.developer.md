# developer: project guidance for future agents of this role. The doctor rewrites this file after every run, keeping only durable, task-agnostic bullets (repo structure, build/test recipes, general shell traps, workflow tips). Never edit this file as the role agent.

- Fixed end-of-run sequence, the same for every task: (1) load the kanban tools with `tool_search("kanban")` in the first block; (2) verify with a scoped test run, then a build; (3) apply the commit rule below; (4) record assumptions and results in one `kanban_update`; (5) stop. The rules below answer the "commit, accept, or update the card" questions; do not spend thinking blocks on them.
- Verification strategy is decided once, in the first planning block, from the task type and the frontmatter complexity (trivial → skip tests; new feature → tests first; refactor → tests before code; fix → failing test first). For a fix, also decide then whether an integration-level regression test is needed, and write it together with the failing unit tests, before the code change; never reopen that scope after green. The scoped suites to run are the ones owning the touched files; decide that once too, and never spend a thinking block re-choosing suites.
- Stack: Vite + Vitest, ESM (`"type": "module"`). Scripts: `npm run dev`, `npm run build`, `npm test` (= `vitest run --passWithNoTests`). Tests sit next to sources as `src/**/*.test.js`; Vite and Vitest share `vite.config.js` (relative `base`, node test env). `npm run build` parses only modules reachable from `main.js`; for a module it does not import, parse-check with `node -e "import('<path>')"`. A green build is a green build: never spend time on build output size, asset counts, or bundle composition.
- `src/math/` holds vec3/mat3/quat/mat4 helpers, out-param style (`add(out, a, b)`, column-major); reuse them, always pass a destination, never alias `out` with an input.
- Worktrees: tasks run in `.worktrees/<branch>`; `main` is the default branch. A fresh worktree has no `node_modules`, and the end-of-run build and vitest always need it: start `npm ci > /tmp/npm-ci.log 2>&1 &` in the first tool block and read or write code while it runs. Check the log once before the first vite/vitest use ("Cannot find module" means a missing install, not broken code). Give empty scaffold dirs a `.gitkeep`.
- New dependencies: redirect install output to a log (`npm install --loglevel=http > /tmp/npm.log 2>&1`), never a bare install against a long timeout. `~/.npmrc` sets `min-release-age=7` and `ignore-scripts=true`; check `npm view <pkg> time` before version floors. On failure read the log and `cat ~/.npmrc`; verify with cheap metadata, not blind retries.
- Commit rule: code changed and tests green → one commit, lockfile included when deps changed. Verification-only run on a clean tree → nothing to commit; put results on the card and stop. Never commit TASK.md, AGENTS.md, or `.kanban/`. Clean-room acceptance (`git archive HEAD | tar -x -C /tmp/check`, then `npm ci && npm test && npm run build` in the copy, confirm relative asset paths in `dist/index.html`, delete the copy) is required only when the run changed committed code.
- Settle deliverable, file placement, and data contracts in the first planning block; record assumptions on the task card. When a convention is derived (sign, axis, numbering, winding, mapping, units — per-unit vs total), write it once as an input-to-expected table and freeze it; never re-derive it in a later block. Every thinking block must end in a decision or a tool call; when a block produces only questions, run the cheapest probe that turns them into data.
- Batch independent calls in one block, and read each file at most once: keep a running map of what has been read; re-reading a file or re-printing a section already returned is waste, grep with context instead. For `edit`, include `path`, keep each `oldText` short, exact, and unique; two edits whose regions overlap or touch are rejected, so merge nearby changes into one edit before submitting.
- Test discipline: after writing a module, run its suite at once. Never run the same suite twice without an intervening code or test change. When a run fails, analyze it fully first, then batch the fix and the rerun into one step. After a fix edit, the rerun is the verification; if the identical failure persists, re-read the edited region before new hypotheses.
- Stop rule: a green scoped run is the evidence; report the pass count and move on. After green, edit again only to fix a real defect. Batch hygiene (dead code, unused imports, temporary debug exports — grep the diff for their markers) into the same edit pass as the last functional change, before the final green run; a post-green cleanup pass forces another full test-plus-build cycle.
- To prove a regression test catches the fixed bug, temporarily revert the fix (two small edits, or `git stash` while uncommitted), run only the one test file, and restore the fix — as commands separated by `;` in a single bash block so the restore always runs, never across several blocks. Expected result: red pre-fix, green post-fix.
- Debug computed data (geometry, physics, generated meshes) with one standalone `/tmp` script that imports the real module, loops every case, and prints actual vs expected side by side. A `/tmp` script must import repo modules by absolute path or `file://` URL: relative specifiers resolve against the script's own directory and fail with ERR_MODULE_NOT_FOUND outside the repo. Never suppress errors in probes: `try { ... } catch {}` and ignored exit codes hide the failure.
- Modules that touch browser APIs (canvas 2D, `document.createElement`, WebGL) cannot run under plain Node: define `document`/`OffscreenCanvas`/2d-context shims in the first draft of any such probe, not after the first `ReferenceError`. Test the pure layer with vitest; leave pixel and DOM output to a browser-check subagent. With a mock or recorder harness (Proxy-based GL context, call log), print one sample record before asserting on indices or tuple positions; a harness failure means the harness is wrong, so fix the harness and do not change production code based on it.
- Construct spatial test fixtures analytically from geometry (known normals, angles, symmetry), never by brute-force parameter sweeps. If a sweep is truly needed, seed it with one known-yes case, cap runtime at seconds, and treat a zero-hit result as a search problem before suspecting the production code. Validate layered derivations (raw vertices → discovered faces → ordered polygons → mass properties) one layer at a time against known reference values; a bug in a base layer poisons every layer above it.
- When a computed result is plausible but wrong, check the cheapest causes first: a swapped entry in a dispatch or lookup table, an inverted sign or winding, a constant copied from the wrong row, an argument in the wrong slot (viewport, matrix, out-param order), a scale factor applied twice or not at all. Print the mapping the code actually used. For contact or normal signs, gate on signed approach velocity (`v·n < 0`), never absolute speed.
- Read file contents with the `read` tool, not `cat`; use offset/limit for large files. Shell traps: single-character greps give noise, so grep a distinctive multi-char token with context flags; `ls`/`cat` on missing paths exits non-zero and prints to stderr, treat as noise, not failure. Validate workflow YAML with `python3 -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))" <file>` (actionlint is not installed).
- Precision and expectations: use `Float64Array` for math and physics state, Float64 in test expectations, and relative tolerances for accumulated sums; pick the precision once, up front, for the whole module family. Tests compute expected values through the same pipeline the code runs: import module constants and apply the module's own transforms before asserting; derive numeric expectations with a throwaway script, not mental arithmetic. When a red test shows a plausible actual value, suspect the expected value first. Where an exact count is fragile, assert a range.
- Formula-dense code (matrix math, geometry, shaders): pick one known-good reference and transcribe the implementation and the expected test values from it in a single pass. Cap convention research (axis signs, coordinate frames, vendor quirks) at one search round plus one fetch; if the source does not state the mapping, derive it once, freeze it, note it as an assumption, and move on.
- Delegate to background subagents in the planning block, not after you get stuck: reference research, browser checks (dev server on an uncommon port, console error scan, visual verification; the subagent kills the server and leaves the repo clean), and independent parallel work. Do not finalize constants that research will confirm before the subagent result arrives; write tests meanwhile. Never let two agents run npm or git commands in the same worktree.
