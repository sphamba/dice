# developer: project guidance for future agents of this role. The doctor rewrites this file after every run and keeps only durable, task-agnostic bullets. Never edit this file as the role agent.

- End-of-run sequence, fixed for every task: (1) block 1 holds three parallel calls, `tool_search("kanban")`, the TASK.md read, and the startup bash of the next bullet; never split them, that is the most common budget breach. (2) Scoped verification. (3) Commit rule. (4) One `kanban_update`. (5) A short final text with durable guidance, then stop. After the last green tool result the order is: spec-check bash if checks remain, `kanban_update`, final text. Do not put a thinking block between the green run and the card update: the skeleton already made every decision, so call `kanban_update` straight away and put wrap-up reasoning into the card notes. Card sections are fixed: Deliverable / Verification / Assumptions / Blockers / Manual checks left to other roles. Write notes from this skeleton; add no other sections.
- Worktree startup, one bash call, before any source read. Worktrees live in `.worktrees/<branch>` and track `main`. One call runs the chain: `cd <worktree> && ls -a && (test -d node_modules || (npm ci > /tmp/npm-ci.log 2>&1 &)) ; git merge --ff-only main; git log --oneline -1; git status --short; ls; ls src/*/` (list each `src/` subdirectory the task touches). This is the run's only state survey. It decides the run shape: HEAD holds the deliverable commit named in prior notes → verification-only skeleton; it does not → implement. It is also the file-presence record for sibling-dependency questions. A fresh worktree has no `node_modules`: chain `tail /tmp/npm-ci.log` before the first vite or vitest call. `git status` runs here, and again only after this run edited files. Never investigate branches or empty log ranges. Parallel tasks land on `main`; after a late merge, re-read code before editing. Later layout or notes questions fold into the block where they arise; never run a second survey.
- Verification-only run (HEAD holds the deliverable). Fixed order: startup trio; one bash that tails the install log, stages sibling copies if needed, runs the scoped suite, the build, and the `dist/index.html` asset check; a spec-check bash only when checks remain; `kanban_update`; stop. Run the acceptance command pinned in the task Specs verbatim; never re-derive or second-guess it mid-run. A spec existence or wiring question is settled by one grep whose output is the evidence of record; run the grep even when reasoning already concluded the answer, and never spend a thinking block predicting it. Never re-count tests, never re-list exports that prior notes name, never re-run a git survey on an unedited tree. A clean run fits in three tool turns and five tool calls plus the final text; more means a rule broke. On a repeat verification run at the same HEAD, run the pinned suite once and refresh only the Verification line on the card; never expand scope to justify the run. Blocker and assumption lines carry over until startup evidence shows a change.
- Build evidence rules. A fresh build's hashed asset name proves nothing: the same tree gives the same hash, a changed tree a new hash. Never compare an asset hash against prior notes, and never treat a hash change as a defect or a hash match as confirmation; check only that `dist/index.html` references `./assets/...` relative paths. The asset grep is valid only after a green build line (`✓ built in`); after a failed build the on-disk `dist/` is stale, so skip the grep or mark the check stale on the card instead of reporting a false green.
- Sibling-task dependency (a module the spec names that a parallel branch owns): stage exactly the named module files with `git show <branch>:<path> > <path>`; never stage the sibling's tests or fixtures, never merge the branch, never write a shim or replacement. Use the full branch ref `feat/<shortName>` from the card or `git worktree list`; on a ref error run `git branch --list '*<fragment>*'` once in the same block and retry. Read the copy before writing tests against its API. Never run a suite or build with a known-missing import: a red run against it buys nothing. Verify against the copy, remove it in the commit block (or the spec-check block on a verification-only run), and record the dependency on the card. The decision is closed once made; only new tool evidence reopens it.
- Verification strategy is decided once, in the first planning block, from task type and complexity: trivial → skip tests; new feature → tests first; refactor → tests before code; fix → failing test first, written together with any regression test. Scoped suites are the ones owning the touched files. After that, never reopen scope, re-choose suites, or add one more probe; settle a coverage question with one grep for existing tests next to the sources, in the same block. Ambiguous spec wording: decide once, record the assumption on the card, move on.
- Stack: Vite + Vitest, ESM (`"type": "module"`). Scripts: `npm run dev`, `npm run build`, `npm test` (= `vitest run --passWithNoTests`). Tests sit next to sources as `src/**/*.test.js`; Vite and Vitest share `vite.config.js`. The build parses only modules reachable from `main.js`; parse-check anything else with `node -e "import('<path>')"`. A green build is a green build: never spend time on bundle size or asset counts. Log installs (`npm install --loglevel=http > /tmp/npm.log 2>&1`), never a bare install against a long timeout. `~/.npmrc` sets `min-release-age=7` and `ignore-scripts=true`; check `npm view <pkg> time` before version floors. Piping a command to `tail` masks its real exit code (`$?` is `tail`'s): judge green from the reporter output (`N passed`) or set `set -o pipefail` first.
- `src/math/` holds vec3/mat3/quat/mat4 helpers, out-param style (`add(out, a, b)`, column-major). Reuse them and always pass a destination; never alias `out` with an input, in production code, probes, or test helpers. Before writing a probe or test that calls a helper, grep the module's exported names once; a guessed API name costs a run-and-fix round.
- Commit rule: code changed and tests green → one commit, lockfile included when deps changed. Verification-only run on a clean tree → no commit, card only. Never commit TASK.md, AGENTS.md, or `.kanban/`. Settle ignore/tracked-file questions with one `git status` plus one `.gitignore` read in the same block, never in thinking. Clean-room acceptance, only when the run changed committed code: `git archive HEAD | tar -x -C /tmp/check`, then in the copy run `npm ci`, `npm test`, `npm run build` separated by `;`, never `&&` (one failing step must not hide later results). On failure read the log tail and name the failing suite before any re-run. Then delete the copy.
- Planning discipline: settle deliverable, file placement, and data contracts in the first planning block. One topic per thinking block, closed with a decision or a tool call. Freeze a derived convention (sign, axis, units, placement) once as an input-to-expected table; never re-derive it. A decision recorded in a plan or on the card is closed; reopen only after new tool evidence. A thinking block that restates what the run already knows (the startup output, prior notes, this file's recipes) is waste: end it with the one command that answers the open question, or skip it. The run-shape statement can be one line leading the next tool call. One planning block per file written: fold the API map, conventions, and draft plan into it, then write in the next block.
- Read discipline: read each file at most once; batch module reads into one or two blocks of parallel `read` calls. Read files whole under ~400 lines, with the `read` tool, not `cat`. A zero-hit grep on one file: rerun directory-wide (`grep -rn "<symbol>" src/`) in the same block. For `edit`, keep each `oldText` short, exact, and unique; merge nearby changes into one edit, because overlapping edits are rejected. Integration tasks (wiring many modules into one file): a batched export map (`grep -n "^export" src/**/*.js`), then batched reads, then one planning block, then write.
- Test discipline: run a new suite at once after writing the module. The first red run of a tests-first suite is the expected signal; write the module in the next block without analysis. Never run the same suite twice without an intervening change. On failure, analyze fully, then batch fix and rerun into one step; if the identical failure persists, re-read the edited region before new hypotheses. Vitest default timeout is 5 s; pass an explicit one for long simulations and keep `expect` out of per-step loops. A red wall-clock or perf assertion in a suite the task did not touch is environmental noise: read the log tail once, record it on the card, move on, never re-run it to confirm.
- Card notes: compose from the TASK.md copy read at startup, changing only the lines the new evidence changes. Never re-enumerate deliverables, exports, or test counts from the repo when prior notes already carry them. On a re-verification run with no new findings, the payload is the prior notes with at most the Verification line refreshed. `kanban_update` is one call; choosing wording is never a block, and the update never re-argues decisions.
- Stop rule: a green scoped run is the evidence; report the pass count and move on. After green, edit only to fix a real defect; a micro-optimization thought of after green goes into the last functional edit before the final green run or is skipped. Batch hygiene (dead code, unused imports, debug leftovers, diff grep for their markers) into the same edit pass as the last functional change. Post-green re-reads count as verification only when they check a spec point. Once the evidence is in hand, the card update is the only remaining step.
- Test-environment globals are partial: Node 21+ and jsdom expose `navigator` without `vibrate` and no `AudioContext`. Feature-gate browser APIs on the function (`typeof navigator.vibrate === 'function'`), not on global presence, or tests and real browsers disagree. Design fakes (audio, vibration, GL) in the planning pass as minimal recorders: settable clock, call log, injectable functions. Derive test values (thresholds, caps, counts) from the module contract so the suite is green on the first run. If unsure what the environment provides, probe once (`node -e "console.log(typeof navigator, typeof AudioContext)"`) in the same block as the test draft.
- Temporary copies and probes: copy a file to `/tmp` before temporary changes and restore or delete it in the same bash block chained with `;`. Regression proof: red before the fix, green after. A probe that copies production modules must trace the full call path, caller included; a partial copy makes probe and production disagree. Regenerate instrumented copies from HEAD at the start of every measurement run, or import the real module and copy nothing; a stale copy reports phantom failures.
- Physics and numeric probes: replicate the production step sequence exactly, every substep in order; a partial re-implementation produces false contradictions. Never suppress errors (`catch { }`, ignored exit codes). Validate the fixture before trusting measurements (spawn margins, valid initial state, one sanity-checked step); never tune production constants from a broken fixture. A spec-suggested fix is a hypothesis: print the actual intermediate values at the failure site first, then implement the root cause and record any deviation as an assumption on the card. When a computed magnitude is implausible, print the whole value chain (input → constant → derived value); suspect a scale applied twice, a per-unit vs total mix-up, or an argument in the wrong slot. For contact or normal signs, gate on signed approach velocity (`v·n < 0`), never absolute speed. Validate layered derivations one layer at a time against reference values.
- Repro search for numerically degenerate bugs: do not hand-tune poses. In one script, sweep the axes the spec names or implies over a decade around the failure scale, seeded with one known-yes case, with a pass predicate that catches every symptom shape. A zero-hit sweep: widen axes or shrink steps. When a sweep hits, minimize it and use it as the regression test. Pick tuned constants (epsilons, welds, tolerances) from the same sweep: the smallest value with zero failures across every symptom shape and fixture; keep the constant unexported with a one-line unit comment.
- Precision: use `Float64Array` for math state and Float64 in expectations, relative tolerances for accumulated sums. Compute expected values through the module's own helpers with a one-line `node -e` script in the same block as the assertion; never mental arithmetic, including counts, limits, and totals in UI or DOM probes (take them from module constants). Write expectations in final form on the first pass (imported constants, tolerance choice); a later refactor to constants is a wasted run. Quantities that physics lets collide tie legitimately: assert ordering non-strictly unless the spec demands strictness. Formula-dense code: transcribe implementation and expectations from one known-good reference in a single pass; cap convention research at one search round plus one fetch, then derive, freeze, record as an assumption.
- UI, DOM, subagents, and live checks: use `setAttribute('aria-label', ...)` and `setAttribute('aria-live', ...)`, never `element.ariaLabel`; never attach custom properties to DOM nodes; a builder returns `{ element, sync }` pairs and one `syncAll` refreshes them. Modules that touch `document`, canvas, or GL need shims in the first draft of a probe; with a recorder harness, print one sample record before asserting on indices or tuples, and treat a harness failure as a harness bug. Live browser probes read the owning module or its test first; a FAIL on an invented expectation is a probe bug. Delegate reference research to background subagents in the planning block; launch browser checks (dev server on an uncommon port, console error scan, kill the server, leave the repo clean) as soon as the build is green, then commit and update the card while the subagent runs; never let two agents run npm or git commands in the same worktree. Live checks use `playwright-core` with the cached Chromium in `~/.cache/ms-playwright`; headless WebGL needs `--use-angle=swiftshader`; if the page does not wire a renderer, import and call the renderer factory from page context. When the only open item is a running subagent's result, block on it in the next tool call, never in a thinking block.
