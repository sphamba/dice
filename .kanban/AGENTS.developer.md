# developer: project guidance for future agents of this role. The doctor rewrites this file after every run and keeps only durable, task-agnostic bullets. Never edit this file as the role agent.

- Startup trio, first block, exactly three parallel invokes: `tool_search("kanban")`, the TASK.md read, and the worktree bash of the next bullet. `read` and `bash` are built-ins, usable before the kanban toolset answers. Issue tool calls in parallel whenever no call consumes another's output.
- Worktree startup, one bash call, before any source read. Worktrees live in `.worktrees/<branch>` and track `main`. One call runs: `cd <worktree> && ls -a && if test -d node_modules; then echo 'deps: present'; else echo 'deps: install started'; (npm ci > /tmp/npm-ci.log 2>&1 &); fi ; git merge --ff-only main; git log --oneline -1; git status --short; ls; ls src/*/`. The glob lists every `src/` tree, that is the one survey, do not filter it and do not repeat it. Read the install-state echo from the output, never re-derive it. A failed `git merge --ff-only main` means divergence: never retry another merge, merges belong to the merger role, record one Blockers line and continue. The run shape is mechanical, decided from this output plus the prior notes alone: verification-only when the tree is clean, ff-only to main is up to date, and the notes report the deliverable complete with green evidence. Implement on a first run, an incomplete or silent card, or a dirty tree. State the shape as one lead-in line on the next tool call, never in a thinking block. Never re-run startup facts to re-decide the shape, and never grep source to pre-confirm a deliverable the notes already report. If the startup leaves a spec-named module missing, settle its presence on main in the same block with `git ls-tree main --name-only src/<dir>/`. Parallel tasks land on `main`, after a late merge re-read code before editing. Never investigate branches or empty log ranges.
- Turn budgets, per shape. Verification-only: startup trio, one chained bash, one `kanban_update`, final text, zero thinking blocks. The bash runs, in order: `tail /tmp/npm-ci.log` only when the startup echo said `install started` (the file is shared across runs, an unconditional tail reads a stale log), the task-pinned acceptance command verbatim, then `npm run build` plus the asset check unless the deliverable is test-only. On a re-run the prior notes are the evidence of record, the pinned acceptance commands are the only re-verification, and the notes' numeric, probe and perceptual claims are never audited, re-derived or re-probed. A verification-only run commits nothing: exactly one bash sits between the startup trio and the card update, whatever doubt surfaces. Implement: startup trio, one planning block, write, one scoped verify, commit, `kanban_update`, final text. The single planning block also closes the test-scope call. A fix task adds the one expected red-to-green cycle, every further red-to-green round names the rule that justifies it. End-of-run order is fixed: green evidence, then `kanban_update` straight away (wrap-up reasoning goes into the card notes), then short final text, then stop. When the spec mandates a live browser check, the live verdict is part of the green evidence: commit and launch the check as parallel calls in one turn, and the card follows the verdict. A second `kanban_update`, a thinking block after green, or a block between the green run and the card update is a breach. A run over budget means a rule broke: find the rule, never add probes.
- Read and edit discipline. Batch reads: the module under change, its `.test.js`, and every module that defines data the assertions use go into one block of parallel `read` calls. Read each file at most once, whole under ~400 lines, with the `read` tool, not `cat`. The `read` tool truncates long output (about 2000 lines or 50 KB). Truncated output is a tool limit, not corruption: settle the file once with one bash (`wc -l <file>` plus `tail -n 40 <file>`, and a `node -e "import('<path>')"` parse check when the tail looks odd), then `read` only the needed ranges with `offset`. Never re-read a section already in context, and never re-read to hunt imagined corruption. Draft no assertion constant before its defining source line is in hand. A zero-hit grep on one file: rerun directory-wide in the same block. All changes to one file are one `edit` call in one block, never append to an already-edited file with a bash heredoc. Keep each `oldText` short, exact, unique, merge nearby changes. Trust a write or edit success: never re-read your own fresh output to hunt an imagined typo, the scoped suite is the re-check, and a re-read without a tool error or a failing suite behind it is a breach. When an in-place edit of a throwaway script gates the same bash run, chain a one-line grep for the edited marker into the same command, so a non-matching replacement cannot hand stale results to the run that follows. A deletion settles orphan imports once, in the planning block: one grep over every name the deleted block referenced. Integration tasks: a batched export map (`grep -n "^export" src/**/*.js`), batched reads, one planning block, then write.
- Planning discipline: the one planning block settles everything at once (run shape, deliverable, file placement, data contract, observability route, test call). Write the data contract first and once: field names, nesting, and whether records hold prepared objects or raw snapshots. Tests and code use that exact shape, a flat fixture against a nested record (or the reverse) yields NaN instead of a clear diff. Test-scope call: trivial, skip tests. New feature, tests first. Refactor, tests before code. Fix, failing test first written with any regression test. Spec leaves the choice open, pick in one line and move on. Ambiguous spec wording: decide once, record the assumption on the card, move on. One topic per thinking block, closed with a decision or a tool call that gathers new evidence. A block that restates known facts, re-derives a frozen convention, or lists alternatives without picking one is waste, emit the probe command instead with one lead-in line. One channel per statement: a lead-in line on a tool call replaces a thinking block, never repeats one. A spec existence or wiring question is settled by one grep in the same block, the output is the evidence of record. Freeze a derived convention (sign, axis, units, placement, threshold, time window) once as an input-to-expected table, never re-derive it in a later block. A decision recorded in a plan or on the card is closed, reopen only on new tool evidence. Design cap: the smallest change that can pass the acceptance test, constants frozen with at most one probe sweep. After a failed command, the next block is one tool call that gathers the missing evidence, never a plan revision. One planning block per file written: fold the API map, conventions, and draft into it, then write in the next block.
- Test discipline. Scoped suites are the ones owning the touched files, run a new suite at once after writing the module. The first red run of a tests-first suite is the expected signal, write the module in the next block without analysis. Never run the same suite twice without an intervening change, each acceptance check runs once per run: green closes it, never re-run a green check or spend a block doubting green evidence. On failure, analyze fully, then batch fix and rerun into one step, if the identical failure persists re-read the edited region before new hypotheses. Vitest default timeout is 5 s, pass an explicit one for long simulations and keep `expect` out of per-step loops. Derive fixture layout from geometry constants before writing the test: bodies spaced under a body width start in contact, and the scene then measures collision response, not settling. A multi-body settle test asserts rest, containment and finiteness, never exact per-body orientation (an exact edge balance is a valid equilibrium). A physics outcome with legitimate variance across seeds or orientations (apex height, settle time, bounce count) gets one aggregate assertion (mean or max over the seeded cases, thresholds derived from one probe over the same seeds), never a per-case numeric bound. An assertion that failed twice on fixture grounds is demoted to the robust form in the next edit, never a third fixture re-tune. Every assertion comes from source read in this run, an expectation copied from another test without checking costs a fix edit.
- Solver-internal state (impulses, biases, cache entries) cancels or overwrites itself after the solve, so post-solve assertions cannot see it. When the deliverable is such state, export the decision logic as a pure function, test it on constructed inputs, and add one thin assertion on the stored cache or side effect. Decide this route inside the planning block, never reopen the observability question in a later block.
- Stack, shell, and math traps: Vite + Vitest, ESM (`"type": "module"`). Scripts: `npm run dev`, `npm run build`, `npm test`. Call the pinned scripts, never `npx <tool>`, the one legitimate `npx` filters a single test by name: `npx vitest run <file> -t '<name>'`. A task-pinned acceptance command overrides this, state the precedence in one lead-in line on the bash. Tests sit next to sources as `src/**/*.test.js`, Vite and Vitest share `vite.config.js`. The build parses only modules reachable from `main.js`, parse-check anything else with `node -e "import('<path>')"`. A green build is a green build: never audit bundle size or asset counts. Log installs (`npm install --loglevel=http > /tmp/npm.log 2>&1`), never a bare install against a long timeout. `~/.npmrc` sets `min-release-age=7` and `ignore-scripts=true`, check `npm view <pkg> time` before version floors. Piping to `tail` or grepping test output masks the real exit code: judge green from the reporter output (`N passed`) or set `pipefail` first, and when grepping outcomes across several runs match both outcomes (`grep -E 'Tests +[0-9]+ (passed|failed)|expected [0-9.]+'`) so a failure-only pattern never turns green runs silent. `src/math/` holds vec3/mat3/quat/mat4 helpers, out-param style (`add(out, a, b)`, column-major): reuse them, always pass a destination, never alias `out` with an input in production code, probes, or test helpers, and grep a module's exported names once before writing a probe or test that calls it (a guessed API name costs a run-and-fix round).
- Build evidence rules. A change confined to `*.test.js` files never enters the build graph: skip `npm run build` and the asset check for it, and say so in one lead-in line on the verify bash. A fresh build's hashed asset name proves nothing, never compare it against prior notes. The one asset check: after a green build line (`✓ built in`), run `grep -oE '(src|href)="[^"]+"' dist/index.html` once, inside the same chained bash when possible. Judge the check only from this output, close it green and never re-run it. After a failed build the on-disk `dist/` is stale: skip the grep or mark the check stale on the card.
- Sibling-task dependency (a module the spec names that a parallel branch owns): stage exactly the named files with `git show <ref>:<path> > <path>`, never stage the sibling's tests or fixtures, never merge the branch, never write a shim. main is a ref like any branch, staging from main never reopens the merge question. Use the full ref from the card or `git worktree list`, on a ref error run `git branch --list '*<fragment>*'` once in the same block and retry. Read the copy before writing tests against its API. Never run a suite or build with a known-missing import. Verify against the copy, remove it in the commit block, and record the dependency on the card. The decision is closed once made, only new tool evidence reopens it.
- Commit rule: code changed and tests green, one commit, lockfile included when deps changed. Verification-only run on a clean tree, no commit, card only. Never commit TASK.md, AGENTS.md, or `.kanban/`. Settle ignore/tracked-file questions with one `git status` plus one `.gitignore` read in the same block, never in thinking. Clean-room acceptance, only when the run changed committed code: `git archive HEAD | tar -x -C /tmp/check`, then in the copy run `npm ci`, `npm test`, `npm run build` separated by `;` (one failing step must not hide later results). On failure read the log tail and name the failing suite before any re-run. Then delete the copy.
- Card notes: compose from the TASK.md copy read at startup, changing only the lines the new evidence changes. Sections are fixed: Deliverable / Verification / Assumptions / Blockers / Manual checks left to other roles, placement is never debated (a merge divergence from main is a Blockers line). The verification line names the HEAD short hash, so the next run's shape decision stays mechanical. Never re-enumerate deliverables, exports, or test counts when prior notes already carry them. Blocker, assumption, and manual-check lines carry over until startup evidence shows a change, and `kanban_update` replaces the whole notes field, so carried lines are resent verbatim. `kanban_update` is one call per run, sent once after green, a wording fix never justifies a second call, resend only for a factual error such as a wrong hash or a dropped carried line. After it returns the run is closed: never re-read the card to audit its wording.
- Subagents and live checks. A background `Agent` call returns at once, `get_subagent_result(wait:true)` blocks the turn for the subagent's full duration (minutes for a browser check). Batch every independent call into the launch turn as parallel invokes, then block on the result as one bare tool call in the next turn (never in a thinking block, never with wrap-up reasoning around it). Delegate reference research to background subagents in the planning block. Launch browser checks as soon as the scoped suite and build are green: dev server on an uncommon port, console error scan, kill the server, leave the repo clean. Never let two agents run npm or git commands in the same worktree at once. Live checks use `playwright-core` with the cached browser in `~/.cache/ms-playwright`, it is not a package.json dependency, so locate it in one command (global npm root, or a prior run's node_modules), never a multi-block filesystem hunt. Headless WebGL needs `--use-angle=swiftshader`, full Chromium can crash at launch (SIGTRAP) on this machine, fall back to `chrome-headless-shell` once, do not debug it. If the page does not wire a renderer, import and call the renderer factory from page context. Live browser probes read the owning module or its test first, a FAIL on an invented expectation is a probe bug.
- Stop rule: a green scoped run is the evidence, report the pass count and move on. After green, edit only to fix a real defect, a micro-optimization thought of after green is skipped. No thinking block sits between a green run and the commit, act on a settled rule in the next tool call with its one-line lead-in. Batch hygiene (dead code, unused imports, debug leftovers) into the same edit pass as the last functional change. Never expand scope to justify the run. Once the evidence is in hand the card update is the only remaining step, after it the run ends with no post-send block of any kind.
- Test environment and UI. jsdom under Node exposes only some browser globals (for example no `AudioContext`, no `navigator.vibrate`): feature-gate browser APIs on the function (`typeof navigator.vibrate === 'function'`), not on global presence. Design fakes (audio, vibration, GL, canvas) in the planning pass as minimal recorders: settable clock, call log, injectable functions. With a recorder harness, print one sample record before asserting on indices or tuples, and treat a harness failure as a harness bug. If unsure what the environment provides, probe once (`node -e "console.log(typeof navigator, typeof AudioContext)"`) in the same block as the test draft. DOM: `setAttribute('aria-label', ...)` and `setAttribute('aria-live', ...)`, never `element.ariaLabel`, never attach custom properties to DOM nodes, a builder returns `{ element, sync }` pairs and one `syncAll` refreshes them.
- Physics probes and fixture validation. Replicate the production step sequence exactly, every substep in order, a partial re-implementation produces false contradictions. Validate the fixture before trusting any measurement: spawn clean or drop-and-settle, then confirm rest-state drift is ~zero over N steps (a body spawned at rest height with a random orientation intersects the floor with its corners, and solver kicks then masquerade as the effect under test, poisoning every sweep downstream). Sweep a parameter only against a validated fixture, when sweep results contradict a derived expectation suspect the fixture before the formula. Never suppress errors (`catch { }`, ignored exit codes). Probes import project modules by absolute path (`const R = '<worktree>'; await import(R + '/src/...')`), a probe under `/tmp` with relative `./src` imports dies before it runs. For contact or normal signs, gate on signed approach velocity (`v·n < 0`), never absolute speed. Repro search for numerically degenerate bugs: in one script sweep the axes the spec names over a decade around the failure scale, seeded with one known-yes case, with a pass predicate that catches every symptom shape (zero hits, widen axes or shrink steps, a hit, minimize it and use it as the regression test). Tuned constants come from the same sweep: the smallest value with zero failures across every symptom shape and fixture, kept unexported with a one-line unit comment. Temporary copies: copy to `/tmp`, restore or delete in the same bash block chained with `;`, and a probe that copies production modules must trace the full call path, caller included, or import the real module and copy nothing.
- Failure diagnosis runs by print, never by derivation. Never re-derive vector math, basis construction, or solver algebra in a thinking block: write one probe that prints the whole value chain (inputs, constants, derived values) at the failure site. The probe uses the failing test's exact fixture objects, imported or rebuilt from the test's literals, a probe on invented look-alike data measures the invention, not the bug. A NaN, an unclamped magnitude, or an implausible value is a data-shape question first: print the record and its `Object.keys` at the failure site and compare fixture shape against the producing code's record (suspect a shape or field-name mismatch, a scale applied twice, a per-unit vs total mix-up, or an argument in the wrong slot) before any formula work. A spec-suggested fix is a hypothesis: the instrumented probe goes out before the hypothesis is written. One probe per hypothesis, two dead hypotheses mean the probe measured the wrong thing: change the measurement, not the hypothesis count.
- Symptom observability. A reported visual symptom is a measurement claim: first check what the camera projection can show. An orthographic top view collapses height, so screen bbox, blob area, and shadow-gap math cannot see a height-defined symptom, read the camera and shader setup before interpreting any screenshot. Headless sweeps that fail to reproduce a live symptom neither disprove it nor localize it: after two dead sweeps, stop sweeping and instrument the live page (add a temporary hook `globalThis.__world = world` in the entry module, drive the real page, and read engine state per frame), one state read beats a chain of pixel estimates. Pixel forensics, when unavoidable: confirm the reference frame actually shows the reference state before deriving numbers from it, and treat shadow- or projection-derived heights as model estimates, never ground truth. Remove the instrumentation hook in the commit block, never ship a debug global.
- Numeric traps and precision. Unary minus on a `Float64Array` (any typed array) yields `NaN`, not element-wise negation: negate element-wise or multiply by -1. After any sign flip or formula edit in vector math, print one concrete derived vector from a `node` probe before rerunning the suite (a NaN or a wrong-facing vector shows there, not in a test diff). When two mathematically equivalent forms disagree, print both from the same inputs in one probe, never alternate edits hoping the suite turns green. Use `Float64Array` for math state and Float64 in expectations, relative tolerances for accumulated sums. `expect(x).toBe(0)` fails on `-0` (`Object.is` semantics): assert small magnitudes with `toBeCloseTo` or an `Math.abs` bound, and pick the tolerance form on the first pass. Compute expected values through the module's own helpers with a one-line `node -e` script in the same block as the assertion, never mental arithmetic (including counts, limits, and totals in UI or DOM probes, take them from module constants). Quantities that physics lets collide tie legitimately, assert ordering non-strictly unless the spec demands strictness. Formula-dense code: transcribe implementation and expectations from one known-good reference in a single pass, cap convention research at one search round plus one fetch, then derive, freeze, record as an assumption.
- Benchmarks, A/B, and wall-clock thresholds. A wall-clock assertion measures the machine as much as the code: never a functional failure, never more than one A/B probe. The one probe, one bash: `rm -rf /tmp/ab && mkdir /tmp/ab && git archive HEAD | tar -x -C /tmp/ab && cp -r src /tmp/ab/ && ln -s "$PWD/node_modules" /tmp/ab/node_modules`, overlay the candidate change in the copy, run the pinned test once per variant (never extract main for a timing question, an overlay of one change is the tighter control). Then fix the confirmed cause in one edit, or record the measured cause on the card, the merger role owns any rerun. Equal work counts with a large slowdown in a float-heavy loop points at subnormal arithmetic first: print the minimum nonzero magnitudes once, fix with an unexported epsilon floor. The same extract-and-overlay recipe, run for behavior instead of time, answers whether a defect exists at the baseline commit: one extraction, one probe, one verdict, a defect absent at both commits shifts the search to measurement and rendering, never more physics sweeps.
