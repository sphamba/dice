# developer: project guidance for future agents of this role. The doctor rewrites this file after every run and keeps only durable, task-agnostic bullets. Never edit this file as the role agent.

- End-of-run sequence, fixed for every task: (1) first block with three parallel calls, `tool_search("kanban")`, the TASK.md read, and the startup bash of the next bullet; (2) scoped verification; (3) the commit rule; (4) one `kanban_update`; (5) a short final text block, then stop. The TASK.md read and the startup bash use core tools and do not depend on the `tool_search` result: issue all three calls in the first block even while the kanban tools are still loading, never one per block. A lead-in text names only the calls the same block issues; never promise a call and defer it to the next block. Wrap up in tool blocks only: after the last green tool result the remaining blocks are, in order, an optional spec-check bash, then `kanban_update`, then the final text. A thinking block between a green run and the card update is always a rule break; put wrap-up reasoning into the card notes instead.
- Worktree startup, one block, before any source read. Worktrees live in `.worktrees/<branch>` and track `main`. One bash call backgrounds the install and runs the chain: `npm ci > /tmp/npm-ci.log 2>&1 & git log HEAD..main --oneline; git merge --ff-only main; git log --oneline -3; ls; ls src/*/; git status --short` (list each `src/` subdirectory the task touches). This is the run's only state survey. It decides the run shape in one step: HEAD holds the deliverable commit named in prior notes → verification-only skeleton; it does not → implement. It also flags a spec-named output file that does not exist (sibling dependency). A fresh worktree has no `node_modules`: chain `tail /tmp/npm-ci.log` before the first vite/vitest call; "Cannot find module" means a missing install. `git status` runs here and again only after this run edited files. Never investigate branches or empty log ranges. After a late merge from `main`, re-read code before editing.
- No second survey. The startup output, the TASK.md read, and the verification output stay in context for the whole run. Never re-grep exports, re-list directories, or re-run `git status` on an unedited tree to confirm a fact. If a card line needs a fact, quote prior notes or the startup output. A later git, layout, or wiring question is one command folded into the block where it arises, never a new survey. This is the most common budget overrun on clean runs.
- Verification-only run (HEAD holds the deliverable). Fixed order, no thinking block after the startup block: startup block; one bash that tails the install log, stages a sibling copy if needed, runs the scoped suite, the build, and the `dist/index.html` asset check; a spec-check bash only when checks remain; `kanban_update`; stop. A clean run fits in three tool turns and five tool calls plus the final text; four turns and six calls when a spec-check remains; more means a rule broke. Run the acceptance command pinned in the task Specs verbatim; never re-derive or doubt it mid-run. The spec-check holds only checks the green run and the startup output did not answer; when nothing is left, skip it and call `kanban_update` next. Evidence is not re-derived: the suite output is the pass count, prior notes name the exports, the tree is clean unless edited. Blocker and assumption lines carry over until startup evidence shows a change; never re-litigate them.
- Sibling-task dependency (a module the spec names that a parallel branch owns): stage exactly the named module files with `git show <branch>:<path> > <path>`, never the sibling's tests or fixtures, never a merge of the branch, never a shim. Use the full branch ref `feat/<shortName>` from the card or `git worktree list`; on a ref error run `git branch --list '*<fragment>*'` once in the same block and retry. Read the copy before writing tests against its API. Never run a suite or build with a known-missing import. Verify against the copy, remove it in the commit block (or the spec-check block on a verification-only run), and record the dependency on the card. The decision is closed once made; only new tool evidence reopens it.
- Verification strategy is decided once, in the first planning block, from task type (trivial → skip tests; new feature → tests first; refactor → tests before code; fix → failing test first, written together with any regression test). Scoped suites are the ones owning the touched files. Never reopen scope, re-choose suites, or add "one more probe"; settle a coverage question with one grep for existing tests next to the sources, in the same block. Ambiguous spec wording: decide once, record the assumption on the card, move on.
- Stack: Vite + Vitest, ESM (`"type": "module"`). Scripts: `npm run dev`, `npm run build`, `npm test` (= `vitest run --passWithNoTests`). Tests sit next to sources as `src/**/*.test.js`; Vite and Vitest share `vite.config.js`. The build parses only modules reachable from `main.js`; parse-check anything else with `node -e "import('<path>')"`. A green build is a green build: never spend time on bundle size or asset counts. Log installs (`npm ci > /tmp/npm-ci.log 2>&1`), never a bare install against a long timeout. `~/.npmrc` sets `min-release-age=7` and `ignore-scripts=true`; check `npm view <pkg> time` before version floors. Piping a command to `tail` masks its real exit code: judge green from the reporter output (`N passed`), or set `set -o pipefail` first.
- `src/math/` holds vec3/mat3/quat/mat4 helpers, out-param style (`add(out, a, b)`, column-major). Reuse them and always pass a destination; never alias `out` with an input, in production code, probes, or test helpers. Before writing a probe or test that calls a helper, grep the module's exported names once; a guessed API name costs a run-and-fix round.
- Commit rule: code changed and tests green → one commit, lockfile included when deps changed. Verification-only run on a clean tree → no commit, card only. Never commit TASK.md, AGENTS.md, or `.kanban/`. Settle ignore/tracked-file questions with one `git status` plus one `.gitignore` read in the same block. Clean-room acceptance, only when the run changed committed code: `git archive HEAD | tar -x -C /tmp/check`, then in the copy run `npm ci`, `npm test`, `npm run build` separated by `;`, never `&&` (one failing step must not hide later results). Confirm relative asset paths in `dist/index.html`, then delete the copy.
- Planning discipline: settle deliverable, file placement, and data contracts in the first planning block. One topic per thinking block, closed with a decision or a tool call. Freeze a derived convention (sign, axis, units, placement) once as an input-to-expected table; never re-derive it. A decision recorded in a plan or on the card is closed; reopen only after new tool evidence. A thinking block that restates known facts is waste: end it with the one command that answers the open question, or skip it. One planning block per file written: fold the API map, conventions, and draft plan into it, then write in the next block.
- Read discipline: read each file at most once; batch module reads into one or two blocks of parallel `read` calls. Read files whole under ~400 lines, with the `read` tool, not `cat`. A zero-hit grep on one file: rerun directory-wide (`grep -rn "<symbol>" src/`) in the same block. For `edit`, keep each `oldText` short, exact, and unique; merge nearby changes into one edit.
- Test discipline: run a new suite at once after writing the module. The first red run of a tests-first suite is the expected signal; write the module in the next block without analysis. Never run the same suite twice without an intervening change. On failure, analyze fully, then batch fix and rerun into one step; if the identical failure persists, re-read the edited region before new hypotheses. Vitest default timeout is 5 s; pass an explicit one for long simulations and keep `expect` out of per-step loops. A red wall-clock or perf assertion in a suite the task did not touch is environmental noise: read the log tail once, record it on the card, move on, never re-run it to confirm.
- Card notes: `kanban_update` is one call. Compose the payload in one pass from the TASK.md copy read at startup: take the prior Notes text as the base and change only the lines the new evidence changes. Never re-enumerate deliverables, exports, or test counts from the repo when prior notes carry them. Wording is never an open question: the startup TASK.md read is the only evidence the notes need; never re-read TASK.md or your own posted payload to check spelling or phrasing. A typo in a posted card stays; a second update only fixes a factual error, and it edits only that line. Card sections are fixed: Deliverable / Verification / Assumptions / Blockers / Manual checks left to other roles; no other sections.
- Stop rule: a green scoped run is the evidence; report the pass count and move on. After green, edit only to fix a real defect; a micro-optimization thought of after green is skipped or goes into the last functional edit before the final green run. Batch hygiene (dead code, unused imports, debug leftovers) into the same edit pass as the last functional change. Post-green re-reads count as verification only when they check a spec point. Once the evidence exists, the card update is the only remaining step.
- Test environment: Node and jsdom expose globals like `navigator` without their methods, and lack `AudioContext` and GL contexts. Feature-gate a browser API on the function itself (`typeof api.method === 'function'`), not on global presence, or tests and real browsers disagree. Design fakes (audio, vibration, GL) in the planning pass as minimal recorders: settable clock, call log, injectable functions. If unsure what the environment provides, probe once (`node -e "console.log(typeof navigator, typeof AudioContext)"`) in the same block as the test draft. Derive test values from the module contract so the suite is green on the first run.
- Temporary copies and probes: copy a file to `/tmp` before temporary changes and restore or delete it in the same bash block chained with `;`. Regression proof: red before the fix, green after. A probe that copies production modules must trace the full call path, caller included; a partial copy makes probe and production disagree. Regenerate instrumented copies from HEAD at the start of every measurement run, or import the real module and copy nothing; a stale copy reports phantom failures against already-fixed code.
- Physics and numeric probes: replicate the production step sequence exactly, every substep in order; a partial re-implementation produces false contradictions. Never suppress errors (`catch { }`, ignored exit codes). Validate the fixture before trusting measurements; never tune production constants from a broken fixture. A spec-suggested fix is a hypothesis: print the actual intermediate values at the failure site first, then implement the root cause and record any deviation as an assumption on the card. When a computed magnitude is implausible, print the whole value chain (input → constant → derived value); suspect a scale applied twice, a per-unit vs total mix-up, or an argument in the wrong slot. For contact or normal signs, gate on signed approach velocity (`v·n < 0`), never absolute speed. Validate layered derivations one layer at a time against reference values.
- Repro search for numerically degenerate bugs: do not hand-tune poses. In one script, sweep the axes the spec names or implies over a decade around the failure scale, seeded with one known-yes case, with a pass predicate that catches every symptom shape. A zero-hit sweep: widen axes or shrink steps. When a sweep hits, minimize it and use it as the regression test. Pick tuned constants (epsilons, welds, tolerances) from the same sweep: the smallest value with zero failures across every symptom shape and fixture; keep the constant unexported with a one-line unit comment.
- Precision: use `Float64Array` for math state and Float64 in expectations, relative tolerances for accumulated sums. Compute expected values through the module's own helpers with a one-line `node -e` script in the same block as the assertion; never mental arithmetic, including counts, limits, and totals in UI or DOM probes (take them from module constants). In a tests-first run, run that script before writing the test file. Write expectations in final form on the first pass. Quantities that physics lets collide tie legitimately: assert ordering non-strictly unless the spec demands strictness. Formula-dense code: transcribe implementation and expectations from one known-good reference in a single pass; cap convention research at one search round plus one fetch, then derive, freeze, record as an assumption.
- UI, DOM, and subagents: use `setAttribute('aria-label', ...)` and `setAttribute('aria-live', ...)`, never `element.ariaLabel`. Never attach custom properties to DOM nodes; a builder returns `{ element, sync }` pairs, the caller collects them in an array, and one `syncAll` refreshes them. Check placement or ordering by reading the written file once, not by re-reasoning from memory. Modules that touch `document`, canvas, or GL need shims in the first draft of a probe; with a recorder harness, print one sample record before asserting on indices or tuples, and treat a harness failure as a harness bug, never a production bug. Delegate reference research to background subagents in the planning block; launch browser checks (dev server on an uncommon port, console error scan, kill the server, leave the repo clean) as soon as the build is green, then commit and update the card while the subagent runs. Never let two agents run npm or git commands in the same worktree. The repo ships no playwright package: live checks use `playwright-core` with the cached Chromium in `~/.cache/ms-playwright`. When the only open item is a running subagent's result, block on it in the next tool call, never in a thinking block. Headless Chromium WebGL needs `--use-angle=swiftshader`; if the page under test does not wire a renderer, import and call the renderer factory from page context.
