# developer: project guidance for future agents of this role. The doctor rewrites this file after every run and keeps only durable, task-agnostic bullets. Never edit this file as the role agent.

- Startup trio, first block, exactly three parallel invokes: `tool_search("kanban")`, the TASK.md read, and the worktree bash of the next bullet. If `tool_search` is not in the tool list, call the kanban read tool in its place; settle tool availability from the tool list itself, never in a thinking block. `read` and `bash` are built-ins, usable before the kanban toolset answers. General rule: issue tool calls in parallel whenever no call consumes another's output.
- Worktree startup, one bash call, before any source read. Worktrees live in `.worktrees/<branch>` and track `main`. One call runs: `cd <worktree> && ls -a && if test -d node_modules; then echo 'deps: present'; else echo 'deps: install started'; (npm ci > /tmp/npm-ci.log 2>&1 &); fi ; git merge --ff-only main; git log --oneline -1; git status --short; ls; ls src/*/` (the glob lists every `src/` tree; that is the one survey — do not filter it and do not repeat it). Read the install-state echo from the output, never re-derive it. `git merge --ff-only main` failing means divergence: never retry another merge — merges belong to the merger role; record one Blockers line and continue. The shape is mechanical, decided from this output plus the prior notes alone: verification-only when the tree is clean, ff-only to main is up to date, and the notes report the deliverable complete with green evidence; implement on a first run, an incomplete or silent card, or a dirty tree. State the shape as one lead-in line on the next tool call, never in a thinking block. Never re-run startup facts to re-decide the shape, and never grep source to pre-confirm a deliverable the notes already report — the pinned acceptance run is that confirmation. If the startup leaves a spec-named module missing, settle its presence on main in the same block with `git ls-tree main --name-only src/<dir>/`. Parallel tasks land on `main`; after a late merge, re-read code before editing. Never investigate branches or empty log ranges.
- Turn budgets, per shape. Verification-only (HEAD holds the deliverable): startup trio, one chained bash, one `kanban_update`, final text; zero thinking blocks — this file is the plan, and the bash, in order, is: `tail /tmp/npm-ci.log` only when the startup echo said `install started` (the file is shared across runs), the task-pinned acceptance command verbatim, then `npm run build` plus the asset check unless the deliverable is test-only. On a re-run the prior notes are the evidence of record: the pinned acceptance commands are the only re-verification; never audit, re-derive or re-probe their claims. A verification-only run commits nothing: exactly one bash sits between the startup trio and the card update, whatever doubt surfaces. Implement: startup trio, one planning block, write, one scoped verify, commit, `kanban_update`, final text; the single planning block also closes the test-scope call, and the `tail /tmp/npm-ci.log` install check rides that block's bash — never a standalone wait block. A fix task adds the one expected red→green cycle; every further red→green round names the rule that justifies it. End-of-run order is fixed: green evidence → commit → launch any live check → `get_subagent_result(wait:true)` as one bare call → `kanban_update` straight away (wrap-up reasoning goes into the card notes) → short final text → stop. A second `kanban_update` after green, a thinking block after green, or a block between the green run and the card update is a breach. A harness checkpoint that blocks on a card write is answered in one mechanical call with the notes as they stand; it never reopens the shape decision. A run over budget means a rule broke; find the rule, never add probes.
- Read and edit discipline. Batch reads: the module under change, its `.test.js`, and every module that defines data the assertions use go into one block of parallel `read` calls in the turn right after the startup trio, under a one-line lead-in that states the shape — no thinking block opens that turn; when the card's Change section names the edited symbol or constant, the orphan-reference grep for it rides the same batch. Read each file at most once per run, whole under ~400 lines, with the `read` tool, not `cat`. A steer, review note, or checkpoint never invalidates in-hand contents: the one reconciliation is a single `git diff` read, then resume the plan already made — never a re-read sweep of files this run already read or wrote. Compaction is the one exception: after a compaction, re-read (batched, one block) every file an edit will touch before drafting its edit — remembered bodies and anchors are stale, and an edit drafted from memory costs a repair round. Draft no assertion constant before its defining source line is in hand. A zero-hit grep on one file: rerun directory-wide in the same block. All changes to one file are one `edit` call in one block; never append to an already-edited file with a bash heredoc. In an `edit` call, oldText is the current file text and newText the replacement, never reversed; keep oldText to the few unique anchor lines — an oldText that carries whole function bodies plus new code is one swap away from truncating the file at the anchor. Unique means unique in the whole current file: boilerplate-heavy modules (shader sources with a shared uniform preamble, twin factory files) repeat bare declaration lines, so extend the anchor with the neighboring lines that name the target site. The block after a rejected edit is one corrected-anchor retry — no analysis, no whole-file re-read. An edit that removes or rewrites lines at a block boundary (`});`) carries that boundary into newText explicitly; a syntax error in the run after an edit is a mechanical repair — one `read` of the edited region, one fix edit, no thinking block, no hypothesis sweep. After any multi-function edit, the scoped suite (or `node -e "import('<path>')"`) runs before the next edit. A deletion, rename, or signature change settles orphan references once, in the planning block: one grep over every name the changed code referenced (a signature change is a rename of the call pattern — grep every callsite), and every consumer moves to the new name in the same edit pass. Replacing a value in an object literal replaces the old line; a second key of the same name is silent breakage. Never leave a placeholder name in an edit's newText: every symbol the new code references must exist by the end of that edit pass. Module-level statements an edit adds (listeners, error handlers, builders) sit below every declaration they reference: scan newText for identifiers declared elsewhere in the same module and confirm their declaration lines sit above the insert point before sending — an error path can run before init, a temporal-dead-zone defect never shows in the suite, and only this static check catches it. Trust a write or edit success: the scoped suite is the re-check, and a re-read of fresh output without a tool error or a failing suite behind it is a breach. When an in-place edit of a throwaway script gates the same bash run, chain a one-line grep for the edited marker into the same command. Integration tasks: a batched export map (`grep -n "^export" src/**/*.js`), batched reads, one planning block, then write.
- Planning discipline: the one planning block settles everything at once — run shape, deliverable, file placement, data contracts, and the test call (trivial → skip tests; new feature → tests first; refactor → tests before code; fix → failing test first, written with any regression test; when the spec leaves the choice open, pick in one line and move on). The planning block ends with its decisions listed one line each (placement, export names, test harness, per-file edit list); a decision absent from that list is open and is settled by the next block's one grep or probe, never by more weighing. A new message, error, or overlay surface reuses the module that already owns the app's one-off DOM: one grep for the existing element (`grep -rn 'unsupported\|aria-live' src/`) in the planning block names the owner, the export lands next to that element's builder, and main.js-versus-UI-module alternatives are never enumerated across blocks — a placement named in a planning block is closed, reopen only on new tool evidence. The red run runs untouched production code: stage no partial fix, rename no constant, and engineer no failure mode before it; a red caused by a syntax error, a dangling name, or an import from the wrong module (`NaN` or `undefined` in the failure output) is not evidence: repair it in one edit and rerun without analysis. Ambiguous spec wording: decide once, record the assumption on the card, move on. A guard or validation placement (which function rejects an out-of-domain input) is settled by one rule in the same planning block: enforce at the mutation point the bad value reaches — the setter or factory that owns the invariant — and test by importing it; testability never reopens the choice while that setter is exported. A capacity or limit question (vertex counts, buffer sizes, array bounds) settles in the planning block with one grep of the defining constant plus one probe; it never waits until after the tests are written. One topic per thinking block, closed with a decision or a tool call that gathers new evidence; a block that restates known facts, re-derives a frozen convention, or lists alternatives without picking one is waste — emit the probe command instead, with one lead-in line. One speculation block per question: a numeric, geometric, or compositing question still open after one thinking block becomes a probe command in the next block, printing the value chain; a second speculation block on the same question is a breach. Keep a thinking block short enough to finish: a truncated derivation is lost work — move the derivation into a probe script or the card notes. One channel per statement: a lead-in line on a tool call replaces a thinking block, never repeats one. A fix whose production diff is one constant or one line spends no planning thinking block: the card's Change and Tests sections are the plan, and the red-step edit carries the one-line lead-in. A thinking block never restates card text or a lead-in already given; it names only what the card does not settle. A spec existence or wiring question is settled by one grep in the same block; the output is the evidence of record. A question about state another module owns (a held flag, an input set, a mode): one grep over `src/` for the owner's API and its consumers goes out in the block the question arises, the consumer module joins the first read batch, and the topic closes there and never returns in a later thinking block. Freeze a derived convention (sign, axis, units, placement, threshold, time window) once as an input-to-expected table; never re-derive it in a later block. A decision recorded in a plan or on the card is closed; reopen only on new tool evidence — re-deriving settled geometry or compositing math is waste. Design cap: the smallest change that can pass the acceptance test, constants frozen with at most one probe sweep. After a failed command, the next block is one tool call that gathers the missing evidence, never a plan revision. One planning block per file written: fold the API map, conventions, and draft into it, then write in the next block.
- Reference math and solver operators (GLSL, ported algorithm math, published formulas, hand-derived matrices): delegate reference research to a background subagent in the planning block; while it runs, build research-independent scaffolding (targets, uniforms, test skeletons) — never hand-derive the exact formula the research is fetching. When the result lands, transcribe its formulas verbatim into the implementation, and make JS-mirror tests check transcription against the reference's own worked cases (a flat surface, a perpendicular wall, a degenerate input), not against a private derivation. Never re-derive or "verify" a fetched formula in a thinking block: a suspected contradiction between spec, reference, and derivation is a transcription or unit bug — print the value chain from the reference's worked case in one probe, fix the transcription, done. Cap: one research round, one transcription pass, one mirror test. Any operator assembled by hand (stiffness or effective-mass matrix, impulse or correction solve) is gated at write time: in the same block as the write, a one-line probe applies it to one concrete state and prints achieved-minus-requested — the operator must reproduce the requested delta exactly or its sign or assembly is wrong, fix it before any suite run; an identity check at write time is one block, the same bug hunted through a suite is ten. When a summed term inside an assembled matrix must be negated, negate all of its entries and then add the scalar to the diagonal. A library convention used for the first time (column-major multiply order, `mat3.invert` returning null on singular input) is settled by one probe at first use and frozen; it is never re-litigated in a later block, and an invert return is guarded before use. Shader sources ship with a frozen validation recipe: one node script extracts each template-literal source to /tmp files, then one chained bash runs `glslangValidator -S vert <f>.vert` and `-S frag <f>.frag` per stage plus `glslangValidator -l <vert> <frag>` per pair; every stage and every pair reports in that one run — settle the invocation once, never per run.
- Wiring and fallback trap: every newly added setup or builder function needs a callsite before commit — in the block with the scoped verify, grep each new symbol's uses; a zero-use grep on a non-entry-point symbol is a defect, not style. A fallback path silently masks a dead real path: when code installs a fallback, add a way to prove the real path ran (a one-shot console marker in the fallback, or an assertion that real resources replaced the fallback). Node suites cannot execute module-level GPU wiring; that blind spot is exactly what the delegated live check covers, so surface the marker to it.
- Test discipline. Scoped suites are the ones owning the touched files; run a new suite at once after writing the module. The first red run of a tests-first suite is the expected signal; write the module in the next block without analysis. Before the test imports production symbols, one grep of the sibling modules' exports settles each symbol's home module in the same block; a test that imports from the wrong sibling turns the red run into test-bug noise, and `NaN` or `undefined` in a failure report names the test's own imports as the cause — one read of the failing test's import lines closes it, and production-code analysis on that signature is a breach. The scoped subset gates the acceptance chain: the full suite, build, and asset check run only after the scoped subset is green, never chained onto a known-red run. Never run the same suite twice without an intervening change; each acceptance check runs once per run — green closes it, and never re-run a green check or spend a block doubting green evidence. On failure, one command prints every failing test's full output first — no `tail` or `grep` filter on that first failing run; a second run only to re-fetch failure detail is a breach. No hypothesis names test order, parallelism, gravity, or fixture reuse before that output is read. Then analyze fully, batch fix and rerun into one step; if the identical failure persists, re-read the edited region before new hypotheses. Vitest default timeout is 5 s; pass an explicit one for long simulations and keep `expect` out of per-step loops. Derive fixture layout from geometry constants before writing the test: bodies spaced under a body width start in contact, and the scene then measures collision response, not settling. A physics test body comes from the project's own factories (`createShape` + `createBody`), never a hand-written literal: containment, sleep, and step paths early-return on fields a literal omits (no `shape` → `containBody` returns early and the body falls through the floor), and the bogus failure then reads as a product bug. Before asserting what containment, sleep, or stepping does to a body, read those functions' early returns; when a failure involves a body a test helper built, one probe prints the body it returns before any physics hypothesis. A multi-body settle test asserts rest, containment and finiteness, never exact per-body orientation — an exact edge balance is a valid equilibrium. Never assert a threshold or timer state exactly at the boundary that accumulated steps reach; assert one step before and one step past the window. Clear per-frame accumulators (`world.events`, contacts) explicitly before asserting a single step's output. A physics outcome with legitimate variance across seeds or orientations gets one aggregate assertion — mean or max over the seeded cases, thresholds derived from one probe over the same seeds, never a per-case numeric bound. A contact with negative depth is a speculative skin contact, not a touch: assertions and probes count only depth > 0 as contact. An assertion that failed twice on fixture grounds is demoted to the robust form in the next edit, never a third fixture re-tune. A production constant changed to make a marginal assertion pass is a threshold decision, not a fix: choose the value from one sweep over the failure metric and record the sweep on the card; never nudge it between single test runs. Every assertion comes from source read in this run; an expectation copied from another test without checking costs a fix edit. A source-pattern assertion pins an exact string: copy it verbatim from the card's Change section into the test and transcribe the same form into the implementation — a failing source-pattern assertion is closed by diffing the two strings, never by reasoning about the shader's math. Module-scope constants are safe to reference inside test callbacks (callbacks run after module evaluation) — evaluation-order questions settle with that clause, never a thinking block.
- Stack and shell traps: Vite + Vitest, ESM (`"type": "module"`). Scripts: `npm run dev`, `npm run build`, `npm test`. Call the pinned scripts, never `npx <tool>`; the one legitimate `npx` filters a single test by name: `npx vitest run <file> -t '<name>'`. A task-pinned acceptance command overrides this — state the precedence in one lead-in line on the bash, never in a thinking block. Tests sit next to sources as `src/**/*.test.js`; Vite and Vitest share `vite.config.js`. The build parses only modules reachable from `main.js`; parse-check anything else with `node -e "import('<path>')"`. A green build is a green build: never audit bundle size or asset counts. Log installs (`npm install --loglevel=http > /tmp/npm.log 2>&1`), never a bare install against a long timeout. `~/.npmrc` sets `min-release-age=7` and `ignore-scripts=true`; check `npm view <pkg> time` before version floors. Piping to `tail`, or grepping test output, masks the real exit code: judge green from the reporter output (`N passed`) or set `set -o pipefail` first; when grepping outcomes across several runs, match both outcomes (`grep -E 'Tests +[0-9]+ (passed|failed)'`). For text extraction prefer `grep -oE`; an awk one-liner with a wrong field separator prints junk — check the separator against one input line before reading its output. `pkill` and `pgrep -f` match their own command line: a bare `pkill -f vite` can kill the running shell (exit 143, silent) — use a bracket pattern (`pkill -f '[v]ite'`) or kill the PIDs printed by `pgrep`, restrict to the port or PID you own, and fold the cleanup into the next verification bash, never a standalone command.
- Build evidence rules. A change confined to `*.test.js` files never enters the build graph: skip `npm run build` and the asset check for it, and say so in one lead-in line on the verify bash, never in a thinking block. A fresh build's hashed asset name proves nothing: never compare it against prior notes. The one asset check: after a green build line (`✓ built in`), run `grep -oE '(src|href)="[^"]+"' dist/index.html` once, inside the same chained bash when possible; copy the pattern character for character. Judge the check only from this output; close it green and never re-run it. After a failed build the on-disk `dist/` is stale: skip the grep or mark the check stale on the card.
- Sibling-task dependency (a module the spec names that a parallel branch owns): stage exactly the named files with `git show <ref>:<path> > <path>`; never stage the sibling's tests or fixtures, never merge the branch, never write a shim. main is a ref like any branch; staging from main never reopens the merge question. Use the full ref from the card or `git worktree list`; on a ref error run `git branch --list '*<fragment>*'` once in the same block and retry. Read the copy before writing tests against its API. Never run a suite or build with a known-missing import. Verify against the copy, remove it in the commit block, and record the dependency on the card. The decision is closed once made; only new tool evidence reopens it.
- Commit rule: code changed and tests green → one commit, lockfile included when deps changed. Verification-only run on a clean tree → no commit, card only. Never commit TASK.md, AGENTS.md, or `.kanban/`. Settle ignore/tracked-file questions with one `git status` plus one `.gitignore` read in the same block, never in thinking. Clean-room acceptance, only when the run changed committed code: `git archive HEAD | tar -x -C /tmp/check`, then in the copy run `npm ci`, `npm test`, `npm run build` separated by `;`, never `&&` (one failing step must not hide later results). On failure read the log tail and name the failing suite before any re-run. Then delete the copy.
- Card notes: compose from the TASK.md copy read at startup, changing only the lines the new evidence changes. Sections are fixed: Deliverable / Verification / Assumptions / Blockers / Manual checks left to other roles; placement is never debated (a merge divergence from main is a Blockers line, an out-of-scope defect note belongs under Assumptions). The verification line names the HEAD short hash, so the next run's shape decision stays mechanical. Never re-enumerate deliverables, exports, or test counts when prior notes already carry them. Blocker, assumption, and manual-check lines carry over until startup evidence shows a change; `kanban_update` replaces the whole notes field, so carried lines are resent verbatim. `kanban_update` is one call per run, sent once after green; a wording fix never justifies a second call, resend only for a factual error such as a wrong hash or a dropped carried line. After it returns, the run is closed: never re-read the card to audit its wording.
- Subagents and live checks. A background `Agent` call returns at once; `get_subagent_result(wait:true)` blocks the turn for the subagent's full duration (tens of minutes for a browser check) — block on it as one bare tool call in the next turn, never in a thinking block, never with wrap-up reasoning around it. Batch every independent call into the launch turn as parallel invokes. The launch text is self-contained: it inlines every fact the check needs — browser flags (`--use-angle=swiftshader`), the `chrome-headless-shell` fallback, dev-server port, repo paths, probe locations, and the full assertion list — because the subagent never reads this file or the worktree context. Delegate reference research in the planning block; launch browser checks only after the scoped suite, build, and commit are green (the check cannot share the worktree with git or npm), and only for acceptance criteria that name them — a pinned acceptance list without a live scenario settles the question in one lead-in line, never a deliberation block. One check runs every acceptance scenario and reports each independently, even after an earlier scenario fails — later defects can mask behind earlier ones. Fix all reported defects in one edit pass, then one re-check; never interleave fix and re-check per defect. The check contract: dev server on an uncommon port, console error scan, probe scripts under `/tmp`, server killed and repo left clean at the end, server port or PID reported back so leftovers can be reaped. Never let two agents run npm or git commands in the same worktree at once. Live checks use `playwright-core` with the cached browser in `~/.cache/ms-playwright`; it is not a package.json dependency, so locate it in one command (global npm root, or a prior run's node_modules) — never a multi-block filesystem hunt. Full Chromium can crash at launch (SIGTRAP) — fall back to `chrome-headless-shell` once, do not debug it. WebGL context-loss probes: capture the `WEBGL_lose_context` extension object before calling `loseContext`; `getExtension` returns null while the context is lost. If the page does not wire a renderer, import and call the renderer factory from page context. Live probes read the owning module or its test first; a FAIL on an invented expectation is a probe bug. An intermittent or pre-existing console error outside the deliverable (a blocked browser API before user activation, for example): one repeat run confirms it is intermittent, then it goes on the card as an out-of-scope note — never a fix debate and never a third analysis run.
- Stop rule: a green scoped run is the evidence; report the pass count and move on. After green, edit only to fix a real defect; a micro-optimization thought of after green is skipped, and cleanups noted after green (scratch reuse, allocation hoisting, dead-code sweeps) go to the card notes as suggestions, never into the tree — each costs a full re-verify. No thinking block sits between a green run and the commit; act on a settled rule in the next tool call, with its one-line lead-in. Batch hygiene (dead code, unused imports, debug leftovers) into the same edit pass as the last functional change. Never expand scope to justify the run. Once the evidence is in hand, the card update is the only remaining step; after it the run ends, with no post-send block of any kind.
- Test environment and UI. jsdom under Node exposes only some browser globals (for example no `AudioContext`, no `navigator.vibrate`): feature-gate browser APIs on the function (`typeof navigator.vibrate === 'function'`), not on global presence. Design fakes (audio, vibration, GL, canvas, input events) in the planning pass as minimal recorders: settable clock, call log, injectable functions; with a recorder harness, print one sample record before asserting on indices or tuples, and treat a harness failure as a harness bug. A fake input event carries the exact coordinates the production code reads (the press point itself, not a derived offset); a lever- or point-quantity assertion recomputes the lever from the same event data the code saw, never from the test's intent. If unsure what the environment provides, probe once (`node -e "console.log(typeof navigator, typeof AudioContext)"`) in the same block as the test draft. DOM: `setAttribute('aria-label', ...)` and `setAttribute('aria-live', ...)`, never `element.ariaLabel`; never attach custom properties to DOM nodes; a builder returns `{ element, sync }` pairs and one `syncAll` refreshes them.
- Physics and numeric probes. Replicate the production step sequence exactly, every substep in order; a partial re-implementation produces false contradictions. Validate the fixture before trusting any measurement: spawn clean or drop-and-settle, then confirm rest-state drift is ~zero over N steps — a body spawned at rest height with a random orientation intersects the floor with its corners, and solver kicks masquerade as the effect under test. Sweep a parameter only against a validated fixture; when sweep results contradict a derived expectation, suspect the fixture before the formula. A probe samples at the same point in the run as the assertion it supports; a maximum taken over the wrong window is a dead measurement — re-measure, never conclude from it. Never suppress errors (`catch { }`, ignored exit codes). A spec-suggested fix is a hypothesis: the instrumented probe that prints the value chain at the failure site goes out before the hypothesis is written. One probe per hypothesis; two dead hypotheses mean the probe measured the wrong thing — change the measurement, not the hypothesis count. A fix that leaves the same assertion failing with a smaller number is a symptom patch, not a root fix: after one shrink, stop reordering surrounding terms and print the invariant at the solve point (achieved minus requested) — an operator that fails its identity check is mis-assembled, and no ordering of the terms around it repairs it. Probes import project modules by absolute path (`const R = '<worktree>'; await import(R + '/src/...')`); a probe under `/tmp` with relative `./src` imports dies before it runs. When a computed magnitude is implausible, print the whole value chain (input → constant → derived value); suspect a scale applied twice, a per-unit vs total mix-up, or an argument in the wrong slot. For contact or normal signs, gate on signed approach velocity (`v·n < 0`), never absolute speed. Repro search for numerically degenerate bugs: in one script, sweep the spec-named axes over a decade around the failure scale, seeded with one known-yes case, with a pass predicate that catches every symptom shape; a hit → minimize it and use it as the regression test. Tuned constants come from the same sweep: the smallest value with zero failures across every symptom shape; keep them unexported with a one-line unit comment. Temporary copies: copy to `/tmp`, restore or delete in the same bash block chained with `;`; a probe that copies production modules must trace the full call path — or import the real module and copy nothing.
- Visual symptoms and live state. A reported visual symptom is a measurement claim: first check what the camera projection can show — an orthographic view collapses one axis, so screen bbox, blob area, and gap math cannot see a symptom defined along that axis; read the camera and shader setup before interpreting any screenshot. Headless sweeps that fail to reproduce a live symptom neither disprove it nor localize it: after two dead sweeps, stop sweeping and instrument the live page — add a temporary hook (`globalThis.__world = world`) in the entry module, drive the real page (dev server plus headless browser), and read engine state (positions, velocities, contacts) per frame; one state read beats a chain of pixel estimates. Pixel forensics, when unavoidable: confirm the reference frame shows the reference state before deriving numbers from it, and treat projection-derived quantities as model estimates, never ground truth. Remove the instrumentation hook in the commit block; never ship a debug global.
- Numeric traps and precision. Unary minus on a typed array yields `NaN`, not element-wise negation: negate element-wise or multiply by -1. After any sign flip or formula edit in vector math, print one concrete derived vector from a `node` probe before rerunning the suite — a NaN or a wrong-facing vector shows there, not in a test diff. When two mathematically equivalent forms disagree, print both from the same inputs in one probe; never alternate edits hoping the suite turns green. `src/math/` holds vec3/mat3/quat/mat4 helpers, out-param style (`add(out, a, b)`, column-major); reuse them, always pass a destination, never alias `out` with an input in production code, probes, or test helpers; before writing a probe or test against a helper, grep the module's exported names once — a guessed API name costs a run-and-fix round. JS-mirror tests never reuse those Float32Array-backed helpers to compute expected values: the mirror inherits float32 rounding and mismatches at ~1e-8. Build mirrors from plain numbers (component math, `Math.hypot`) and compare float32 module output with a tolerance near 1e-6 relative. A mismatch at the 8th decimal in fresh geometry code is a precision signature, not a logic bug — suspect float32 first and confirm with one probe. Use `Float64Array` for math state, relative tolerances for accumulated sums. Compute expected values through the module's own helpers with a one-line `node -e` script in the same block as the assertion; never mental arithmetic, including counts, limits, and totals in UI or DOM probes (take them from module constants). Write expectations in final form on the first pass (imported constants, tolerance choice); a later refactor to constants is a wasted run. Quantities that physics lets collide tie legitimately: assert ordering non-strictly unless the spec demands strictness.
- Benchmarks, A/B, and wall-clock thresholds. A wall-clock assertion measures the machine as much as the code: never a functional failure, never more than one A/B probe. The one probe, one bash: `rm -rf /tmp/ab && mkdir /tmp/ab && git archive HEAD | tar -x -C /tmp/ab && cp -r src /tmp/ab/ && ln -s "$PWD/node_modules" /tmp/ab/node_modules`, overlay the candidate change in the copy, run the pinned test once per variant; never extract main for a timing question — an overlay of one change is the tighter control. Then fix the confirmed cause in one edit, or record the measured cause on the card; the merger role owns any rerun. Equal work counts with a large slowdown in a float-heavy loop points at subnormal arithmetic first: print the minimum nonzero magnitudes once, fix with an unexported epsilon floor. The same extract-and-overlay recipe, run for behavior instead of time, answers "does the defect exist at the baseline commit": one extraction, one probe, one verdict; a defect absent at both commits shifts the search to measurement and rendering, never more physics sweeps.
