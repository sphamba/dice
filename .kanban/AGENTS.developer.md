# developer: project guidance for future agents of this role. The doctor rewrites this file after every run, keeping only durable, task-agnostic bullets (repo structure, build/test recipes, general shell traps, workflow tips). Never edit this file as the role agent.

- Fixed end-of-run sequence, the same for every task: (1) load the kanban tools with `tool_search("kanban")` during initial recon, never at the end; (2) verify with a scoped test run, then a build; (3) apply the commit rule below; (4) record assumptions and results in one `kanban_update`; (5) stop. The rules below answer the "should I commit, accept, or update the card" questions; do not spend thinking blocks on them.
- Stack: Vite + Vitest, ESM (`"type": "module"`). Scripts: `npm run dev`, `npm run build`, `npm test` (= `vitest run --passWithNoTests`). Tests sit next to sources as `src/**/*.test.js`; Vite and Vitest share `vite.config.js` (relative `base`, node test env). `src/math/` holds vec3/mat3 (and quat where present); reuse those helpers before writing new vector code.
- Tasks run in git worktrees under `.worktrees/<branch>`; `main` is the default branch. Fresh worktrees have no `node_modules`: start `npm ci > /tmp/npm-ci.log 2>&1 &` in the first block and read or write code while it runs; "Cannot find module vite/vitest" means a missing install, not broken code. Give empty scaffold dirs a `.gitkeep`.
- New dependencies: redirect install output to a log (`npm install --loglevel=http > /tmp/npm.log 2>&1`), never a bare install against a long timeout. `~/.npmrc` sets `min-release-age=7` and `ignore-scripts=true`; check `npm view <pkg> time` before version floors. On failure read the log and `cat ~/.npmrc`; verify with cheap metadata, not blind retries.
- Commit rule: code changed and tests green → one commit, lockfile included when deps changed. Verification-only run on a clean tree → nothing to commit; put results on the card and stop. Never commit TASK.md, AGENTS.md, or `.kanban/`. Clean-room acceptance (`git archive HEAD | tar -x -C /tmp/check`, then `npm ci && npm test && npm run build` in the copy, confirm relative asset paths in `dist/index.html`, delete the copy) is required only when the run changed committed code.
- Settle the deliverable, file placement, data contracts, and do-or-skip choices in the first planning block; record assumptions on the task card. Every thinking block must end in a decision or a tool call. When a block produces only questions, run the cheapest probe (a 10-line script or one test) that turns them into data. Do not relitigate settled choices, and do not reopen a skipped item after tests are green.
- Batch independent calls in one block: source reads, `git status`, and test runs do not depend on each other. Do not serialize them and then re-plan.
- Never re-run a failing test suite until you have changed something; batch the fix and the rerun into one step. After writing a module, run its suite at once instead of a self-review thinking pass. A green scoped run is the evidence; report the pass count and move on.
- Debug computed data (geometry, physics, generated meshes) with one standalone `/tmp` script that imports the real module, loops every case, and prints actual vs expected side by side (counts, signs, invariants). Never suppress errors in inline snippets: `try { ... } catch {}` and ignored exit codes hide the failure and waste a block. If a case list is long, one loop over all cases beats one command per case.
- Validate generated structures in layers: each layer (for example raw vertices → discovered faces → ordered polygons → mass properties) gets its own printout against known reference values (element counts, Euler characteristic, analytic volumes) before the next layer is built on it. A bug in a base layer poisons every layer above it; debugging layers together multiplies the hypotheses per failure.
- When a computed result is plausible but wrong (a count matches a sibling value, a volume is near zero, a sum is off by one), check the cheapest causes first before debugging the algorithm: a swapped entry in a dispatch or lookup table, an inverted sign or winding, and a constant copied from the wrong row. Print the mapping the code actually used.
- Read file contents with the `read` tool, not `cat`; use offset/limit for large files. Shell traps: single-character greps give noise, so grep a distinctive multi-char token with context flags; `ls`/`cat` on missing paths exits non-zero and prints to stderr — treat as noise, not failure. Validate workflow YAML with `python3 -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))" <file>` (actionlint is not installed), and verify action majors against their release tags, not memory.
- Precision: use `Float64Array` for math and physics state, Float64 in test expectations, and relative tolerances (for example a `nearRel` helper) for accumulated sums. Pick the precision once, up front, for the whole module family.
- In tests, compute expected values through the same pipeline the code runs: import the module constants and apply the module's own filter, clamp, or window to the input before asserting. A hand-derived literal that skips one step fails late; when a red test shows a plausible actual value, suspect the expected value first. Where an exact count is fragile, assert a range. Write tests only against the planned public API.
- For pure logic, go test-first: write the test, run to red, implement, run to green. An import-resolution red for a module you have not written yet is the expected first red; write the module next, do not investigate it.
- Formula-dense code (matrix math, geometry, physics): pick one known-good reference and transcribe the implementation and the expected test values from it in a single pass. When a test is red, compare the expected value against the reference first; change code only after the reference confirms the test. Cap convention research (axis signs, coordinate frames, vendor quirks) at one search round plus one fetch; if the source does not state the mapping, derive it once, freeze it as an input-to-expected table, note it as an assumption, and move on.
- Delegate to background subagents in the planning block, not after you get stuck: reference research (canonical constants, standard proportions, published formulas), browser checks (dev server on an uncommon port, desktop plus mobile viewports, console error scan; the subagent kills the server and leaves the repo clean), and independent work that can run in parallel. Keep small pure-logic implementation direct. Do not finalize constants that research will confirm before the subagent result arrives; write tests meanwhile. Never let two agents run npm or git commands in the same worktree.
- Temporary debug exports or instrumentation added to a module during debugging are removed before commit; grep the final diff for their marker names.
- A failed tool call (missing or invalid argument) is fixed by re-issuing the corrected call in the next block; do not spend a thinking block re-planning around it. For `edit`, always include `path`, and keep each `oldText` short, exact, and unique.
