# developer: project guidance for future agents of this role. The doctor rewrites this file after every run, keeping only durable, task-agnostic bullets (repo structure, build/test tips). Never edit this file as the role agent.

- Stack: Vite + Vitest, ESM (`"type": "module"`). Scripts: `npm run dev`, `npm run build`, `npm test` (= `vitest run --passWithNoTests`). Tests sit next to sources as `src/**/*.test.js`; Vite and Vitest share `vite.config.js` (relative `base`, node test env).
- Tasks run in git worktrees under `.worktrees/<branch>`; `main` is the default branch. Give empty scaffold dirs a `.gitkeep` file.
- Fresh worktrees have no `node_modules`. `npm ci` against the existing lockfile is routine: run it once with output redirected to a log, then read code while it runs. "Cannot find module vite/vitest" at startup means a missing install, not broken code; install and rerun, do not diagnose further.
- First install of new dependencies: cap the timeout at 120-300 s and redirect output to a file (`npm install --loglevel=http > /tmp/npm.log 2>&1`). Never run a bare install against a long timeout. On failure, read the log and `cat ~/.npmrc` before any retry.
- npm trap: `~/.npmrc` sets `min-release-age=7` and `ignore-scripts=true`. Versions younger than about a week are invisible to resolution and can hang `npm install` in a retry loop. Before picking version floors, check `npm view <pkg> time` and choose floors at least 7 days old.
- Verify failure hypotheses with cheap metadata (`npm view`, config files, `npm ping`) instead of retrying the failing command blind.
- Decide the deliverable in the first planning block and do not relitigate it mid-run. Verification cards follow a fixed checklist: run the suite and build, inspect the diff, read the touched modules. Add an extra test file only when a defect or convention mismatch surfaces or the card demands a durable check; make that call once, then act.
- Do not adjudicate design questions the card does not ask about (for example return-value conventions on edge cases). Record observed-but-unexplained behavior as assumptions on the task card instead.
- Batch independent calls in one block: source reads, `git status`, and test runs do not depend on each other. Do not serialize them and then re-plan, and do not spend a thinking block choosing between background and timeout for a routine command.
- Load kanban tools via tool_search ("kanban") during initial recon, not at the end, so the card update needs no search. Record assumptions, versions chosen, and verification results on the task card at the end.
- Commit the lockfile; `npm ci` needs it. Never commit TASK.md, AGENTS.md, or `.kanban/`; their tracking status is settled, so do not re-check it. Default to one commit per card when tests and implementation land together, and do not spend planning turns on commit granularity.
- Clean-room acceptance before finishing: `git archive HEAD | tar -x -C /tmp/check`, then run `npm ci && npm test && npm run build` in the copy. This validates the committed tree without touching the worktree's `node_modules`.
- After a build, confirm `dist/index.html` references relative asset paths.
- actionlint is not installed. Validate workflow YAML with `python3 -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))" <file>`. Verify GitHub Action majors against their release tags, not memory. Reuse and update the existing workflow in `.github/workflows/` when one exists.
- Implement small, self-contained logic tasks (pure modules, unit tests, verification) directly in this role. Delegate to subagents only browser checks (dev server on an uncommon port, desktop plus mobile viewports, console error scan, concrete layout or rendering assertions, subagent kills the server and leaves the repo clean) and independent work that can run in parallel.
- While a background subagent runs, do unrelated local work. Block on `get_subagent_result` only when truly blocked; do not poll. Never let two agents run npm or git commands in the same worktree at the same time.
- For pure logic, go test-first: write the test, run to red, implement, run to green. Write tests only against the planned public API of the module. Never invent helper properties or placeholder functions that no module will export.
- For formula-dense code (matrix math, projections, physics), pick one known-good reference and transcribe both the implementation and the expected test values from it in a single pass. Do not hand-derive expected values from memory. When a new test is red, compare the expected value against the reference first, and change the code only after the reference confirms the test is right.
- In test files, import only modules the task spec lists or the repo already contains. Confirm every import path resolves before running the suite.
- Shell trap: `ls` or `cat` on missing paths exits non-zero and prints to stderr; treat this as noise, not failure. Use `ls -a` to confirm dotfiles such as `.gitkeep`.
