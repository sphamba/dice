# developer: project guidance for future agents of this role. The doctor rewrites this file after every run, keeping only durable, task-agnostic bullets (repo structure, build/test recipes, general shell traps, workflow tips). Never edit this file as the role agent.

- Fixed end-of-run sequence, the same for every task: (1) load the kanban tools with `tool_search("kanban")` in the first block, before any thinking about commits, notes, or scope; (2) verify with one scoped test run, then one build; (3) apply the commit rule below; (4) record assumptions, measured values, and results in one `kanban_update`; (5) stop. These rules answer the "commit, verify, or update the card" questions, so do not spend thinking blocks on them.
- Worktree startup, one block: worktrees live in `.worktrees/<branch>` and track `main`. A fresh worktree has no `node_modules`, so start `npm ci > /tmp/npm-ci.log 2>&1 &` immediately and read the log before the first vite/vitest use ("Cannot find module" means a missing install, not broken code). Check staleness once, here: `git log HEAD..main --oneline`, then `git merge --ff-only main`. This is the run's only ancestry and staleness check; never repeat it in a later block.
- Card notes are replaceable evidence, not history to reconcile. If prior notes cite a commit hash absent from the log, never investigate amend-versus-rebase or prove lineage; a dead hash in notes costs nothing. Verify the present state only (clean tree, scoped suite green, build green), then overwrite the notes with the current HEAD, pass counts, and results. Rewriting a note is always cheaper than investigating it.
- Verification strategy is decided once, in the first planning block, from the task type and frontmatter complexity (trivial → skip tests; new feature → tests first; refactor → tests before code; fix → failing test first, written together with any integration-level regression test, before the code change). Scoped suites are the ones owning the touched files. Never reopen scope after green, and never re-choose suites in a later block. Ambiguous spec wording (heights, tolerances, injectable parameters): decide once, record the assumption on the card, move on.
- Stack: Vite + Vitest, ESM (`"type": "module"`). Scripts: `npm run dev`, `npm run build`, `npm test` (= `vitest run --passWithNoTests`). Tests sit next to sources as `src/**/*.test.js`; Vite and Vitest share `vite.config.js`. `npm run build` parses only modules reachable from `main.js`; parse-check anything else with `node -e "import('<path>')"`. A green build is a green build: never spend time on bundle size, asset counts, or module counts.
- `src/math/` holds vec3/mat3/quat/mat4 helpers, out-param style (`add(out, a, b)`, column-major); reuse them, always pass a destination. Never alias `out` with an input, in production code, probes, or test helpers. A scratch vector used as both destination and argument silently corrupts both values.
- New dependencies: redirect install output to a log (`npm install --loglevel=http > /tmp/npm.log 2>&1`), never a bare install against a long timeout. `~/.npmrc` sets `min-release-age=7` and `ignore-scripts=true`; check `npm view <pkg> time` before version floors. On failure read the log and `cat ~/.npmrc`; verify with cheap metadata, not blind retries.
- Commit rule: code changed and tests green → one commit, lockfile included when deps changed. Verification-only run on a clean tree → nothing to commit; put results on the card and stop. Never commit TASK.md, AGENTS.md, or `.kanban/`. Clean-room acceptance (`git archive HEAD | tar -x -C /tmp/check`, then `npm ci && npm test && npm run build` in the copy, confirm relative asset paths in `dist/index.html`, delete the copy) is required only when the run changed committed code.
- Settle deliverable, file placement, and data contracts in the first planning block. When a convention is derived (sign, axis, numbering, units, per-unit vs total), write it once as an input-to-expected table and freeze it; never re-derive it in a later block. Every thinking block must end in a decision or a tool call; when a block produces only questions, run the cheapest probe that turns them into data.
- Batch independent calls in one block, and keep a running map of what is known (files read, checks already run, suites already green); re-reading a file or re-running a check is waste. Read files with the `read` tool, not `cat`; use offset/limit for large files. For `edit`, keep each `oldText` short, exact, and unique; merge nearby changes into one edit, because overlapping edits are rejected.
- Test discipline: after writing a module, run its suite at once. Never run the same suite twice without an intervening code or test change. When a run fails, analyze it fully first, then batch the fix and the rerun into one step. If the identical failure persists after a fix, re-read the edited region before new hypotheses.
- Stop rule: a green scoped run is the evidence; report the pass count and move on. After green, edit again only to fix a real defect. Batch hygiene (dead code, unused imports, debug leftovers) into the same edit pass as the last functional change, before the final green run. A post-green cleanup pass forces another full test-plus-build cycle.
- Temporary code changes (regression proof, debug logging in sources): copy the file to `/tmp` first, and restore it in the same bash block chained with `;` so the restore always runs (`cp src/f.js /tmp/f.bak; ...; cp /tmp/f.bak src/f.js`). Regression proof: revert the fix, run only the one test file, restore the fix. Expected result: red pre-fix, green post-fix. Prefer a probe that wraps or mocks over editing source.
- Physics probes: a `/tmp` probe must replicate the production step sequence exactly. Copy the loop from the source, every substep in the same order; a partial re-implementation produces false contradictions and wasted reruns. Probes import repo modules by absolute path or `file://` URL, and never suppress errors (`try { } catch { }` and ignored exit codes hide failures). Validate the fixture before trusting its measurements: spawn positions clear of geometry by body radius or extent margins, a physically valid initial state, one sanity-checked step. Never tune production constants from a broken fixture.
- When a computed magnitude is implausible (too small, too large, wrong units), print the whole value chain in one probe: input → geometry or shape constant → density or mass scale → derived tensor. Do not re-derive units mentally across blocks. Check first for a scale applied twice or not at all, a per-unit vs total convention mix-up, a swapped table entry, an argument in the wrong slot. For contact or normal signs, gate on signed approach velocity (`v·n < 0`), never absolute speed.
- Long simulations in vitest: the default timeout is 5 s. Pass an explicit one (`it(name, fn, 30000)`) whenever a test runs seconds of simulation. Never put `expect` inside per-step loops; accumulate a worst case in a variable and assert once after the loop. Vitest instrumentation adds roughly 1.5-2x wall time over a standalone `node` run: measure standalone once, then set performance thresholds with at least 2x headroom.
- Precision and expectations: use `Float64Array` for math and physics state, Float64 in test expectations, and relative tolerances for accumulated sums; pick the precision once for the whole module family. Tests compute expected values through the module's own helpers and constants, derived with a throwaway script, never mental arithmetic. When a red test shows a plausible actual value, suspect the expected value first. Where an exact count is fragile, assert a range.
- Construct spatial test fixtures analytically from geometry (known normals, angles, symmetry), never by brute-force parameter sweeps. If a sweep is truly needed, seed it with one known-yes case, cap runtime at seconds, and treat a zero-hit result as a search problem before suspecting the production code. Validate layered derivations (raw vertices → discovered faces → mass properties) one layer at a time against known reference values; a bug in a base layer poisons every layer above it. Formula-dense code (matrix math, geometry, shaders, contact solvers): pick one known-good reference and transcribe the implementation and the expected test values from it in a single pass.
- Convention research (axis signs, coordinate frames, vendor quirks): cap at one search round plus one fetch; if the source does not state the mapping, derive it once, freeze it, note it as an assumption, and move on. Modules that touch browser APIs cannot run under plain Node: define `document`/`OffscreenCanvas`/2d-context shims in the first draft of any such probe. Test the pure layer with vitest; leave pixel and DOM output to a browser-check subagent. With a mock or recorder harness (Proxy-based GL context, call log), print one sample record before asserting on indices or tuple positions; a harness failure means the harness is wrong, so fix the harness and never change production code based on it.
- Delegate to background subagents in the planning block, not after you get stuck: reference research, browser checks (dev server on an uncommon port, console error scan; the subagent kills the server and leaves the repo clean), and independent parallel work. Write tests while research runs; never finalize constants that research will confirm. Never let two agents run npm or git commands in the same worktree.
