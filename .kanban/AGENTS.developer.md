# developer: project guidance for future agents of this role. The doctor rewrites this file after every run, keeping only durable, task-agnostic bullets (repo structure, build/test recipes, general shell traps, workflow tips). Never edit this file as the role agent.

- End-of-run sequence, the same for every task: (1) load the kanban tools with `tool_search("kanban")` in the first block; (2) verify with a scoped test run, then a build; (3) apply the commit rule below; (4) record results, assumptions, and blockers in one `kanban_update`; (5) stop. Wrap up in tool blocks only: after the last green run the next block is the card update and the run ends — no wrap-up thinking blocks, no closing text block after the card update, and card-note wording is never a deliberation topic; write the notes directly in the `kanban_update` call. If HEAD already contains the deliverable commit, the run is verification-only: steps 1, 2, 4, 5 only, and the run ends at the build. A verification-only run re-reads no delivered module, re-checks no status or HEAD after the build (the startup block fixed both), runs no extra probe, and extends the prior run's card notes with one fresh verification line (suite, pass count, build result, HEAD).
- Worktree startup, one block: worktrees live in `.worktrees/<branch>` and track `main`. Make `npm ci > /tmp/npm-ci.log 2>&1 &` the first command, then `git log HEAD..main --oneline`, `git merge --ff-only main`, and one layout look (`ls` of repo root and each `src/` subdirectory the task touches) in the same block, before any source read. In the same block, compare the task's named output files against that listing: a named file that does not exist yet is a sibling dependency (next bullet), flagged here, not rediscovered after the reads. Parallel tasks land on `main`; a late merge means you inspect old code and read again after the merge. A fresh worktree has no `node_modules`: read the install log before the first vite/vitest use ("Cannot find module" means a missing install, not broken code). Never investigate branches or empty log ranges.
- Sibling-task dependencies (a module the spec or contract names that an in-progress sibling branch owns): the recipe in this bullet is the entire decision — spend no thinking block weighing wait, merge, or copy, and never query the board or sibling cards for state; branch state (`git show <branch>:<path>`, `ls .worktrees/<branch>/<path>`) is the only input. Stage the copy in one command (`git show <branch>:<path> > <path>`), no `/tmp` detour; never merge the sibling branch into yours, never write your own replacement, never add a dynamic-import or fallback shim. Read the copy before writing tests against its API. Never run a suite or build whose known-missing import you have not staged yet: a red run against a known-missing import is a wasted block, not new evidence, and does not reopen the strategy. Verify tests and build against the copy, remove it in the commit block (on a verification-only run, in the same bash block after the green run), and record the dependency on the card. Once made, the decision is closed; only new tool evidence reopens it.
- Verification strategy is decided once, in the first planning block, from the task type and frontmatter complexity (trivial → skip tests; new feature → tests first; refactor → tests before code; fix → failing test first, written together with any regression test, before the code change). Scoped suites are the ones owning the touched files. Decide in the same block whether any extra probe beyond the scoped suite is needed; after that, never reopen scope, re-choose suites, or add "one more probe". A later "should I also probe X?" itch is settled by one grep for existing coverage of that behavior (tests sit next to sources) in the same block; covered → the probe is unnecessary, done. Ambiguous spec wording: decide once, record the assumption on the card, move on.
- Stack: Vite + Vitest, ESM (`"type": "module"`). Scripts: `npm run dev`, `npm run build`, `npm test` (= `vitest run --passWithNoTests`). Tests sit next to sources as `src/**/*.test.js`; Vite and Vitest share `vite.config.js`. `npm run build` parses only modules reachable from `main.js`; parse-check anything else with `node -e "import('<path>')"` and never re-derive this rule. A green build is a green build: never spend time on bundle size or asset counts.
- `src/math/` holds vec3/mat3/quat/mat4 helpers, out-param style (`add(out, a, b)`, column-major); reuse them, always pass a destination. Never alias `out` with an input, in production code, probes, or test helpers. Before writing a probe or test that calls a helper, grep the module's exported names once; a guessed API name costs a full run-and-fix round.
- New dependencies: redirect install output to a log (`npm install --loglevel=http > /tmp/npm.log 2>&1`), never a bare install against a long timeout. `~/.npmrc` sets `min-release-age=7` and `ignore-scripts=true`; check `npm view <pkg> time` before version floors. On failure read the log and `cat ~/.npmrc`; verify with cheap metadata, not blind retries.
- Commit rule: code changed and tests green → one commit, lockfile included when deps changed. Verification-only run on a clean tree → nothing to commit; put results on the card and stop. Run `git status --porcelain` in the same bash block as the build; a clean status there closes the commit question for the whole run, so never reopen it in a later thinking or tool block. Never commit TASK.md, AGENTS.md, or `.kanban/`. Settle ignore/tracked-file questions with one `git status` plus one read of `.gitignore` in the same block, never in thinking. Clean-room acceptance, only when the run changed committed code: `git archive HEAD | tar -x -C /tmp/check`, then in the copy run `npm ci`, `npm test`, and `npm run build` as three separate commands (or one chain with `;`), never one `&&` chain: a single failing test must not abort the build and hide its result. When a step fails, read the log tail and name the failing suite before any re-run. Confirm relative asset paths in `dist/index.html`, then delete the copy.
- Planning discipline: settle deliverable, file placement, and data contracts in the first planning block. When a convention is derived (sign, axis, numbering, units, placement, fallback), write it once as an input-to-expected table and freeze it; never re-derive it later. A decision recorded in a plan or on the card is closed: reopen it only after new tool evidence, never in a thinking block; one flip-flop on a settled choice costs a whole block per swing. Every thinking block must end in a decision or a tool call. One planning block per file you write: fold the API map, the conventions, and the full draft plan into that one block, then write in the next block; never two planning blocks for the same file. When a mid-run "does X hold in my code?" question appears, settle it with one `read` or `grep` in the same block, not with a deliberation block; a question you defer costs a re-derivation later.
- Read discipline: read each file at most once, keep a running map of what has been read, and batch all module reads for one task into one or two blocks, issuing the batch's `read` calls as parallel calls in one block, not one call per block. Modules under ~400 lines: read whole, do not take ranged reads that force a follow-up. Read files with the `read` tool, not `cat`; use offset/limit only for large files. A zero-hit grep on one file is not a dead end: rerun the same grep directory-wide (`grep -rn "<symbol>" src/`) in the same block; symbols often live in a sibling module. For `edit`, keep each `oldText` short, exact, and unique; merge nearby changes into one edit, because overlapping edits are rejected.
- Integration or entry-point tasks (wiring many existing modules into one file): first a batched export map (`grep -n "^export" src/**/*.js`, per directory), then the batched reads of the consumed modules, then one planning block, then write. Do not spread single-file reads over many blocks; 12 modules do not need 15 calls.
- Test discipline: after writing a module, run its suite at once. The first red run of a new suite (module not yet written) is the expected tests-first signal; write the module in the next block without analysis. Never run the same suite twice without an intervening change. When a run fails, analyze it fully first, then batch the fix and the rerun into one step; if the identical failure persists, re-read the edited region before new hypotheses. Long simulations in vitest: default timeout is 5 s, pass an explicit one; never put `expect` inside per-step loops, assert once on the worst case. Vitest adds roughly 1.5-2x wall time over a standalone `node` run: measure standalone once, set thresholds with 2x headroom. A red wall-clock or perf assertion in a suite the task did not touch is environmental noise, in the worktree and in clean-room copies alike: read the log tail once to name it, record it on the card, move on, and never re-run the same timing test in extra directories to confirm it.
- Stop rule: a green scoped run is the evidence; report the pass count and move on. After green, edit again only to fix a real defect. A micro-optimization thought of after green (early exits, allocation trims) goes into the last functional edit before the final green run or is skipped; a post-green edit buys a full re-verify cycle. Batch hygiene (dead code, unused imports, debug leftovers, grep the diff for their markers) into the same edit pass as the last functional change, before the final green run. Post-green re-reads of code the run did not change count as verification only when they check a spec point; reading implementation internals for reassurance is not verification, skip it.
- Test-environment globals are partial: Node 21+ and jsdom expose `navigator` without `vibrate` and no `AudioContext`. A module that calls a browser API must feature-gate on the function (`typeof navigator.vibrate === 'function'`), not on global presence, or tests and real browsers disagree. Design fakes (AudioContext, vibration, GL) in the planning pass as minimal recorders: settable clock, call log, injectable functions. Derive test values (thresholds, gains, caps, counts) from the module contract, so the suite is green on the first implementation. If unsure what the environment provides, probe once (`node -e "console.log(typeof navigator, navigator?.vibrate)"`) in the same block as the test draft; a wrong global-presence assumption costs a fix-and-rerun round.
- Temporary copies and probes: copy a file to `/tmp` before temporary changes (regression proof, debug logging), restore in the same bash block chained with `;`, delete `/tmp` copies when done. Regression proof: red before the fix, green after. Probes that copy production modules must trace the full call path, caller included; a partial copy makes probe and production disagree in ways that cost many blocks. Regenerate instrumented copies from HEAD at the start of every measurement run, or import the real module and copy nothing; a stale `/tmp` copy reports phantom failures against already-fixed code.
- Physics and numeric probes: replicate the production step sequence exactly, every substep in the same order; a partial re-implementation produces false contradictions. Never suppress errors (`catch { }` and ignored exit codes hide failures). Validate the fixture before trusting measurements: clear spawn margins, a valid initial state, one sanity-checked step; never tune production constants from a broken fixture. A spec-suggested fix is a hypothesis: before implementing it, print the actual intermediate values at the failure site in one probe and check the mechanism against the data; implement the root cause and record the deviation as an assumption on the card. When a computed magnitude is implausible, print the whole value chain (input → shape constant → derived value) in one probe; suspect a scale applied twice, a per-unit vs total mix-up, or an argument in the wrong slot. For contact or normal signs, gate on signed approach velocity (`v·n < 0`), never absolute speed. Validate layered derivations one layer at a time against known reference values.
- Repro search for numerically degenerate bugs: do not hand-tune poses. In one script, sweep the axes the spec names or implies over a decade around the failure scale, seeded with one known-yes case, with a pass predicate that catches every symptom shape. A zero-hit sweep means widen axes or shrink steps. When a sweep hits, minimize it and use it as the regression test. Pick tuned constants (epsilons, welds, tolerances) from the same sweep: choose the smallest value with zero failures across every symptom shape and fixture; keep the constant unexported with a one-line unit comment.
- Precision and expectations: use `Float64Array` for math state, Float64 in test expectations, relative tolerances for accumulated sums. Compute expected values through the module's own helpers and constants, with a one-line `node -e` script in the same block as the assertion; never mental arithmetic — this includes counts, limits, and totals in UI or DOM probes, which must come from module constants (type lists, caps), not from counting in your head. In a tests-first run, run that `node -e` script before writing the test file: a count or cap derived from memory in the planning block becomes a wrong literal that costs an edit-and-rerun round. Write expectations in final form on the first pass (imported constants, tolerance choice); a literal you refactor to a constant later is a wasted run. Quantities that physics lets collide tie legitimately: assert ordering non-strictly and allow equal values unless the spec explicitly demands strictness. Formula-dense code: transcribe implementation and expected values from one known-good reference in a single pass; cap convention research at one search round plus one fetch, then derive once, freeze, record as an assumption.
- UI and DOM modules: use `setAttribute('aria-label', ...)` and `setAttribute('aria-live', ...)`; never set `element.ariaLabel` or deliberate about it. Never attach custom properties to DOM nodes; a builder returns `{ element, sync }` pairs or plain data, the caller collects them in an array, and one `syncAll` refreshes them. Check placement or ordering questions by reading the written file once, not by re-reasoning from memory. Modules that touch `document`, canvas, or GL need shims defined in the first draft of any probe; with a mock or recorder harness (Proxy-based GL context, call log), print one sample record before asserting on indices or tuple positions, and treat a harness failure as a harness bug: fix the harness, never the production code. Live browser probes obey the expectation rule: read the owning module or its test file before writing the probe and take every expectation from it; a FAIL on an expectation you invented is a probe bug, so re-check the expectation first and the code second.
- Delegate reference research to background subagents in the planning block. Launch browser checks (dev server on an uncommon port, console error scan, kill the server, leave the repo clean) as soon as the build is green, then commit and update the card while the subagent runs. Never let two agents run npm or git commands in the same worktree. The repo ships no playwright package: live checks use `playwright-core` with the cached Chromium browser in `~/.cache/ms-playwright`. When the only open item is a running subagent's result, block on the result in your next tool call; never spend a thinking block choosing between polling and waiting. While a subagent runs, spend no thinking block on re-derivations; do owed reads (selectors, constants, specs) or end the block with the blocking wait. Headless Chromium WebGL needs the flag `--use-angle=swiftshader`; if the page under test does not wire a renderer, import and call the renderer factory directly from page context.
