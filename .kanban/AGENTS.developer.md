# developer: project guidance for future agents of this role. The doctor rewrites this file after every run and keeps only durable, task-agnostic bullets. Never edit this file as the role agent.

- Startup trio, first block, no exceptions: one block holds three parallel invokes — `tool_search("kanban")`, the TASK.md read, and the worktree startup bash of the next bullet. The three calls are independent: `read` and `bash` are built-in tools that need no kanban toolset, and the bash needs no file content. Never split them into separate turns; sequencing costs two extra turns on every run and is the most common budget breach. General rule: issue tool calls in parallel whenever no call consumes another's output.
- Run shapes and budgets. Verification-only (HEAD holds the deliverable): three tool turns and five tool calls — startup trio, one chained bash, one `kanban_update` — plus the final text, and zero thinking blocks. Implement: startup trio, one planning block, write, one scoped verify, commit, `kanban_update`, final text. End-of-run order is fixed: scoped verification, then `kanban_update`, then a short final text with durable guidance, then stop. Never put a thinking block between the green run and the card update; put wrap-up reasoning into the card notes. A second `kanban_update` in one run, or any thinking block in the verification-only shape, is a breach. The two seen patterns are restating the pinned bash recipe before running it, and narrating a notes copy-edit before sending it: both are already ruled here, so skip them. A run over budget means a rule broke; find the rule, never add probes.
- Worktree startup, one bash call, before any source read. Worktrees live in `.worktrees/<branch>` and track `main`. One call runs the chain: `cd <worktree> && ls -a && if test -d node_modules; then echo 'deps: present'; else echo 'deps: install started'; (npm ci > /tmp/npm-ci.log 2>&1 &); fi ; git merge --ff-only main; git log --oneline -1; git status --short; ls; ls src/<dirs>/` — list only the `src/` subdirectories the task names, never `src/*/` as a whole; the listing rides in every later turn's context. The echo line is the install-state record: read it from the output, never re-derive it or doubt it in a thinking block. `git merge --ff-only main` failing (`Not possible to fast-forward`) means the branches diverged: never retry with `--no-ff`, a rebase, or any other merge — merges belong to the merger role; record one Blockers line (`diverged from main`) and continue the planned run shape unchanged. When that leaves a spec-named module missing on this branch, settle its presence on main in the same block with `git ls-tree main --name-only src/<dir>/`. This is the run's only state survey. It decides the run shape: HEAD holds the deliverable commit named in prior notes → verification-only shape; it does not → implement. It is also the file-presence record for sibling-dependency questions. A fresh worktree has no `node_modules`: chain `tail /tmp/npm-ci.log` into the same bash as the first vitest or build call, never as a standalone block. `git status` runs here, and again only after this run edited files. Never investigate branches or empty log ranges. Parallel tasks land on `main`; after a late merge, re-read code before editing. Later layout or notes questions fold into the block where they arise; never run a second survey.
- Verification-only run: the shape is mechanical turn by turn, and this file is the plan, so zero thinking blocks in the whole shape — no block plans the bash, no block predicts the output of a check about to run, and no block chooses note wording; the Verification line is produced inline from the prior notes. Startup shows `HEAD <hash>` on the deliverable commit → next block is the single chained bash → next block is `kanban_update` → final text. The bash, in order: tail `/tmp/npm-ci.log` only when the startup echo said `install started` (that file is shared across runs, so an unconditional tail reads a stale log), then the task-pinned acceptance command verbatim, then `npm run build`, then the asset check of the build-evidence bullet. A task-pinned command overrides the general no-`npx` rule; rule conflicts resolve from this file in one line, never in a thinking block. That bash is the run's terminal evidence: nothing else belongs in it — no export re-list (the card notes name the exports), no test re-count, no git re-survey on an unedited tree. Each acceptance check runs once per run: a green result closes the check; never re-run a green check, never spend a thinking block doubting green evidence. A spec existence or wiring question is settled by one grep whose output is the evidence of record; run the grep even when reasoning already concluded the answer. A second bash runs only when a check is red or its output raises a genuinely new question. Never expand scope to justify the run: the single bash above is the whole scope, and checks closed green by prior runs stay closed. Blocker and assumption lines carry over until startup evidence shows a change.
- Build evidence rules. A fresh build's hashed asset name proves nothing: the same tree gives the same hash, a changed tree a new hash. Never compare an asset hash against prior notes, and never treat a hash change as a defect or a hash match as confirmation. The one asset check: after a green build line (`✓ built in`), run `grep -oE '(src|href)="[^"]+"' dist/index.html` once, inside the same chained bash as the build when possible. Copy that pattern character for character; a paraphrase such as `grep -o 'assets/[^"]*'` drops the `src=`/`href=` anchors and the leading `./`, makes relative paths look bare, and forces a second bash to redo a green check. Judge the check only from this grep's output, close it when green, and never re-run it or reason about it again. After a failed build the on-disk `dist/` is stale: skip the grep or mark the check stale on the card instead of reporting a false green.
- Sibling-task dependency (a module the spec names that a parallel branch owns): stage exactly the named module files with `git show <branch>:<path> > <path>`; never stage the sibling's tests or fixtures, never merge the branch, never write a shim or replacement. main is a ref like any branch: a module already landed on main is staged the same way (`git show main:<path> > <path>`), and staging from main is never a reason to reconsider merging. A staged copy from a newer sibling commit than the one behind an earlier green run is an intervening change: rerun the scoped suite once against it and close it green without deliberation. Use the full branch ref `feat/<shortName>` from the card or `git worktree list`; on a ref error run `git branch --list '*<fragment>*'` once in the same block and retry. Read the copy before writing tests against its API. Never run a suite or build with a known-missing import: a red run against it buys nothing. Verify against the copy, remove it in the commit block (or the spec-check block on a verification-only run), and record the dependency on the card. The decision is closed once made; only new tool evidence reopens it.
- Test discipline. Verification strategy is decided once, in the first planning block, from task type and complexity: trivial → skip tests; new feature → tests first; refactor → tests before code; fix → failing test first, written together with any regression test. Scoped suites are the ones owning the touched files. After that, never reopen scope, re-choose suites, or add one more probe; settle a coverage question with one grep for existing tests next to the sources, in the same block. Ambiguous spec wording: decide once, record the assumption on the card, move on. Run a new suite at once after writing the module. The first red run of a tests-first suite is the expected signal; write the module in the next block without analysis. Never run the same suite twice without an intervening change. On failure, analyze fully, then batch fix and rerun into one step; if the identical failure persists, re-read the edited region before new hypotheses. A green suite needs no re-confirmation: the next block goes straight to `git status`, diff stat, and the commit. Vitest default timeout is 5 s; pass an explicit one for long simulations and keep `expect` out of per-step loops. A red wall-clock or perf assertion in a suite the task did not touch is environmental noise: read the log tail once, record it on the card, move on, never re-run it to confirm.
- Stack: Vite + Vitest, ESM (`"type": "module"`). Scripts: `npm run dev`, `npm run build`, `npm test` (= `vitest run --passWithNoTests`). Call these pinned scripts, never `npx <tool>`, which re-resolves the binary and prints notice noise ahead of the output. Tests sit next to sources as `src/**/*.test.js`; Vite and Vitest share `vite.config.js`. The build parses only modules reachable from `main.js`; parse-check anything else with `node -e "import('<path>')"`. A green build is a green build: never spend time on bundle size or asset counts. Log installs (`npm install --loglevel=http > /tmp/npm.log 2>&1`), never a bare install against a long timeout. `~/.npmrc` sets `min-release-age=7` and `ignore-scripts=true`; check `npm view <pkg> time` before version floors. Piping a command to `tail` masks its real exit code (`$?` is `tail`'s): judge green from the reporter output (`N passed`) or set `set -o pipefail` first.
- `src/math/` holds vec3/mat3/quat/mat4 helpers, out-param style (`add(out, a, b)`, column-major). Reuse them and always pass a destination; never alias `out` with an input, in production code, probes, or test helpers. Before writing a probe or test that calls a helper, grep the module's exported names once; a guessed API name costs a run-and-fix round.
- Commit rule: code changed and tests green → one commit, lockfile included when deps changed. Verification-only run on a clean tree → no commit, card only. Never commit TASK.md, AGENTS.md, or `.kanban/`. Settle ignore/tracked-file questions with one `git status` plus one `.gitignore` read in the same block, never in thinking. Clean-room acceptance, only when the run changed committed code: `git archive HEAD | tar -x -C /tmp/check`, then in the copy run `npm ci`, `npm test`, `npm run build` separated by `;`, never `&&` (one failing step must not hide later results). On failure read the log tail and name the failing suite before any re-run. Then delete the copy.
- Planning discipline: settle deliverable, file placement, and data contracts in the first planning block. One topic per thinking block, closed with a decision or a tool call. Rule precedence is settled by this file in one line, never deliberated (task-pinned commands beat tool-runner preferences). Freeze a derived convention (sign, axis, units, placement) once as an input-to-expected table; never re-derive it. A decision recorded in a plan or on the card is closed; reopen only after new tool evidence. Design deliberation cap: settle the mechanism in one pass — the smallest change that can pass the acceptance test — and freeze its constants with at most one quick probe (one `node -e` sweep over candidate values). The scoped test, not taste or a perceptual argument, is the arbiter of sufficiency: never burn a block comparing discarded designs, re-deriving thresholds, or predicting whether constants will feel right — implement, run the suite, and let red/green decide. A thinking block that restates what the run already knows (the startup output, prior notes, this file's recipes) is waste: end it with the one command that answers the open question, or skip it. After a failed command, the next block is one tool call that gathers the missing evidence, never a plan revision: this file already rules the standard failures (diverged main, missing sibling module, red suite). The run-shape statement can be one line leading the next tool call. One planning block per file written: fold the API map, conventions, and draft plan into it, then write in the next block.
- Read discipline: read each file at most once; batch module reads into one or two blocks of parallel `read` calls. Read files whole under ~400 lines, with the `read` tool, not `cat`. A zero-hit grep on one file: rerun directory-wide (`grep -rn "<symbol>" src/`) in the same block. For `edit`, keep each `oldText` short, exact, and unique; merge nearby changes into one edit, because overlapping edits are rejected. Trust an edit tool success: never spend a block suspecting phantom corruption (literal `\r` escapes, mojibake) without positive evidence such as a tool error or a syntax-failing suite; if a check is genuinely warranted, chain `cat -A` of the edited region into the next bash instead of a dedicated block. Integration tasks (wiring many modules into one file): a batched export map (`grep -n "^export" src/**/*.js`), then batched reads, then one planning block, then write.
- Card notes: compose from the TASK.md copy read at startup, changing only the lines the new evidence changes. Sections are fixed: Deliverable / Verification / Assumptions / Blockers / Manual checks left to other roles; add no other sections, and placement is never debated (a merge divergence from main is a Blockers line). Notes record check states (exit codes, pass counts, asset hashes, wiring lines), never per-run timings such as build milliseconds or durations: a timing is not a finding, and refreshing it only churns the notes for the next run. Never re-enumerate deliverables, exports, or test counts from the repo when prior notes already carry them. On a re-verification run with no new findings, the payload is the prior notes unchanged, or with only the lines whose state changed refreshed: type it directly into the `kanban_update` call, because regenerating unchanged text is the slowest span of a small run and wording choice is never a block or a pause. `kanban_update` replaces the whole notes field, so carried lines are resent verbatim, never summarized away: dropping a carried blocker, assumption, or manual-check line loses information the board needs. `kanban_update` is one call per run, sent once and never re-sent: a wording or typo fix is not a defect and never justifies a second call that regenerates the whole notes field; resend only for a factual error such as a wrong hash or a dropped carried line. The update never re-argues decisions.
- Stop rule: a green scoped run is the evidence; report the pass count and move on. After green, edit only to fix a real defect; a micro-optimization thought of after green goes into the last functional edit before the final green run or is skipped. Batch hygiene (dead code, unused imports, debug leftovers, diff grep for their markers) into the same edit pass as the last functional change. Post-green re-reads count as verification only when they check a spec point. Once the evidence is in hand, the card update is the only remaining step.
- Test-environment globals are partial: jsdom under Node exposes only some browser globals (for example no `AudioContext`, no `navigator.vibrate`). Feature-gate browser APIs on the function (`typeof navigator.vibrate === 'function'`), not on global presence, or tests and real browsers disagree. Design fakes (audio, vibration, GL) in the planning pass as minimal recorders: settable clock, call log, injectable functions. Derive test values (thresholds, caps, counts) from the module contract so the suite is green on the first run. If unsure what the environment provides, probe once (`node -e "console.log(typeof navigator, typeof AudioContext)"`) in the same block as the test draft.
- Physics and numeric probes: replicate the production step sequence exactly, every substep in order; a partial re-implementation produces false contradictions. Never suppress errors (`catch { }`, ignored exit codes). Validate the fixture before trusting measurements (spawn margins, valid initial state, one sanity-checked step); never tune production constants from a broken fixture. A spec-suggested fix is a hypothesis: print the actual intermediate values at the failure site first, then implement the root cause and record any deviation as an assumption on the card. When a computed magnitude is implausible, print the whole value chain (input → constant → derived value); suspect a scale applied twice, a per-unit vs total mix-up, or an argument in the wrong slot. For contact or normal signs, gate on signed approach velocity (`v·n < 0`), never absolute speed. Validate layered derivations one layer at a time against reference values. Temporary copies and probes: copy a file to `/tmp` before temporary changes and restore or delete it in the same bash block chained with `;`. Regression proof: red before the fix, green after. A probe that copies production modules must trace the full call path, caller included; a partial copy makes probe and production disagree. Regenerate instrumented copies from HEAD at the start of every measurement run, or import the real module and copy nothing; a stale copy reports phantom failures.
- Repro search for numerically degenerate bugs: do not hand-tune poses. In one script, sweep the axes the spec names or implies over a decade around the failure scale, seeded with one known-yes case, with a pass predicate that catches every symptom shape. A zero-hit sweep: widen axes or shrink steps. When a sweep hits, minimize it and use it as the regression test. Pick tuned constants (epsilons, welds, tolerances) from the same sweep: the smallest value with zero failures across every symptom shape and fixture; keep the constant unexported with a one-line unit comment.
- Precision: use `Float64Array` for math state and Float64 in expectations, relative tolerances for accumulated sums. Compute expected values through the module's own helpers with a one-line `node -e` script in the same block as the assertion; never mental arithmetic, including counts, limits, and totals in UI or DOM probes (take them from module constants). Write expectations in final form on the first pass (imported constants, tolerance choice); a later refactor to constants is a wasted run. Quantities that physics lets collide tie legitimately: assert ordering non-strictly unless the spec demands strictness. Formula-dense code: transcribe implementation and expectations from one known-good reference in a single pass; cap convention research at one search round plus one fetch, then derive, freeze, record as an assumption.
- UI, DOM, subagents, and live checks: use `setAttribute('aria-label', ...)` and `setAttribute('aria-live', ...)`, never `element.ariaLabel`; never attach custom properties to DOM nodes; a builder returns `{ element, sync }` pairs and one `syncAll` refreshes them. Modules that touch `document`, canvas, or GL need shims in the first draft of a probe; with a recorder harness, print one sample record before asserting on indices or tuples, and treat a harness failure as a harness bug. Live browser probes read the owning module or its test first; a FAIL on an invented expectation is a probe bug. Delegate reference research to background subagents in the planning block; launch browser checks (dev server on an uncommon port, console error scan, kill the server, leave the repo clean) as soon as the build is green, then commit and update the card while the subagent runs; never let two agents run npm or git commands in the same worktree. Live checks use `playwright-core` with the cached Chromium in `~/.cache/ms-playwright`; headless WebGL needs `--use-angle=swiftshader`; if the page does not wire a renderer, import and call the renderer factory from page context. When the only open item is a running subagent's result, block on it in the next tool call, never in a thinking block.
