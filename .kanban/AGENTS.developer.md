# developer: project guidance for future agents of this role. The doctor rewrites this file after every run and keeps only durable, task-agnostic bullets. Never edit this file as the role agent.

- Startup trio, first block, exactly three parallel invokes: `tool_search("kanban")`, the TASK.md read, and the worktree bash of the next bullet. `tool_search` is not a gate: `read` and `bash` are built-ins, usable before the kanban toolset answers. Sending the three calls in separate turns costs two turns on every run. General rule: issue tool calls in parallel whenever no call consumes another's output.
- Worktree startup, one bash call, before any source read. Worktrees live in `.worktrees/<branch>` and track `main`. One call runs: `cd <worktree> && ls -a && if test -d node_modules; then echo 'deps: present'; else echo 'deps: install started'; (npm ci > /tmp/npm-ci.log 2>&1 &); fi ; git merge --ff-only main; git log --oneline -1; git status --short; ls; ls src/*/` (the glob lists every `src/` tree; that is the one survey — do not filter it and do not repeat it after reading TASK.md). The echo line is the install-state record: read it from the output, never re-derive it. `git merge --ff-only main` failing means the branches diverged: never retry with another merge — merges belong to the merger role; record one Blockers line and continue the planned shape. The shape is mechanical, decided from this startup output and the prior notes alone: verification-only when the tree is clean, ff-only to main is up to date, and the prior notes report the deliverable complete (a verification line naming HEAD's short hash, or an approved/complete outcome line with green evidence); implement on a first run, an incomplete or silent card, or a dirty tree. State the shape as one lead-in line on the next tool call, never in a thinking block. Never re-run or extend the startup facts (log hash, merge state, tree state) to re-decide the shape, and never grep source to pre-confirm a deliverable the notes already report — the pinned acceptance run is that confirmation. If the startup leaves a spec-named module missing, settle its presence on main in the same block with `git ls-tree main --name-only src/<dir>/`. Parallel tasks land on `main`; after a late merge, re-read code before editing. Never run a second survey, never investigate branches or empty log ranges.
- Turn budgets, per shape. Verification-only (HEAD holds the deliverable): startup trio, one chained bash, one `kanban_update`, final text; zero thinking blocks — this file is the plan, and the bash, in order, is: `tail /tmp/npm-ci.log` only when the startup echo said `install started` (the file is shared across runs; an unconditional tail reads a stale log), the task-pinned acceptance command verbatim, `npm run build`, the asset check; nothing else belongs in it. On a re-run the prior notes are the evidence of record: the pinned acceptance commands are the only re-verification, and the notes' numeric, probe and perceptual claims are never audited, re-derived or re-probed. A verification-only run commits nothing, so `git status`, `.gitignore` and tracked-output questions never arise after the startup call: exactly one bash sits between the startup trio and the card update, whatever doubt surfaces. Implement: startup trio, one planning block, write, one scoped verify, commit, `kanban_update`, final text; the single planning block also closes the test-scope call, so no second planning block appears anywhere in the run. A fix task adds the one expected red→green cycle to this budget; every further red→green round names the rule it came from. End-of-run order is fixed: green evidence → `kanban_update` straight away (wrap-up reasoning goes into the card notes) → short final text → stop. When the spec mandates a live browser check, the live verdict is part of the green evidence: commit and launch the check as parallel calls in one turn, and the card follows the verdict. A second `kanban_update`, a thinking block after green, or a block between the green run and the card update is a breach. A run over budget means a rule broke; find the rule, never add probes.
- Read and edit discipline. Batch reads: the module under change, its `.test.js`, and every module that defines data the assertions use (value ranges, counts, enums, exported names, constants) go into one block of parallel `read` calls; read each file at most once, whole under ~400 lines, with the `read` tool, not `cat`. Draft no assertion constant before its defining source line is in hand: a planning block that ends by dispatching a read it should have started with is a wasted block — the read ships in the first read batch, and the planning block then only freezes the expectations. A zero-hit grep on one file: rerun directory-wide (`grep -rn "<symbol>" src/`) in the same block. All changes to one file are one `edit` call in one block: additions, removals, and the small fixes they force, together; never append to an already-edited file with a bash heredoc — a second mechanism and a second turn on one file. Keep each `oldText` short, exact, and unique; merge nearby changes, because overlapping edits are rejected. Trust an edit success: the scoped suite is the only edit re-check, and a re-read of an edited region without a tool error or a failing suite behind it is a breach; if a check is genuinely warranted, chain `cat -A` of the edited region into the next bash. Integration tasks (wiring many modules into one file): a batched export map (`grep -n "^export" src/**/*.js`), batched reads, one planning block, then write.
- Planning discipline: the one planning block settles everything at once — run shape, deliverable, file placement, data contracts, and the test call (trivial → skip tests; new feature → tests first; refactor → tests before code; fix → failing test first, written with any regression test; when the spec leaves the choice open, pick in one line and move on). Ambiguous spec wording: decide once, record the assumption on the card, move on. One topic per thinking block, closed with a decision or a tool call. Rule precedence is settled by this file in one line, never deliberated (task-pinned commands beat tool-runner preferences). If shape or precedence reasoning starts to surface anyway, emit the tool call at once with that one line as lead-in; a thinking block plus a lead-in stating the same conclusion is a double spend. A spec existence or wiring question is settled by one grep in the same block; the output is the evidence of record, even when reasoning already concluded the answer. Freeze a derived convention (sign, axis, units, placement, threshold, time window) once as an input-to-expected table; never re-derive it in a later block. A decision recorded in a plan or on the card is closed; reopen only after new tool evidence. Design cap: settle the mechanism in one pass — the smallest change that can pass the acceptance test — and freeze its constants with at most one probe (one `node -e` sweep over candidate values). The scoped test, not taste or a perceptual argument, is the arbiter. A thinking block that restates known facts (the startup output, prior notes, this file's recipes) is waste: end it with the one command that answers the open question, or skip it. One channel per statement: a lead-in line on a tool call replaces a thinking block, never repeats one. After a failed command, the next block is one tool call that gathers the missing evidence, never a plan revision: this file already rules the standard failures (diverged main, missing sibling module, red suite). One planning block per file written: fold the API map, conventions, and draft into it, then write in the next block.
- Test discipline. Scoped suites are the ones owning the touched files. Run a new suite at once after writing the module. The first red run of a tests-first suite is the expected signal; write the module in the next block without analysis. Never run the same suite twice without an intervening change; each acceptance check runs once per run — green closes it, and never re-run a green check or spend a block doubting green evidence. On failure, analyze fully, then batch fix and rerun into one step; if the identical failure persists, re-read the edited region before new hypotheses. A second bash runs only on a red check or a genuinely new question. A green suite needs no re-confirmation: the next block goes straight to `git status`, diff stat, and the commit. Vitest default timeout is 5 s; pass an explicit one for long simulations and keep `expect` out of per-step loops. A red wall-clock or perf assertion is measurement, never behavior: the benchmark bullet owns it. Derive fixture layout from geometry constants before writing the test: bodies spaced under a body width start in contact, and the scene then measures collision response, not settling. A multi-body settle test asserts rest, containment and finiteness, never exact per-body orientation — an exact edge balance is a valid equilibrium, and orientation assertions on packed piles churn fixtures. An assertion that failed twice on fixture grounds is demoted to the robust form in the next edit; never a third fixture re-tune. Every assertion comes from source read in this run: before asserting what a function does or does not reset, grep its lines; an expectation copied from another test without checking costs a fix edit.
- Stack: Vite + Vitest, ESM (`"type": "module"`). Scripts: `npm run dev`, `npm run build`, `npm test` (= `vitest run --passWithNoTests`). Call the pinned scripts, never `npx <tool>`, which re-resolves the binary and prints notice noise ahead of the output; the one legitimate `npx` use is filtering a single test by name: `npx vitest run <file> -t '<name>'`. A task-pinned acceptance command overrides this — state the precedence in one lead-in line on the bash, never in a thinking block. Tests sit next to sources as `src/**/*.test.js`; Vite and Vitest share `vite.config.js`. The build parses only modules reachable from `main.js`; parse-check anything else with `node -e "import('<path>')"`. A green build is a green build: never spend time on bundle size or asset counts. Log installs (`npm install --loglevel=http > /tmp/npm.log 2>&1`), never a bare install against a long timeout. `~/.npmrc` sets `min-release-age=7` and `ignore-scripts=true`; check `npm view <pkg> time` before version floors. Piping a command to `tail` masks its real exit code (`$?` is `tail`'s): judge green from the reporter output (`N passed`) or set `set -o pipefail` first. The same masking applies to any grep filter over test output (see the benchmark bullet).
- Build evidence rules. A fresh build's hashed asset name proves nothing: never compare it against prior notes, and never read a hash change as a defect or a hash match as confirmation. The one asset check: after a green build line (`✓ built in`), run `grep -oE '(src|href)="[^"]+"' dist/index.html` once, inside the same chained bash when possible. Copy the pattern character for character; a paraphrase drops the `src=`/`href=` anchors, manufactures false doubt, and forces a redo of a green check. Judge the check only from this output; close it green and never re-run it. After a failed build the on-disk `dist/` is stale: skip the grep or mark the check stale on the card.
- Sibling-task dependency (a module the spec names that a parallel branch owns): stage exactly the named files with `git show <ref>:<path> > <path>`; never stage the sibling's tests or fixtures, never merge the branch, never write a shim. main is a ref like any branch, and staging from main is never a reason to reconsider merging. Use the full ref from the card or `git worktree list`; on a ref error run `git branch --list '*<fragment>*'` once in the same block and retry. Read the copy before writing tests against its API. Never run a suite or build with a known-missing import. Verify against the copy, remove it in the commit block (or the spec-check block on a verification-only run), and record the dependency on the card. The decision is closed once made; only new tool evidence reopens it.
- Commit rule: code changed and tests green → one commit, lockfile included when deps changed. Verification-only run on a clean tree → no commit, card only. Never commit TASK.md, AGENTS.md, or `.kanban/`. Settle ignore/tracked-file questions with one `git status` plus one `.gitignore` read in the same block, never in thinking. Clean-room acceptance, only when the run changed committed code: `git archive HEAD | tar -x -C /tmp/check`, then in the copy run `npm ci`, `npm test`, `npm run build` separated by `;`, never `&&` (one failing step must not hide later results). On failure read the log tail and name the failing suite before any re-run. Then delete the copy.
- Card notes: compose from the TASK.md copy read at startup, changing only the lines the new evidence changes. Sections are fixed: Deliverable / Verification / Assumptions / Blockers / Manual checks left to other roles; add no other sections, and placement is never debated (a merge divergence from main is a Blockers line). The verification line names the HEAD short hash, so the next run's shape decision stays mechanical. Never re-enumerate deliverables, exports, or test counts when prior notes already carry them. Blocker and assumption lines carry over until startup evidence shows a change. `kanban_update` replaces the whole notes field, so carried lines are resent verbatim: dropping a carried blocker, assumption, or manual-check line loses information the board needs. `kanban_update` is one call per run, sent once: a wording or typo fix is not a defect and never justifies a second call; resend only for a factual error such as a wrong hash or a dropped carried line. After it returns, the run is closed: never re-read the card or a sent message to audit its wording; a suspected typo in sent text is not tool evidence and never reopens the run.
- Subagents and live checks. A background `Agent` call returns at once; `get_subagent_result(wait:true)` blocks the turn for the subagent's full duration (minutes for a browser check). Batch every independent call (commit, and the card update when the verdict cannot change it) into the launch turn as parallel invokes, then block on the result as one bare tool call in the next turn — never in a thinking block, never with wrap-up reasoning around it. When the only open item is a running subagent's result, the blocking call is the next tool call, full stop. Delegate reference research to background subagents in the planning block. Launch browser checks as soon as the scoped suite and build are green: dev server on an uncommon port, console error scan, kill the server, leave the repo clean. Never let two agents run npm or git commands in the same worktree at once. Live checks use `playwright-core` with the cached browser in `~/.cache/ms-playwright`; headless WebGL needs `--use-angle=swiftshader`; full Chromium can crash at launch (SIGTRAP) on this machine — fall back to `chrome-headless-shell` once, do not debug it. If the page does not wire a renderer, import and call the renderer factory from page context. Live browser probes read the owning module or its test first; a FAIL on an invented expectation is a probe bug.
- Stop rule: a green scoped run is the evidence; report the pass count and move on. After green, edit only to fix a real defect; a micro-optimization thought of after green goes into the last functional edit before the final green run or is skipped. Batch hygiene (dead code, unused imports, debug leftovers, diff grep for their markers) into the same edit pass as the last functional change. Post-green re-reads count as verification only when they check a spec point. Never expand scope to justify the run. Once the evidence is in hand, the card update is the only remaining step; after it the run ends, with no post-send block of any kind.
- Test-environment globals are partial: jsdom under Node exposes only some browser globals (for example no `AudioContext`, no `navigator.vibrate`). Feature-gate browser APIs on the function (`typeof navigator.vibrate === 'function'`), not on global presence, or tests and real browsers disagree. Design fakes (audio, vibration, GL, canvas) in the planning pass as minimal recorders: settable clock, call log, injectable functions; a recorder that tracks the 2D affine transform stack turns canvas-placement bugs into plain coordinate assertions. Derive test values (thresholds, caps, counts) from the module contract so the suite is green on the first run. If unsure what the environment provides, probe once (`node -e "console.log(typeof navigator, typeof AudioContext)"`) in the same block as the test draft.
- `src/math/` holds vec3/mat3/quat/mat4 helpers, out-param style (`add(out, a, b)`, column-major). Reuse them and always pass a destination; never alias `out` with an input, in production code, probes, or test helpers. Before writing a probe or test that calls a helper, grep the module's exported names once; a guessed API name costs a run-and-fix round.
- Physics and numeric probes. Replicate the production step sequence exactly, every substep in order; a partial re-implementation produces false contradictions. Never suppress errors (`catch { }`, ignored exit codes). Validate the fixture before trusting measurements (spawn margins, valid initial state, one sanity-checked step); never tune production constants from a broken fixture. A spec-suggested fix is a hypothesis: the instrumented probe that prints the value chain at the failure site goes out before the hypothesis is written, then the root cause gets implemented and any deviation is recorded as an assumption on the card. One probe per hypothesis; two dead hypotheses mean the probe measured the wrong thing, not that more speculation will help. Probes that import project modules import by absolute path (`const R = '<worktree>'; await import(R + '/src/...')`): a probe saved under `/tmp` with relative `./src` imports dies with ERR_MODULE_NOT_FOUND before it runs. When a computed magnitude is implausible, print the whole value chain (input → constant → derived value); suspect a scale applied twice, a per-unit vs total mix-up, or an argument in the wrong slot. For contact or normal signs, gate on signed approach velocity (`v·n < 0`), never absolute speed. Validate layered derivations one layer at a time against reference values. Temporary copies: copy a file to `/tmp` before temporary changes and restore or delete it in the same bash block chained with `;`. Regression proof: red before the fix, green after. A probe that copies production modules must trace the full call path, caller included; a stale or partial copy reports phantom failures. Regenerate instrumented copies from HEAD at the start of every measurement run, or import the real module and copy nothing. Repro search for numerically degenerate bugs: do not hand-tune poses. In one script, sweep the axes the spec names or implies over a decade around the failure scale, seeded with one known-yes case, with a pass predicate that catches every symptom shape. A zero-hit sweep: widen axes or shrink steps. When a sweep hits, minimize it and use it as the regression test. Pick tuned constants (epsilons, welds, tolerances) from the same sweep: the smallest value with zero failures across every symptom shape and fixture; keep the constant unexported with a one-line unit comment.
- Precision: use `Float64Array` for math state and Float64 in expectations, relative tolerances for accumulated sums. Compute expected values through the module's own helpers with a one-line `node -e` script in the same block as the assertion; never mental arithmetic, including counts, limits, and totals in UI or DOM probes (take them from module constants). Write expectations in final form on the first pass (imported constants, tolerance choice); a later refactor to constants is a wasted run. Quantities that physics lets collide tie legitimately: assert ordering non-strictly unless the spec demands strictness. Formula-dense code: transcribe implementation and expectations from one known-good reference in a single pass; cap convention research at one search round plus one fetch, then derive, freeze, record as an assumption.
- Benchmarks and wall-clock thresholds. A wall-clock assertion measures the machine as much as the code: it is never a functional failure, never blocks the deliverable, and never earns more than one A/B probe. Read the log tail once. The one probe, one bash: `rm -rf /tmp/ab && mkdir /tmp/ab && git archive HEAD | tar -x -C /tmp/ab && cp -r src /tmp/ab/ && ln -s "$PWD/node_modules" /tmp/ab/node_modules`, overlay the candidate change in the copy (the old constants or the pre-change module), and run the pinned test once per variant; an overlay of one change is a tighter control than a main-branch baseline, so never extract main for a timing question. Then fix the confirmed cause in one edit, or record the measured cause on the card. No alternated batches, no variance sweeps, no re-runs of a red threshold: the wall-clock perf test in `src/physics/world.e2e.test.js` is a known machine-load flake, and the merger role owns its one rerun. Equal work counts (contacts, iterations, calls) with a large slowdown in a float-heavy loop points at subnormal arithmetic first: print the minimum nonzero magnitudes once, and fix with an unexported epsilon floor that skips impulses below physical scale. When grepping outcomes across several runs, match both outcomes (`grep -E 'Tests +[0-9]+ (passed|failed)|expected [0-9.]+'`): a failure-only pattern makes green runs silent, and a silent result is ambiguous, never evidence.
- UI and DOM: use `setAttribute('aria-label', ...)` and `setAttribute('aria-live', ...)`, never `element.ariaLabel`; never attach custom properties to DOM nodes; a builder returns `{ element, sync }` pairs and one `syncAll` refreshes them. Modules that touch `document`, canvas, or GL need shims in the first draft of a probe; with a recorder harness, print one sample record before asserting on indices or tuples, and treat a harness failure as a harness bug.
