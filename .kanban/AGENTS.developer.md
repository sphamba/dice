# developer: project guidance for future agents of this role. The doctor rewrites this file after every run, keeping only durable, task-agnostic bullets (repo structure, build/test recipes, general shell traps, workflow tips). Never edit this file as the role agent.

- Stack: Vite + Vitest, ESM (`"type": "module"`). Scripts: `npm run dev`, `npm run build`, `npm test` (= `vitest run --passWithNoTests`). Tests sit next to sources as `src/**/*.test.js`; Vite and Vitest share `vite.config.js` (relative `base`, node test env).
- Tasks run in git worktrees under `.worktrees/<branch>`; `main` is the default branch. Give empty scaffold dirs a `.gitkeep` file.
- Fresh worktrees have no `node_modules`. `npm ci` against the lockfile is routine: run it once in the background with output redirected to a log, and read or write code while it runs; never spend a block idle-waiting or re-checking it. "Cannot find module vite/vitest" at startup means a missing install, not broken code.
- Installing new dependencies: redirect output to a log (`npm install --loglevel=http > /tmp/npm.log 2>&1`), never a bare install against a long timeout. `~/.npmrc` sets `min-release-age=7` and `ignore-scripts=true`; versions younger than a week are invisible to resolution and can hang installs in a retry loop, so check `npm view <pkg> time` before version floors. On failure, read the log and `cat ~/.npmrc`; verify hypotheses with cheap metadata (`npm view`, `npm ping`), not blind retries.
- Settle the deliverable, every file placement, every cross-module data contract, and every do-or-skip choice in the first planning block. Record assumptions on the task card and move on. Do not relitigate a settled choice in a later block, and do not reopen a skipped item after the implementation and its tests are green.
- Batch independent calls in one block: source reads, `git status`, and test runs do not depend on each other. Do not serialize them and then re-plan.
- Never re-run a failing test suite until you have changed something (code, test, or config); batch the fix and the rerun into one step. After writing a module, run its suite at once instead of a self-review thinking pass. A test-only change needs only the test rerun; the build output does not change.
- Use `Float64Array` for math and physics state, and Float64 in test expectations. Float32 storage rounds constants and breaks tight assertions. Pick the precision once, up front, for the whole module family, and prefer relative tolerances (for example a `nearRel` helper) over absolute 1e-12 for accumulated sums.
- In tests, compute expected values through the same pipeline the code runs: import the module constants (caps, time windows, fixed dt, damping) and apply the module's own filter, clamp, or window to the input before asserting. A hand-derived literal that skips one filter step looks plausible and fails late. When a red test shows a plausible actual value, suspect the expected value first. Where an exact count is fragile, assert a range. Write tests only against the planned public API, and never invent helper properties or placeholder exports that no module provides.
- For pure logic, go test-first: write the test, run to red, implement, run to green. An import-resolution red for a module you have not written yet is the expected first red; write the module next, do not investigate it.
- For formula-dense code (matrix math, projections, physics), pick one known-good reference and transcribe both the implementation and the expected test values from it in a single pass. When a test is red, compare the expected value against the reference first, and change the code only after the reference confirms the test is right.
- Cap convention research for platform or standards behavior (axis signs, coordinate frames, vendor quirks): one search round plus one fetch attempt. If the source does not state the mapping outright, stop consulting sources, derive the mapping once, freeze it as an input-to-expected test table, note platform differences as an assumption on the task card, and move on. Never spend a second thinking block re-deriving the same convention.
- Load kanban tools via tool_search ("kanban") during initial recon, not at the end. Record assumptions, versions chosen, and verification results on the task card in one update at the end.
- Commit the lockfile; `npm ci` needs it. Never commit TASK.md, AGENTS.md, or `.kanban/`; their tracking status is settled, so do not re-check it. Default to one commit per card when tests and implementation land together, and do not spend planning turns on commit granularity.
- Clean-room acceptance before finishing: `git archive HEAD | tar -x -C /tmp/check`, then run `npm ci && npm test && npm run build` in the copy, confirm `dist/index.html` references relative asset paths, and remove the copy afterwards. This validates the committed tree without touching the worktree's `node_modules`.
- actionlint is not installed. Validate workflow YAML with `python3 -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))" <file>`. Verify GitHub Action majors against their release tags, not memory. Reuse an existing workflow in `.github/workflows/` when one exists.
- Implement small, self-contained logic tasks (pure modules, unit tests, verification) directly in this role. Delegate to subagents only browser checks (dev server on an uncommon port, desktop plus mobile viewports, console error scan, subagent kills the server and leaves the repo clean) and independent work that can run in parallel. Never let two agents run npm or git commands in the same worktree at the same time.
- A failed tool call (missing or invalid argument) is fixed by re-issuing the corrected call in the next block; do not spend a thinking block re-planning around it. For `edit`, always include `path`, and keep each `oldText` short, exact, and unique.
- Shell trap: `ls` or `cat` on missing paths exits non-zero and prints to stderr; treat this as noise, not failure. Use `ls -a` to confirm dotfiles such as `.gitkeep`.
