# Reviewer role guidance

- The cwd is never the repo (the orchestrator starts you elsewhere, e.g. `.kanban/.logs`). First call resolves the worktree path; every git call uses `git -C <worktree>`. Run each check one way only; two variants of one check make contradictory evidence.
- Read the task file once for Summary, Specs, Notes, and current state. You rewrite the Notes at the end, so treat the developer's Notes as stale input. Never spend a pass on who wrote them.
- One git pass: `git -C <wt> rev-parse --abbrev-ref HEAD`, `git -C <wt> status`, then `git -C <wt> diff <base>...HEAD` with `--stat` and the full patch (`main` when no base is named). The diff is the scope record: cite it later, never re-run it.
- `main...HEAD` often carries unmerged commits from earlier tasks. Scope is this task's own commits: one `git log --oneline main..HEAD`, pick them, diff those, done. No second scoping pass.
- Repo layout: tasks run in worktrees under `.worktrees/<fix|feat>/<n>-<slug>`, the repo root is the main checkout. `src/main.js` wires the modules in `src/{audio,dice,input,math,physics,render,ui}`. Tests sit next to sources as `*.test.js`.
- Batch the reads of all changed source and test files as parallel calls in one turn. Read each file fully once before you judge anything. Truncated output is display-only, continue with `offset`.
- After the reads, one grep round for facts still unverified: imports, exports, exact signatures, and the construction site of every field you rely on. A fact seen once is closed; never re-open or re-print a file to re-see it.
- Reachability and usage questions ("is this helper called?", "who reads this field?") are greps, not reasoning. A thinking block about reachability is always slower than one grep call.
- Spec-interpretation judgment calls: decide once, pick the reading that matches the user-visible requirement, record it as an assumption in the note. Never relitigate an interpretation, an edge case, or settled math in a later block.
- Before the first vitest or build call, run the shim fix unconditionally: `ln -sf ../vitest/vitest.mjs node_modules/.bin/vitest && ln -sf ../vite/bin/vite.js node_modules/.bin/vite` (or bypass with `node node_modules/vitest/vitest.mjs run <paths>`). Do not inspect shims or node_modules internals.
- Run the scoped tests (`npx vitest run <changed test paths>`) and `npm run build`; there is no lint script. Redirect full output to a file and `tail` it, never pipe through grep. Record counts and exit codes once, then stop narrating results.
- Keep one running findings list. Fix each finding in the pass that finds it: edit, scoped rerun, commit, continue. Diagnose once, act next: one thinking block per finding, then the next tool call must edit, grep, or probe; if you write the same diagnosis twice, run the tool.
- Settle semantic uncertainty (helper behavior, argument shape, NaN, mutation) with a 3-line `node -e` probe in one call. JS never throws on a wrong argument shape, it silently yields NaN. Re-deriving library behavior in thinking blocks is wasted time.
- Review guard and match predicates on their reject path: feed a deliberately violating input, not inputs copied from the production shape. Fixtures that mirror production stay green even when the filter is dead.
- Cap the review at two passes: one after reading everything, one sweep over the findings list. A green assert, test, or build settles an item. Non-blocking flags get one line in the notes, not a second pass.
- Map each Spec bullet to diff or test evidence. Validate a Spec number only when the code computes it; never re-check settled math in a later pass.
- Probe scripts in one pass: imports, inputs, expected values, asserts. Derive expected values with the code's own decomposition; check units, signs, and axis conventions first. Floats: `toBeCloseTo` near boundaries, exact `toBe(0)` only for exact-zero guards. No assert-free loops.
- Timing-sensitive tests: after one unexpected failure, rerun at most twice, then one A/B against base (`git archive <base> | tar -x -C /tmp/perfbase && ln -s "$PWD/node_modules" /tmp/perfbase/node_modules`), record numbers, stop. Node has no DOM or canvas; review browser-only code by reading it.
- Shell traps: quote `sed` ranges (`sed -n '50,70p'`); chain independent commands with `&&` in one call, except git checks (see bullet 1).
- Outcomes: `approved`, `fixed` (commit small fixes yourself, stage only touched files), `violation` (only this calls `kanban_set_state` back to `to-do`). Close with green evidence, one `kanban_update` with condensed bullets plus one guidance line, then a short final text. State each conclusion once; the final text never restates the note. Defer live GL, feel, and sound checks to the live-tester role as deferred items.
