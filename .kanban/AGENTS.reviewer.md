# Reviewer role guidance

- **Worktree and cwd.** The orchestrator starts you outside the repo (typically `.kanban/.logs`). Worktrees live at `<repo>/.worktrees/<fix|feat>/<n>-<slug>`; the task file lives in `.kanban/`. Use `git -C <wt>` for every git call, never bare git and never a `cd` first: a bare git call answers for whatever checkout the inherited cwd carries, so two git calls from different cwds give contradictory branch names. Chain independent commands with `&&`. Quote `sed` ranges (`sed -n '50,70p'`). Read files with the read tool, never bash cat. Bash output truncates near 8k and hides hunks, so a diff echoed through bash is unusable. Read calls also truncate near 8k characters: continue any truncated read with `offset` in the same turn, or the tail of that file is unreviewed. Run each check one way only; two variants of one check make contradictory evidence.

- **Fixed opening sequence.** Block 1: read the task file once with the read tool; it names the worktree and the base branch, so no bash call comes before it. Block 2: one chained bash call that runs the git pass recipe below against that worktree. Block 3: read `/tmp/review.diff` — and `/tmp/review.unstaged.diff` when status was dirty — with the read tool, continuing past truncation with `offset`. Block 4: all diff-touched files in one batched turn of parallel read calls. No thinking or text block sits between these four. After that, stages never repeat: one grep round, evidence chain, verdict, `kanban_update`, one-line outcome. Banned at any point: a plan or step list of the pipeline, an outline of the next bash command before running it, and a recap or audit of already-green evidence after the last bash call. If you can name the next stage, make that stage's tool call.

- **One carrier per result.** Each stage result lives in one place: the thinking block that holds it, or a short lead-in on the next tool call, never both and never in two blocks. A green result or a zero-match grep needs no carrier at all. The spec-bullet-to-evidence mapping lives only on the findings list; restating it in a thinking or text block is always waste. Standalone text blocks carry nothing except the final one-line outcome.

- **The task read settles four decisions once.** In that same read: first-review vs re-review (a card back after `fixed` is a normal re-review, spend no block on it), base branch (the base the task names, else `main`), suite scope (Specs name the full suite → `npm test` runs, and no other instruction changes that; Specs name no suite → scoped suites for diff-touched paths, recorded as one findings line), and dirty files (status-listed uncommitted files are in scope). The developer's claimed file lists and measured numbers are claims to verify, never the review scope and never targets to reproduce. You rewrite the Notes at the end, so all Notes content is stale input.

- **Git pass recipe (one chained call, never repeated).** `git -C <wt> rev-parse --abbrev-ref HEAD && git -C <wt> status && git -C <wt> log --oneline <base>..HEAD && git -C <wt> diff <base>...HEAD --stat && git -C <wt> diff <base>...HEAD > /tmp/review.diff`, and when status lists dirty files append `&& git -C <wt> diff > /tmp/review.unstaged.diff` to the same chain. Read both diffs in the following block. The recorded diffs are the scope record: cite them later, never re-run them, never re-diff any file. A later "committed or uncommitted" question is answered by re-reading the recorded diffs, never by a thinking-block reconstruction or a new git call. If a spec-required change exists only uncommitted, verify it and commit it yourself.

- **Batch the file reads.** All diff-touched source and test files go out as parallel read calls in ONE turn, the very next block after the diff read. Continue truncated reads with `offset` in the same turn. Do not read or diff files the diffs do not touch; a read outside the diffs needs a finding that demands it. Consumed-module context is read at the contract lines (offset and limit), not as whole files.

- **One grep round, bounded scope.** After the reads, before the verdict: imports, exports, exact signatures, construction sites, removed tokens, leftover hard-coded values. Removed-token and leftover-literal greps cover the whole `src/` tree (sources and tests), never only diff-touched files. `rg`/`grep` exit 1 on zero matches, which aborts an `&&` chain: chain the round with `;` (or end each grep with `|| true`) and read exit 1 with empty output as a clean no-match. Cap each grep's output (`-l`, `-c`, or `| head -20`); oversized combined output is an error, not evidence. Every side-question the round surfaces gets its grep inside the same round. A side-claim that does not gate the verdict gets one probe, then is dropped. Never infer file contents from guessed tokens; to check what a test asserts, read it or list its `describe`/`it` lines.

- **Findings list and fix pass.** Keep one running findings list: one line per Spec bullet mapping bullet to evidence, started during the file reads, append-only. Later stages append, amend, or strike lines, and never rebuild or re-argue a settled line. Fix each finding in the pass that finds it: edit, scoped rerun, commit, continue, with no narration block before the edit. When the diff misses a Spec-named test, add it in that same pass, mirror the nearest existing test, and let the scoped rerun be the only verification. Cap the review at two passes: pass one maps every Spec bullet to diff or test evidence exactly once; pass two sweeps the findings list green. A green assert, test, or build settles an item; re-checking already-green evidence in any later block is banned.

- **Derivation budget.** Hand-derive a quantity at most once, cap that derivation at about ten lines, attach the result to the findings list, and never touch the quantity again. Convention questions (storage order, row-to-UV mapping, transform direction, sign conventions) are settled by quoting the defining lines of already-read modules, never by derivation. When a derivation conflicts with green tests, the derivation's premise is wrong. When a scoped suite covers the derived question, the derivation ends at its conclusion. A derivation that grows past the cap, repeats a pass over the same signs or units, or gets truncated is a hard stop: cut the block, keep what it settled, and settle the number with one probe.

- **Spec interpretation decides in one block.** Borderline readings (assertion strength, wrapper scope, how a Spec names an acceptance value) get one sentence of reasoning, one choice that matches the user-visible requirement, one assumption line on the findings list, and one mention in the note. The debate never spans blocks: a second block on the same question is a defect. Numbers produced by an interpretation are verified by a probe or an existing test, never by another derivation round. Loosened test tolerances, rewritten or moved fixtures, and similar test adaptations are accepted once they map to a Spec bullet and the suite is green: one or two sentences, one findings line, one mention in the note. An accepted adaptation or settled math never reappears in a later block.

- **Numeric and geometric questions get probes.** A probe runs in the block where the question arises, never as hand derivation in a thinking block. Keep inline `node -e` to about 3 lines; for multi-part checks write a small script to `/tmp` with the write tool and run `node /tmp/x.mjs`. Build the script from the committed test fixture, not from memory: copy its imports and fixture setup, point every import at the worktree source, write each generation step once. The script prints its inputs, asserts with `node:assert`, and ends with one PASS or FAIL line. JS silently yields NaN on wrong argument shapes, so assert endpoints and edges, never eyeball printed values. On FAIL or nonsense, suspect the probe first (wrong pairing, units, index), fix it, rerun once. When your numbers differ from claimed numbers, the question is closed: record yours, correct the claim in the Notes rewrite, add one line that the values are re-measured. After two probe attempts, judge with the recorded numbers and move on.

- **Evidence chain (one or two back-to-back bash calls, no block between).** (1) Heal the worktree tooling unconditionally: `test -x <wt>/node_modules/.bin/vitest || npm --prefix <wt> ci > /tmp/npm-ci.log 2>&1; tail -3 /tmp/npm-ci.log`. (2) Fix the shims: `ln -sf ../vitest/vitest.mjs <wt>/node_modules/.bin/vitest && ln -sf ../vite/bin/vite.js <wt>/node_modules/.bin/vite`. (3) `npx vitest run <changed test paths> > /tmp/vitest.log 2>&1; tail -20 /tmp/vitest.log`. (4) `npm test > /tmp/npm-test.log 2>&1; tail -5 /tmp/npm-test.log` only if the task read flagged the full suite. (5) `npm run build > /tmp/build.log 2>&1; tail -10 /tmp/build.log`. Never inspect shims or node_modules internals. There is no lint script. Redirect full output to a file and `tail` it, never pipe through grep. Record counts and exit codes once, then stop narrating results.

- **A/B-verify each behavioral fix once.** If the fix is uncommitted, stage it first (`git -C <wt> add <paths>`), then: `git -C <wt> restore --source <base-commit> -- <path>`, run the scoped tests and expect the new assertion to fail, `git -C <wt> restore -- <path>` (the index returns the fix), confirm with `git status`. Never restore a path whose fix is neither staged nor backed up: a bare restore from HEAD or index destroys uncommitted work. If the old source breaks the new test API, extract the base tree instead: `git -C <wt> archive <base-commit> | tar -x -C /tmp/ab && ln -s "$PWD/node_modules" /tmp/ab/node_modules`. Skip A/B for whitespace-only, comment-only, rename-only, and test-only additions; a green scoped rerun settles those, and no block re-litigates the skip.

- **Commit rule.** Commit after the evidence chain is green, staging only the files the findings list names as touched. The findings list already names them, so the commit command needs no planning block and no re-derivation of the file set. Keep `git -C <wt>` in the commit command.

- **Shader changes.** The task's Specs are the oracle, not recall of the named algorithm or of GLSL capability. Settle compile, link, and capability questions (uniform-array sizes vs vertex or instance counts, dynamic indexing, loop bounds) with one probe, never thinking-block recall: extract the GLSL sources to `/tmp`, run `glslangValidator` on each source and each linked program pair at the spec's ES profile, and assert counts fit the uniform arrays in the same script. A validator PASS settles compile, link, and indexing questions outright.

- **Review guard and match predicates.** On their reject path, feed a deliberately violating input, not inputs copied from the production shape: fixtures that mirror production stay green even when the filter is dead.

- **Node has no DOM or canvas.** Review browser-only code by reading it. Verify page-level assumptions (canvas background, CSS compositing) with one grep of `index.html` and `src/style.css`. Timing-sensitive failures: rerun at most twice, then one A/B, record numbers, stop. Live GL, screenshots, sound, and feel are the live-tester role's scope: never read the developer's live evidence (no screenshot PNGs, no `/tmp` out or report dirs); accept or flag each live claim in the note in one line.

- **Outcomes.** `approved`, `fixed` (commit small fixes yourself, stage only touched files), `violation` (only violation calls `kanban_set_state` back to `to-do`; approved and fixed never touch state). Close with green evidence and one `kanban_update`: condensed bullets, counts not narratives, one guidance line, deferred live GL, feel, and sound items for the live-tester role. Draft the note inside the `kanban_update` call from the findings list; no pre-note audit block. After `kanban_update` the review is over: zero further tool calls, and a final text of one line that names the outcome alone.
