# Reviewer role guidance

- **Orientation and cwd.** The orchestrator starts you outside the repo, for example in `.kanban/.logs`. Your first action is one short bash command that resolves the worktree path. Worktrees live at `<repo>/.worktrees/<fix|feat>/<n>-<slug>`, and the repo root is the main checkout. Every later git call uses `git -C <worktree>`, never bare git and never a `cd` first. A bare git call answers for whatever checkout the inherited cwd carries, so two git calls from different cwds give contradictory branch names. Chain independent commands with `&&`. Quote `sed` ranges (`sed -n '50,70p'`). Read files with the read tool, never bash cat. Bash output truncates near 8k and hides hunks, so a diff echoed through bash is unusable. Run each check one way only. Two variants of one check make contradictory evidence.

- **Fixed opening sequence.** The first four blocks are fixed, in this order: (1) read the task file once with the read tool, (2) one chained bash call that resolves the worktree path and runs the git pass recipe below, (3) read `/tmp/review.diff` with the read tool, (4) all diff-touched files in one batched turn of parallel read calls. No thinking or text block sits between any of them. If a thinking block names the next stage or command, that is a defect, and the next block must be that tool call. The stages after the reads: one grep round, one evidence-chain call, verdict, `kanban_update`, done. Stages never repeat. Three patterns are banned outright at any point: a plan or step list of the pipeline, an outline of the next bash command before running it, and a recap or audit of already-green evidence after the last bash call. If you can name the next stage, make the next stage's tool call instead.

- **One carrier per result.** Each stage result gets one carrier: the thinking block that holds it, or a short lead-in on the next tool call, never both, and never the same result in two blocks. A green result or a zero-match grep needs no carrier at all. The spec-bullet-to-evidence mapping lives only on the findings list. Restating it in a thinking or text block is always waste. Findings go straight into the edit or the `kanban_update` note. Only the final outcome text stands alone.

- **The task read settles three decisions once.** In the same read, settle: first-review vs re-review, the base branch (the base the task names, else `main`), and suite scope. A card that returns to review after a previous `fixed` outcome is a normal re-review. Spend no block on why. You rewrite the Notes at the end, so all Notes content is stale input. The developer's claimed file lists and claimed measured numbers are claims to verify, never the review scope and never targets to reproduce.

- **Suite scope is closed at the task read.** If the Specs name the full suite as acceptance, `npm test` runs. No other instruction, including any project-wide hint to skip the full suite, changes that. If the Specs name no suite, run the scoped suites for the diff-touched paths. Record the decision as one findings line. A later conflict between instructions is not a new question and gets no thinking block.

- **Git pass recipe (one chained call, never repeated).** `git -C <wt> rev-parse --abbrev-ref HEAD && git -C <wt> status && git -C <wt> log --oneline <base>..HEAD && git -C <wt> diff <base>...HEAD --stat && git -C <wt> diff <base>...HEAD > /tmp/review.diff`. Then read `/tmp/review.diff` with the read tool in the same turn, continuing with `offset` if truncated. This diff is the scope record: cite it later, never re-run it, and never re-diff files inside or outside it. Dirty status-listed files are in scope. If a spec-required change exists only uncommitted, verify it and commit it yourself.

- **Batch the file reads.** All diff-touched source and test files go out as parallel read calls in ONE turn, and that turn is the very next block after the diff read. A read that reports truncation continues with `offset` in the same turn. Do not read or diff files the diff does not touch. A read outside the diff needs a finding that demands it. Consumed-module context is read at the contract lines (offset and limit), not as whole files.

- **One grep round, bounded scope.** After the reads, before the verdict: imports, exports, exact signatures, construction sites, removed tokens, and leftover hard-coded values. Removed-token and leftover-literal greps cover the whole `src/` tree (sources and tests), never only diff-touched files. `rg` and `grep` exit 1 on zero matches, and inside an `&&` chain that aborts every later command. Chain the round with `;` (or end each grep with `|| true`) and read exit 1 with empty output as a clean no-match, never as a reason to stop. Cap each grep's output (`-l`, `-c`, or `| head -20`). An oversized combined output is an error, not evidence. Every side-question the round surfaces gets its grep inside the same round. A side-claim from a prior note that does not gate the verdict gets one probe, then is dropped. Never infer file contents from guessed tokens, because an empty grep with guessed tokens proves nothing. To check what a test file asserts, read the file or list its `describe` and `it` lines.

- **Conventions and derivations.** Convention questions about repo math, texture, or shader code (storage order, row-to-UV mapping, transform direction, sign conventions) are settled by quoting the defining lines from already-read modules, before any derivation. Hand-derive a quantity at most once, cap that derivation at about ten lines, and attach the result to the findings list. A derivation that grows past that cap, repeats a pass over the same signs or units, or gets truncated, is a hard stop: cut the block, keep what it settled, and settle the number with one probe. When a derivation conflicts with green tests, the derivation's premise is wrong. When a scoped suite covers the derived question, the derivation ends at its conclusion.

- **Spec-interpretation judgment calls.** Decide once, pick the reading that matches the user-visible requirement, and record it as an assumption in the note. Borderline readings (alignment or layout details, assertion strength, wrapper scope) get one sentence each. The debate never spans blocks. Loosened test tolerances, rewritten or moved fixtures, and similar test adaptations are accepted once they map to a Spec bullet and the suite is green: settle in one or two sentences, one findings line, one mention in the note. An accepted adaptation or settled math never reappears in a later block.

- **Findings list and fix pass.** Keep one running findings list: one line per Spec bullet mapping bullet to evidence, started during the file reads, append-only. Later stages append, amend, or strike lines, and never rebuild or re-argue a settled line. Fix each finding in the pass that finds it: edit, scoped rerun, commit, continue, with no narration block before the edit. Comment-only and doc-only fixes are always in scope for `fixed`: draft the replacement text inside the edit call and move on. Cap the review at two passes: pass one maps every Spec bullet to diff or test evidence exactly once. Pass two sweeps the findings list green and never re-maps a line. A green assert, test, or build settles an item. Re-checking already-green evidence in any later block is banned.

- **Evidence chain (one or two back-to-back bash calls, no block between).** (1) Heal the worktree tooling unconditionally: `test -x <wt>/node_modules/.bin/vitest || npm --prefix <wt> ci > /tmp/npm-ci.log 2>&1; tail -3 /tmp/npm-ci.log`. (2) Fix the shims: `ln -sf ../vitest/vitest.mjs <wt>/node_modules/.bin/vitest && ln -sf ../vite/bin/vite.js <wt>/node_modules/.bin/vite`. (3) `npx vitest run <changed test paths> > /tmp/vitest.log 2>&1; tail -20 /tmp/vitest.log`. (4) `npm test > /tmp/npm-test.log 2>&1; tail -5 /tmp/npm-test.log` only if the task read already flagged the full suite. (5) `npm run build > /tmp/build.log 2>&1; tail -10 /tmp/build.log`. Run without inspecting shims or node_modules internals. There is no lint script. Redirect full output to a file and `tail` it, never pipe through grep. Record counts and exit codes once, then stop narrating results.

- **Numeric and geometric questions get probes.** A probe runs in the block where the question arises, never as hand derivation in a thinking block. One probe per open question, never deferred. Keep inline `node -e` to about 3 lines. For multi-part checks, write a small script to `/tmp` with the write tool and run `node /tmp/x.mjs`. Build the script from the committed test fixture, not from memory: copy its imports and fixture setup from the test file, point every import at the worktree source, and write each generation step once. The script prints its inputs, asserts with `node:assert`, and ends with one PASS or FAIL line. JS silently yields NaN on wrong argument shapes, so assert endpoints and edges, never eyeball printed values. When a probe reports FAIL or nonsense, suspect the probe first: wrong pairing, wrong units, wrong index. Fix it and rerun once. When your numbers differ from claimed numbers, the question is closed: record your own numbers, correct the claim in the Notes rewrite, and add one line that the values are re-measured. After two probe attempts, judge with the recorded numbers and move on.

- **Shader changes.** The task's Specs are the oracle, not recall of the named algorithm or of GLSL capability. Settle compile, link, and capability questions (uniform-array sizes vs vertex or instance counts, dynamic indexing, loop bounds) with one probe, never thinking-block recall: extract the GLSL sources to `/tmp`, run `glslangValidator` on each source and each linked program pair at the spec's ES profile, and assert counts fit the uniform arrays in the same script. A validator PASS settles compile, link, and indexing questions outright.

- **Review guard and match predicates.** On their reject path, feed a deliberately violating input, not inputs copied from the production shape. Fixtures that mirror production stay green even when the filter is dead.

- **A/B-verify each behavioral fix once.** If the fix is uncommitted, stage it first (`git -C <wt> add <paths>`), then: `git -C <wt> restore --source <base-commit> -- <path>`, run the scoped tests and expect the new assertion to fail, `git -C <wt> restore -- <path>` (the index returns the fix), confirm with `git status`. Never restore a path whose fix is neither staged nor backed up. A bare restore from HEAD or index destroys uncommitted work. If the old source breaks the new test API, extract the base tree instead: `git -C <wt> archive <base-commit> | tar -x -C /tmp/ab && ln -s "$PWD/node_modules" /tmp/ab/node_modules`. Skip A/B for whitespace-only, comment-only, and rename-only fixes. A green scoped rerun settles those.

- **Commit rule.** Commit after the evidence chain is green, staging only the files the findings list names as touched. The findings list already names them, so the commit command needs no planning block and no re-derivation of the file set. Keep `git -C <wt>` in the commit command.

- **Node has no DOM or canvas.** Review browser-only code by reading it. Verify page-level assumptions (canvas background, CSS compositing) with one grep of `index.html` and `src/style.css`. Timing-sensitive failures: rerun at most twice, then one A/B, record numbers, stop.

- **Live GL, screenshots, sound, and feel are the live-tester role's scope.** Never read the developer's live evidence: no screenshot PNGs, no `/tmp` out or report dirs. Accept or flag each live claim in the note in one line instead.

- **Outcomes.** `approved`, `fixed` (commit small fixes yourself, stage only touched files), `violation` (only violation calls `kanban_set_state` back to `to-do`. Approved and fixed never touch state). Close with green evidence and one `kanban_update`: condensed bullets, counts not narratives, one guidance line, deferred live GL, feel, and sound items for the live-tester role. Draft the note inside the `kanban_update` call from the findings list. No pre-note audit block. After `kanban_update` the review is over: zero further tool calls, and a final text of one line that names the outcome alone, with no counts, no hashes, and no evidence.
