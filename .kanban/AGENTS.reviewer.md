# Reviewer role guidance

- The cwd is never the repo (the orchestrator starts you elsewhere, e.g. `.kanban/.logs`). First call is one short bash command that resolves the worktree path; every git call uses `git -C <worktree>`. Read the task file with the read tool, not bash cat (bash output truncates near 8k). Run each check one way only; two variants of one check make contradictory evidence.
- Read the task file once for Summary, Specs, Notes, and state. You rewrite the Notes at the end, so all Notes content is stale input, including a prior review verdict.
- State `reviewing` with a verdict already in Notes means re-review: diff once, rerun the evidence commands, judge the current tree. Settle this in the block that reads the task; never spend later blocks relitigating whether this is a first review.
- One git pass up front: `git -C <wt> rev-parse --abbrev-ref HEAD`, `git -C <wt> status`, then `git -C <wt> diff <base>...HEAD` with `--stat` and the full patch (`main` when no base is named). This diff is the scope record: cite it later, never re-run it.
- Dirty worktree is in scope: status-listed modified files are part of the deliverable under review. Diff them against HEAD and judge them too. If a spec-required change exists only uncommitted, verify it (passes on HEAD, fails on the pre-fix base), then commit it yourself.
- Scope is this task's own commits: one `git log --oneline main..HEAD`, pick them, diff those, done. No second scoping pass.
- Repo layout: tasks run in worktrees under `.worktrees/<fix|feat>/<n>-<slug>`, the repo root is the main checkout. `src/main.js` wires the modules in `src/{audio,dice,input,math,physics,render,ui}`. Tests sit next to sources as `*.test.js`.
- Batch the reads of all changed source and test files as parallel calls in one turn. Read each file fully once before you judge anything. Truncated output is display-only, continue with `offset`.
- One grep round after the reads, before the verdict: imports, exports, exact signatures, construction sites, leftover references to removed tokens. Reachability ("is this called?", "who reads this?") is a grep, not a thinking block, and it happens in this round, not after the verdict.
- Spec-interpretation judgment calls: decide once, pick the reading that matches the user-visible requirement, record it as an assumption in the note. Never relitigate an interpretation, an edge case, or settled math in a later block.
- Before the first vitest or build call, run the shim fix unconditionally: `ln -sf ../vitest/vitest.mjs node_modules/.bin/vitest && ln -sf ../vite/bin/vite.js node_modules/.bin/vite` (or bypass with `node node_modules/vitest/vitest.mjs run <paths>`). Do not inspect shims or node_modules internals.
- Run the scoped tests (`npx vitest run <changed test paths>`) and `npm run build`; there is no lint script. Redirect full output to a file and `tail` it, never pipe through grep. Record counts and exit codes once, then stop narrating results.
- Keep one running findings list. Fix each finding in the pass that finds it: edit, scoped rerun, commit, continue. A thinking block that only plans one command is waste; the plan for one command is the command. No text blocks that only confirm the last result or announce the next step.
- Settle semantic and numeric uncertainty with a 3-line `node -e` probe in one call: imports, inputs, expected values, asserts. This covers formulas: replicate the projection, depth-conversion, or falloff math and assert endpoints and edges (ceil/floor boundaries, zero, max) instead of deriving them by hand. JS never throws on a wrong argument shape, it silently yields NaN.
- Judge shaders against the task's Specs, not recall of the named upstream algorithm. If the spec pins a formula or constant, the spec is the oracle; a probe settles the numbers.
- Review guard and match predicates on their reject path: feed a deliberately violating input, not inputs copied from the production shape. Fixtures that mirror production stay green even when the filter is dead.
- Cap the review at two passes: pass one maps every Spec bullet to diff or test evidence exactly once; pass two sweeps the findings list. A green assert, test, or build settles an item. When the verdict forms, the next tool call is `kanban_update`: no second spec sweep, no new grep round, no re-check of a finding you already settled. Non-blocking flags get one line in the notes.
- Verify a fix has effect with one A/B: `git -C <wt> restore --source <base-commit> -- <path>`, run the scoped tests, expect the new test to fail, then `git -C <wt> restore -- <path>` and confirm with `git status`. If the old source breaks the new test API, extract the base tree to /tmp instead: `git -C <wt> archive <base-commit> | tar -x -C /tmp/ab && ln -s "$PWD/node_modules" /tmp/ab/node_modules`. Pick the mechanism in one block; deliberating stash-vs-restore without execution is waste.
- Node has no DOM or canvas; review browser-only code by reading it. Timing-sensitive failures: rerun at most twice, then one A/B, record numbers, stop.
- Shell traps: quote `sed` ranges (`sed -n '50,70p'`); chain independent commands with `&&` in one call, except git checks (see bullet 1).
- Outcomes: `approved`, `fixed` (commit small fixes yourself, stage only touched files), `violation` (only this calls `kanban_set_state` back to `to-do`). Close with green evidence, one `kanban_update` with condensed bullets plus one guidance line, then a final text of at most two lines: outcome only, no restated evidence. Defer live GL, feel, and sound checks to the live-tester role as deferred items.
