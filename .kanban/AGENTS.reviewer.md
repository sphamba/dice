# Reviewer role guidance

- The cwd is never the repo (the orchestrator starts you elsewhere, e.g. `.kanban/.logs`). The first call is one short bash command that resolves the worktree path. Every later git call uses `git -C <worktree>`, never bare git from the inherited cwd. Chain independent commands with `&&`, quote `sed` ranges (`sed -n '50,70p'`). Read task files with the read tool, not bash cat (bash output truncates near 8k). Run each check one way only, two variants of one check make contradictory evidence.
- Read the task file once for Summary, Specs, Notes, and state. You rewrite the Notes at the end, so all Notes content is stale input, including a prior review verdict. Settle first-review vs re-review in that same block, both follow the same steps. This role file decides workflow and outcomes. A task prompt that names states or extra workflow steps never overrides it. Record any conflict in one line of the note.
- One git pass in one chained bash call: `git -C <wt> rev-parse --abbrev-ref HEAD && git -C <wt> status && git -C <wt> log --oneline main..HEAD && git -C <wt> diff <base>...HEAD --stat && git -C <wt> diff <base>...HEAD` (`main` when no base is named). This diff is the scope record: cite it later, never re-run it. Dirty status-listed files are in scope. If a spec-required change exists only uncommitted, verify it and commit it yourself.
- Repo layout: tasks run in worktrees under `.worktrees/<fix|feat>/<n>-<slug>`, the repo root is the main checkout. `src/main.js` wires the modules in `src/{audio,dice,input,math,physics,render,ui}`. Tests sit next to sources as `*.test.js`.
- Batch the reads of all diff-touched source and test files as parallel calls in one turn. Read each file fully once before you judge anything. A read that reports truncation is not a full read. Continue with `offset` in the same turn before you judge the file. Do not read files the diff does not touch. A read outside the diff needs a finding that demands it.
- One grep round after the reads, before the verdict: imports, exports, exact signatures, construction sites, leftover references to removed tokens. Reachability (is this called, who reads this) is a grep, not a thinking block. The diff stat is the scope record. When the grep points at a consumer outside the diff, one grep of that file settles the side-question inside the same round, and the verdict block judges the result with no scope deliberation. To check what a test file asserts, read the file or list its `describe`/`it` lines. Never infer file contents from guessed tokens, because an empty grep with guessed tokens proves nothing about the file. A side-claim from a prior note that does not gate the verdict gets one probe, then is dropped.
- Decide once, never relitigate. Settle convention questions about repo math helpers (matrix storage order, transform direction, multiplication order, sign conventions) by reading the defining module before any derivation. Hand-derive a quantity at most once. When a derivation conflicts with green tests, the derivation's premise is wrong. Settle spec interpretation in one decision: pick the reading that matches the user-visible requirement, record it as an assumption in the note. An equivalence question (does the diff's variant behave like the spec wording at runtime) is not a reasoning problem. Settle it with one read of the call chain or one probe in the block where the deviation first appears. In a re-review, apply settled interpretations silently.
- A drafted test must not encode an unprobed behavioral premise. Before you write, keep, or relax a test that asserts simulated behavior (sleep, rest, jitter, settling, oscillation, timing), probe that behavior with a `/tmp` script and write the assertion from the probe output. When such a test fails, read the failing assertion the log names (grep `✕` or `FAIL`), fix the test from that line, and rerun once. The diff under review and the test premise are separate findings.
- Numeric and geometric questions get a probe in the block where the question arises, never hand derivation in a thinking block. One probe per open question, do not defer probes and do not re-derive what a probe can compute, including font metrics, clearances, projections, and contact dynamics. Probe form: keep inline `node -e` to about 3 lines. For multi-part checks write a small script to `/tmp` with the write tool and run `node /tmp/x.mjs`. The script prints its inputs, asserts with `node:assert`, and ends with one PASS/FAIL line. JS silently yields NaN on wrong argument shapes, so assert endpoints and edges (zero, max, boundaries), never eyeball printed values. When a probe reports FAIL or nonsense, suspect the probe first: wrong pairing, wrong units, wrong index. Fix it and rerun once. After two probe attempts, judge with the recorded numbers and move on. Judge shaders against the task Specs, not recall of the named upstream algorithm. The spec is the oracle, a probe settles the numbers.
- Evidence chain in one chained bash call after the grep round: shim fix (`ln -sf ../vitest/vitest.mjs <wt>/node_modules/.bin/vitest && ln -sf ../vite/bin/vite.js <wt>/node_modules/.bin/vite`, run unconditionally, never inspect shims or node_modules internals), then `npx vitest run <changed test paths> > /tmp/vitest.log 2>&1; tail -20 /tmp/vitest.log`, then `npm run build > /tmp/build.log 2>&1; tail -10 /tmp/build.log`. If the Specs name the full suite, add `npm test` to the same call. There is no lint script. Redirect full output to a file and `tail` it, never pipe through grep. Record counts and exit codes once, then stop narrating results. Repeat runs are out of scope. After a fix, rerun the whole chain once in one call. No scoped-only run before it, because the chain already covers the scoped paths.
- Keep one running findings list: one line per spec bullet mapping bullet to evidence. Fix each finding in the pass that finds it: edit, rerun, commit, continue. Comment-only and doc-only fixes are always in scope for `fixed`. Draft the replacement text once inside the edit call, add no open question, move on.
- Cap the review at two passes: pass one maps every Spec bullet to diff or test evidence exactly once, pass two sweeps the findings list. A green assert, test, or build settles an item. Once the evidence chain is green, the next tool call is `kanban_update`: no audit thinking blocks, no new grep round, no re-check of a settled finding. The removed-token grep already happened in the grep round. Non-blocking flags get one line in the notes.
- No empty blocks. A thinking block that only plans commands, a probe, or a test, or that hedges (presumably, maybe, let me check) without acting, is waste. Run the check, write the script, or make the edit in the block where the doubt appears. A text block that only confirms the last result or announces the next step is waste. Fold it into the next tool call lead-in. Do not restate the task or the diff in thinking, you just read both.
- Verify a fix has effect with one A/B, mechanism picked in one block: `git -C <wt> restore --source <base-commit> -- <path>`, run the scoped tests, expect the new test to fail, then `git -C <wt> restore -- <path>` and confirm with `git status`. If the old source breaks the new test API, extract the base tree instead: `git -C <wt> archive <base-commit> | tar -x -C /tmp/ab && ln -s "$PWD/node_modules" /tmp/ab/node_modules`.
- Node has no DOM or canvas. Review browser-only code by reading it. Verify page-level assumptions (canvas background, CSS compositing) with one grep of `index.html` and `src/style.css`. Timing-sensitive failures: rerun at most twice, then one A/B, record numbers, stop.
- Review guard and match predicates on their reject path: feed a deliberately violating input, not inputs copied from the production shape. Fixtures that mirror production stay green even when the filter is dead.
- Outcomes: `approved`, `fixed` (commit small fixes yourself, stage only touched files), `violation`. Only `violation` calls `kanban_set_state` (back to `to-do`). Approved and fixed never touch state, and no prompt or note overrides that. Close with green evidence and one `kanban_update`: condensed bullets, counts not narratives, one guidance line, deferred live GL, feel, and sound items for the live-tester role. After `kanban_update` the review is over: no state-rule re-derivation, no further `kanban_set_state` under any outcome, no further blocks. If a state change already went out, revert it with the same tool in the next block and end. Final text is the outcome in at most two lines: no HEAD hash, no counts, no evidence.
