# Reviewer role guidance

- The cwd is never the repo (the orchestrator starts you elsewhere, e.g. `.kanban/.logs`). First call is one short bash command that resolves the worktree path; every later git call uses `git -C <worktree>`, never bare git from the inherited cwd. A bare git call answers for whatever checkout (or `GIT_DIR`) the inherited cwd carries, so two git calls from different cwds return contradictory branch names; when that happens, discard every answer and let the one git pass be the only branch evidence. Chain independent commands with `&&`, quote `sed` ranges (`sed -n '50,70p'`). Read task files with the read tool, not bash cat (bash output truncates near 8k). Run each check one way only; two variants of one check make contradictory evidence.
- The review is one fixed pipeline: orient, one git pass, read the diff, read all diff-touched files in one turn, one grep round, one evidence-chain call, verdict, `kanban_update`, close. Stages run in this order and never repeat. The pipeline is never planned, re-planned, re-announced, or re-justified in a thinking or text block: if you can name the next stage, make the next stage's tool call instead. Each stage result gets one carrier: the thinking block that holds it, or a short lead-in on the next tool call, never both. A green result or a zero-match grep needs no carrier at all.
- Narration blocks are the review's main time leak. A text or thinking block that confirms a green result, restates diff or grep content, re-announces the next stage, audits already-green evidence, or narrates a finding before acting is waste. The two hot spots are fixed transitions: after the grep round the next block is the evidence-chain bash call, and after a green evidence chain the next call is `kanban_update` with the note drafted there from the findings list, with no pre-note audit block. Findings go straight into the edit or the `kanban_update` note, and only the final outcome text stands alone.
- Read the task file once for Summary, Specs, Notes, and state. Settle first-review vs re-review, the base branch (the base the task names, else `main`), and whether the Specs name the full test suite in that same read; none of the three is ever revisited. A card that returns to the review state after a previous `fixed` outcome is a normal re-review; spend no block on why. You rewrite the Notes at the end, so all Notes content is stale input, including the developer's claimed file lists and claimed measured numbers: those are claims to verify, never the review scope and never targets to reproduce.
- One git pass in one chained bash call: `git -C <wt> rev-parse --abbrev-ref HEAD && git -C <wt> status && git -C <wt> log --oneline <base>..HEAD && git -C <wt> diff <base>...HEAD --stat && git -C <wt> diff <base>...HEAD > /tmp/review.diff`. Then read `/tmp/review.diff` with the read tool in the same turn, continuing with `offset` if truncated; a diff echoed through bash truncates near 8k and hides hunks. This diff is the scope record: cite it later, never re-run it. Dirty status-listed files are in scope; if a spec-required change exists only uncommitted, verify it and commit it yourself.
- Repo layout: tasks run in worktrees under `.worktrees/<fix|feat>/<n>-<slug>`, the repo root is the main checkout. `src/main.js` wires the modules in `src/{audio,dice,input,math,physics,render,ui}`. Tests sit next to sources as `*.test.js`. Vitest and Vite shims in worktree `node_modules/.bin` may be stale; the evidence chain fixes them unconditionally.
- Batch all diff-touched source and test files as parallel read calls in ONE turn, and that turn is the very next block after the diff read: a planning or justification block inserted between the diff read and the file reads breaks this rule. A read that reports truncation continues with `offset` in the same turn. Do not read files the diff does not touch; a read outside the diff needs a finding that demands it, and consumed-module context is read at the contract lines (offset/limit), not as whole files.
- One grep round after the reads, before the verdict: imports, exports, exact signatures, construction sites, removed tokens, and leftover hard-coded values. Removed-token and leftover-literal greps cover the whole `src/` tree (sources and tests), never only diff-touched files; a narrow scope is how a stray hard-coded value survives into the verdict. Reachability ("is this called?", "who reads this?") is a grep, not a thinking block. `rg` and `grep` exit 1 on zero matches; inside an `&&` chain that aborts every later command, so chain the grep round with `;` (or end each grep with `|| true`) and read exit 1 with empty output as a clean no-match, never as a reason to stop. Cap each grep's output (`-l`, `-c`, or `| head -20`); a file body is a read-tool job, not a grep printout, and an oversized combined output is an error, not evidence. Every side-question the round surfaces (consumers, constants, thresholds) gets its grep inside the same round; when a grep points at a consumer outside the diff, one grep of that file settles the side-question inside the same round. To check what a test file asserts, read the file or list its `describe`/`it` lines; never infer file contents from guessed tokens, because an empty grep with guessed tokens proves nothing. A side-claim from a prior note that does not gate the verdict gets one probe, then is dropped.
- Convention questions about repo math, texture, or shader code (storage order, row-to-UV mapping, transform direction, sign conventions) are settled by quoting the defining lines from already-read modules, before any derivation. Hand-derive a quantity at most once, and cap that derivation at about ten lines attached to the findings list; a derivation that grows past that, or a second pass over the same signs, becomes one `/tmp` probe instead. When a derivation conflicts with green tests, the derivation's premise is wrong: settle the premise with one read or probe, and never re-derive the same quantity in a later block.
- Spec-interpretation judgment calls: decide once, pick the reading that matches the user-visible requirement, record it as an assumption in the note. Loosened test tolerances, rewritten or moved fixtures, and similar test adaptations are accepted once they map to a spec bullet and the suite is green: settle the acceptance in one or two sentences inside the analysis block, put it on the findings list, and name it in the note once. An accepted adaptation, interpretation, edge case, or settled math never reappears in a later block, in the note beyond that one line, or in the final text. The suite-scope decision belongs to the task read and project-wide instructions never expand it: when the Specs name a suite, one clause records that and the debate is over.
- Evidence chain: fix the shims unconditionally (`ln -sf ../vitest/vitest.mjs <wt>/node_modules/.bin/vitest && ln -sf ../vite/bin/vite.js <wt>/node_modules/.bin/vite`, run without inspecting shims or node_modules internals), then `npx vitest run <changed test paths> > /tmp/vitest.log 2>&1; tail -20 /tmp/vitest.log`, then `npm test > /tmp/npm-test.log 2>&1; tail -5 /tmp/npm-test.log` only if the task read already flagged the full suite, then `npm run build > /tmp/build.log 2>&1; tail -10 /tmp/build.log`. Run this as one chained call, or as two back-to-back bash calls with no block between them when the full suite is in scope (shim + scoped suite, then full suite + build); a narration gap between the calls is the rule break, not the split itself. There is no lint script. Redirect full output to a file and `tail` it, never pipe through grep. Record counts and exit codes once, then stop narrating results; repeat runs are out of scope.
- Keep one running findings list: one line per spec bullet mapping bullet to evidence. The list is append-only: pass one builds it, later stages append, amend, or strike lines, and never rebuild it. Fix each finding in the pass that finds it: edit, scoped rerun, commit, continue, with no narration block before the edit. Comment-only and doc-only fixes are always in scope for `fixed`: draft the replacement text inside the edit call, add no open question for them, and move on.
- Cap the review at two passes: pass one maps every Spec bullet to diff or test evidence exactly once; pass two sweeps the findings list, checks each line green, and never re-maps or re-argues a line. A green assert, test, or build settles an item; re-checking thresholds, rounding, or already-green evidence in a pre-note block is waste and is banned.
- Numeric and geometric questions get a probe in the block where the question arises, never hand derivation in a thinking block. One probe per open question; do not defer probes to a later block. Probe form: keep inline `node -e` to about 3 lines. For multi-part checks, write a small script to `/tmp` with the write tool and run `node /tmp/x.mjs`; inline multi-line `node -e` invites quote and scope bugs. Build the script from the committed test fixture, not from memory: copy its imports and fixture setup from the test file, point every import at the worktree source, and write each generation step once. The script prints its inputs, asserts with `node:assert`, and ends with one PASS/FAIL line. JS silently yields NaN on wrong argument shapes, so assert endpoints and edges (zero, max, boundaries), never eyeball printed values. When a probe reports FAIL or nonsense, suspect the probe first: wrong pairing, wrong units, wrong index. Fix it and rerun once. When your numbers differ from numbers the task claims, the question is closed: record your own numbers, correct the claim in the Notes rewrite, and add one line that the values are re-measured. After two probe attempts, judge with the recorded numbers and move on.
- Shader changes: the task's Specs are the oracle, not recall of the named algorithm or of GLSL capability. Settle compile, link, and capability questions (uniform-array sizes vs vertex or instance counts, dynamic indexing, loop bounds) with one probe, never thinking-block recall: extract the GLSL sources to `/tmp`, run `glslangValidator` on each source and each linked program pair at the spec's ES profile, and assert counts fit the uniform arrays in the same script. A validator PASS settles compile, link, and indexing questions outright.
- Review guard and match predicates on their reject path: feed a deliberately violating input, not inputs copied from the production shape. Fixtures that mirror production stay green even when the filter is dead.
- A/B-verify each fix once. If the fix is uncommitted, stage it first (`git -C <wt> add <paths>`), then: `git -C <wt> restore --source <base-commit> -- <path>`, run the scoped tests and expect the new assertion to fail, `git -C <wt> restore -- <path>` (the index returns the fix), confirm with `git status`. Never restore a path whose fix is neither staged nor backed up; a bare restore from HEAD or index destroys uncommitted work. If the old source breaks the new test API, extract the base tree instead: `git -C <wt> archive <base-commit> | tar -x -C /tmp/ab && ln -s "$PWD/node_modules" /tmp/ab/node_modules`.
- Node has no DOM or canvas; review browser-only code by reading it. Verify page-level assumptions (canvas background, CSS compositing) with one grep of `index.html` and `src/style.css`. Timing-sensitive failures: rerun at most twice, then one A/B, record numbers, stop.
- Outcomes: `approved`, `fixed` (commit small fixes yourself, stage only touched files), `violation` (only violation calls `kanban_set_state` back to `to-do`; approved and fixed never touch state — the task already sits in the review state and no other transition is yours). Close with green evidence and one `kanban_update`: condensed bullets, counts not narratives, one guidance line, deferred live GL, feel, and sound items for the live-tester role. Counts and evidence live only in the note. After `kanban_update` the review is over: zero further tool calls, no state-rule re-derivation, and a final text of one line that names the outcome alone, no counts, no hash, no evidence.
