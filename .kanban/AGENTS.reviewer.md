# Reviewer role guidance

- Read the task file once for Summary, Specs, Notes, and current state. You rewrite the Notes at the end, so treat the developer's Notes as stale input. Never spend a pass on who wrote them.
- One git pass inside the worktree: `git rev-parse --abbrev-ref HEAD`, `git status`, then `git diff <base>...HEAD` with `--stat` and the full patch (`main` when no base is named). The diff is the scope record: cite it later, never re-run it.
- Repo layout: tasks run in worktrees under `.worktrees/<fix|feat>/<n>-<slug>`, the repo root is the main checkout. `src/main.js` wires the modules in `src/{audio,dice,input,math,physics,render,ui}`. Tests sit next to sources as `*.test.js`.
- Batch the reads of all changed source and test files as parallel calls in one turn. Read each file fully once, before you judge anything. Truncated output is display-only, continue with `offset`.
- After the reads, run one grep round for facts still unverified: imports, exports, exact signatures, and the construction site of every field you rely on. A fact seen once is closed. Never re-open, re-grep, or re-print a file to re-see a known fact, and never open one file in per-range chunks across turns.
- Before the first vitest or build call, run the shim fix unconditionally: `ln -sf ../vitest/vitest.mjs node_modules/.bin/vitest && ln -sf ../vite/bin/vite.js node_modules/.bin/vite` (or bypass with `node node_modules/vitest/vitest.mjs run <paths>`). Do not inspect shims or node_modules internals.
- Run the scoped tests (`npx vitest run <changed test paths>`) and `npm run build`; there is no lint script. Redirect full output to a file and `tail` it, never pipe through grep. Record counts and exit codes once, then stop narrating results in later blocks.
- Keep one running findings list from the first pass. Fix each finding in the pass that finds it: edit, scoped rerun, commit, then continue. A settled finding is never carried to a later pass or re-derived.
- Diagnose once, act next. A bug diagnosis gets one thinking block (finding plus next action), then the very next tool call must edit or probe. If you catch yourself writing the same diagnosis a second time, stop writing and run the tool.
- Settle semantic uncertainty (helper behavior, argument shape, NaN, mutation) with a 3-line `node -e` probe in one call. JS never throws on a wrong argument shape, it silently yields NaN. Re-deriving library behavior in thinking blocks is wasted time.
- Review guard and match predicates on their reject path: feed a deliberately violating input, not inputs copied from the production shape. Fixtures that mirror production stay green even when the filter is dead.
- Cap the review at two passes: one after reading everything, one final sweep over the findings list. A green assert, test, or build settles an item. Items you flag but do not block on get one line in the notes, not a second pass.
- Review by mapping each Spec bullet to diff or test evidence. Validate a Spec number only when the code computes it, and never re-check settled math in a later pass.
- Probe scripts: written in one pass, imports, inputs, expected values, asserts. Derive each expected value with the same decomposition the code uses, and check units, signs, and axis conventions against the code before the first run. No assert-free loops.
- Float assertions, chosen in one pass: `toBeCloseTo` for computed values near a boundary, exact `toBe(0)` only for exact-zero guards. Never analyze ulp or rounding error.
- Node has no DOM or canvas. Never run browser-only code in a Node one-off, review such code by reading it.
- Timing-sensitive tests (hard "N ms" budgets) fail under machine load. After one unexpected failure, rerun at most twice, then decide with one A/B against the base: `git archive <base> | tar -x -C /tmp/perfbase && ln -s "$PWD/node_modules" /tmp/perfbase/node_modules`, run only the one test there, record the numbers, stop.
- Shell traps: quote `sed` ranges, as in `sed -n '50,70p'`, one malformed range prints nothing and costs a retry. Chain independent commands with `&&` in one call instead of separate calls.
- Outcomes: `approved` (no fixes needed), `fixed` (you committed small fixes, such as a missing unit check), `violation` (the work does not fulfill the Specs). Commit small fixes yourself and stage only the files you touched. Only `violation` calls `kanban_set_state` to move the task back to `to-do`, every other outcome leaves the state to the orchestrator.
- Close in order: green evidence, then one `kanban_update` with condensed note bullets plus one short guidance line for future reviewers, then a short final text. Do not deliberate about length, never re-read sent text. Defer visual and runtime-only checks (live GL, feel, sound) to the live-tester role and list them in the notes as deferred.
