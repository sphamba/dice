# Reviewer role guidance

- **Blocks are tool calls.** Block 1 reads the task file. Every block after that is a tool call. Thinking blocks that plan, queue, audit, re-check, or re-weigh a decision are the recorded top time sink of past runs, up to a third of all blocks, and they change nothing: the recipes below already hold the plan. Do not think about a step and then call it. Call it. After an unanswered question the next block is the tool call that answers it, never a deliberation. Standalone text carries only the final one-line outcome. A green result needs no comment at all.

- **Absolute paths and `git -C` only.** You start in `.kanban/.logs`. `<repo>` is the directory that holds `.kanban/`. Worktrees sit at `<repo>/.worktrees/<fix|feat>/<n>-<slug>`. Prefix any relative path a task gives with `<repo>/`. Use `git -C <wt>` for every git call, never bare git and never a `cd` first. Chain independent commands with `&&`. Read files with the read tool, never `cat`. Quote `sed` ranges (`sed -n '50,70p'`). Bash truncates output near 50k characters, so a diff echoed through bash is unusable: write diffs to files and read them with the read tool. Continue a truncated read with `offset`. Run each check one way only.

- **Opening, zero narration.** Block 1: read the task file with the read tool. Block 2: the git pass. Block 3: read `/tmp/review.diff` (and `/tmp/review.unstaged.diff` when status was dirty), continuing past truncation with `offset`; an empty file is a result, not a failure. Block 4: read all diff-touched files plus every module the Specs name as parallel read calls in one turn; with an empty diff that is just the Specs-named modules. Issuing these reads one per turn is a defect. Non-diff modules enter at their contract lines with `offset`/`limit`, not as whole files. Stages never repeat: one grep round, evidence chain, verdict, `kanban_update`, one-line outcome.

- **The task read settles four decisions once:** first vs re-review (a card back after `fixed` is a normal re-review, no block on it), base branch (the base the task names, else `main`), suite scope (Specs name the full suite → `npm test` runs; Specs name no suite → scoped suites for diff-touched paths, one findings line), and dirty files (status-listed uncommitted files are in scope). The Specs line is the verdict on suite scope. Deliberating it in a later block is a defect. Developer-claimed file lists and numbers are claims to check against the diff, never the scope, never targets to reproduce. You rewrite the Notes at the end, so Notes content is stale input.

- **Git pass (one chained call, never repeated).** `git -C <wt> rev-parse --abbrev-ref HEAD && git -C <wt> status && git -C <wt> log --oneline <base>..HEAD && git -C <wt> diff <base>...HEAD --stat && git -C <wt> diff <base>...HEAD > /tmp/review.diff`, and when status lists dirty files append `&& git -C <wt> diff > /tmp/review.unstaged.diff`. The recorded diffs are the scope record: cite them, never re-run them, never re-diff a file. A committed-or-uncommitted question is answered by re-reading the recorded diffs. If a Spec-required change exists only uncommitted, verify it and commit it yourself.

- **Empty diff is a verdict input, not a mystery.** An empty `<base>..HEAD` log and diff mean the branch carries no work beyond `<base>`: the task is unimplemented, or its commits already merged into `<base>`. That settles the branch state for the rest of the run. Review the Specs-named modules at HEAD against the Specs and decide which case holds from their content. Never re-derive the branch state: no second diff, no hash comparisons, no branch, stash, or worktree listings, no other-branch hunts. One `git -C <wt> log --oneline -5 <base>` inside the grep round is the only allowed follow-up, and only to name which prior commit landed a Spec-cited change.

- **Absent Spec change means `violation`, decided at once.** When a read or grep shows a Spec-required change missing from the tree, the outcome is `violation`, settled in that block. A reviewer repairs a present change in place (small edits plus a scoped rerun); a reviewer never implements a missing feature, chain, file, or test suite, and never implements a change whose acceptance lives in the browser: that is developer plus live-tester work. With no diff there is nothing to run: skip the evidence chain, A/B, and commit stages, finish the findings list from the reads, and go straight to `kanban_update`.

- **Findings list, fix in the pass that finds it.** One line per Spec bullet mapping bullet to evidence, started during the file reads, append-only. Later stages append, amend, or strike lines, never rebuild or re-argue a settled line. Fix each finding where found: edit, scoped rerun, commit, continue, with no narration block first. Cap the review at two passes: pass one maps every Spec bullet to evidence once, pass two sweeps the list green. Green evidence is final. Re-checking it in any later block is banned.

- **One grep round.** After the reads, before the verdict: imports, exports, exact signatures, construction sites, removed tokens, leftover hard-coded values. Removed-token and leftover-literal greps cover the whole `src/` tree, never only diff-touched files. Chain the round with `;` or end each query with `|| true`: zero matches exit 1 and abort an `&&` chain, so read exit 1 with empty output as a clean no-match. `rg` has no `--count-lines`, use `-c`. A missing section in chained output means rerun that one query, not assume zero. Cap output (`-l`, `-c`, `| head -20`). Every side question the round surfaces gets its grep inside the same round. A later block that greps a token the round already settled is a defect, including re-proving confinement or sole-consumer claims. To know what a test asserts, read it or list its `describe`/`it` lines, never infer from guessed tokens.

- **Derivation budget.** Hand-derive a quantity once, cap it at about ten lines, attach the result to the findings list, and never touch it again. When two modules must agree, settle it by putting the two defining lines side by side in one read or grep. Convention questions (order, mapping, direction, sign) are settled by quoting defining lines of already-read modules. When a derivation conflicts with green tests, its premise is wrong. A derivation that grows past the cap or repeats a pass is a hard stop: keep what it settled and settle the number with one probe.

- **Probes, not reasoning.** A probe runs in the block where the question arises. Keep inline `node -e` to about 3 lines, or write `/tmp/x.mjs` with the write tool from the committed test fixture: copy imports and fixture setup, point imports at the worktree source, print inputs, assert with `node:assert`, end with one PASS or FAIL line. JS yields silent NaN on wrong shapes, so assert endpoints and edges, never eyeball prints. On FAIL suspect the probe first, fix it, rerun once. Two probe attempts maximum. When your numbers differ from claimed numbers, record yours and move on, never reproduce the claim. Spec interpretation closes in one block: one sentence, one choice, one assumption line on the findings list. An accepted test adaptation gets one findings line and one note mention, and never reappears later.

- **Evidence chain (one or two back-to-back bash calls, no block between).** (1) Heal tooling: `test -x <wt>/node_modules/.bin/vitest || npm --prefix <wt> ci > /tmp/npm-ci.log 2>&1; tail -3 /tmp/npm-ci.log`. (2) Fix shims: `ln -sf ../vitest/vitest.mjs <wt>/node_modules/.bin/vitest && ln -sf ../vite/bin/vite.js <wt>/node_modules/.bin/vite`. (3) `npx vitest run <changed test paths> > /tmp/vitest.log 2>&1; tail -20 /tmp/vitest.log`. (4) `npm test > /tmp/npm-test.log 2>&1; tail -5 /tmp/npm-test.log` only when the task read flagged the full suite. (5) `npm run build > /tmp/build.log 2>&1; tail -10 /tmp/build.log`. Never inspect shims or node_modules internals. There is no lint script. Redirect full output to a file and `tail` it, never pipe through grep. Record counts and exit codes once, then stop: never reconcile a measured count with a claimed or remembered number, never predict runtimes or counts before a run.

- **A/B-verify each behavioral fix once, directly.** Stage the fix if uncommitted (`git -C <wt> add <paths>`), then `git -C <wt> restore --source <base-commit> -- <path>`, run the scoped tests and expect the new assertion to fail, `git -C <wt> restore -- <path>`, confirm with `git status`. Never restore a path whose fix is neither staged nor backed up. If old source breaks the new test API, extract the base tree: `git -C <wt> archive <base-commit> | tar -x -C /tmp/ab && ln -s "$PWD/node_modules" /tmp/ab/node_modules`. Skip A/B for whitespace-only, comment-only, rename-only, and test-only diffs. A green scoped rerun settles those, and no block re-litigates the skip.

- **Commit rule.** Commit after the evidence chain is green, staging only the files the findings list names as touched. Keep `git -C <wt>` in the commit command.

- **Shader and GL questions.** The Specs are the oracle, not recall of the named algorithm or GLSL capability. Compile, link, and capability questions (uniform-array sizes vs vertex or instance counts, dynamic indexing, loop bounds) get one probe: extract the GLSL sources to `/tmp`, run `glslangValidator` on each source and each linked program pair at the spec's ES profile, and assert counts fit the uniform arrays in the same script. Render-state questions (blend, alpha, discard, stencil, depth func) are source questions: one grep of the shader sources and context-attribute call sites settles them, never recall of GL semantics.

- **Node has no DOM or canvas.** Review browser-only code by reading it. Verify page-level assumptions with one grep of `index.html` and `src/style.css`. Timing-sensitive failures: rerun at most twice, then one A/B, record numbers, stop. Live GL, screenshots, sound, and feel are the live-tester role's scope: never read the developer's live evidence (no screenshot PNGs, no `/tmp` out or report dirs), and accept or flag each live claim in one line.

- **Review guard and match predicates.** On their reject path, feed a deliberately violating input, not inputs copied from the production shape. Fixtures that mirror production stay green even when the filter is dead.

- **Card provenance, no enumeration.** Which prior task landed a change is answered by the card under review, its `commits` and `changes` fields, and `git -C <wt> log`. Never call `kanban_list` to reconstruct pipeline history: it returns thousands of lines and answers a question git already answered.

- **Outcomes and a hard stop.** `approved`, `fixed` (commit small fixes yourself, stage only touched files), `violation` (only violation calls `kanban_set_state` back to `to-do`; approved and fixed never touch state). After the last green result, or a settled violation, the next block is the `kanban_update`, drafted inside the call from the findings list: condensed bullets, counts not narratives, one guidance line, live GL, feel, and sound deferred to the live-tester. A closing audit, summary, or note-draft block before the call is a defect. After `kanban_update` the review is over: one final text line that names the outcome word (`approved`, `fixed`, or `violation`), never `done`, and zero further tool calls.
