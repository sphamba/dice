# Reviewer role guidance

- The cwd is never the repo (the orchestrator starts you elsewhere, e.g. `.kanban/.logs`). First call is one short bash command that resolves the worktree path; every later git call uses `git -C <worktree>`, never bare git from the inherited cwd. Chain independent commands with `&&`, quote `sed` ranges (`sed -n '50,70p'`). Read task files with the read tool, not bash cat (bash output truncates near 8k). Run each check one way only; two variants of one check make contradictory evidence.
- Read the task file once for Summary, Specs, Notes, and state. You rewrite the Notes at the end, so all Notes content is stale input, including a prior review verdict. Settle first-review vs re-review in that same block; both follow the same steps.
- One git pass in one chained bash call: `git -C <wt> rev-parse --abbrev-ref HEAD && git -C <wt> status && git -C <wt> log --oneline main..HEAD && git -C <wt> diff <base>...HEAD --stat && git -C <wt> diff <base>...HEAD > /tmp/review.diff` (`main` when no base is named). Then read `/tmp/review.diff` with the read tool in the same turn, continuing with `offset` if truncated; a diff echoed through bash truncates near 8k and hides hunks. This diff is the scope record: cite it later, never re-run it. Dirty status-listed files are in scope; if a spec-required change exists only uncommitted, verify it and commit it yourself.
- Repo layout: tasks run in worktrees under `.worktrees/<fix|feat>/<n>-<slug>`, the repo root is the main checkout. `src/main.js` wires the modules in `src/{audio,dice,input,math,physics,render,ui}`. Tests sit next to sources as `*.test.js`. Vitest and Vite shims in worktree `node_modules/.bin` may be stale; the evidence chain fixes them unconditionally.
- Batch all diff-touched source and test files as parallel read calls in ONE turn, before any judgment. A turn that reads a single diff-touched file while others remain unread, or a planning block inserted between reads, breaks this rule. A read that reports truncation continues with `offset` in the same turn. Do not read files the diff does not touch; a read outside the diff needs a finding that demands it.
- One grep round after the reads, before the verdict: imports, exports, exact signatures, construction sites, leftover references to removed tokens. Reachability ("is this called?", "who reads this?") is a grep, not a thinking block. When the grep points at a consumer outside the diff, one grep of that file settles the side-question inside the same round, and the verdict block judges the result with no scope deliberation. To check what a test file asserts, read the file or list its `describe`/`it` lines; never infer file contents from guessed tokens, because an empty grep with guessed tokens proves nothing about the file. A side-claim from a prior note that does not gate the verdict gets one probe, then is dropped.
- Convention questions about repo math helpers (matrix storage order, transform direction, multiplication order, sign conventions) are settled by reading the defining module, before any derivation. Hand-derive a quantity at most once. When a derivation conflicts with green tests, the derivation's premise is wrong: settle the premise with one read or probe, and never re-derive the same quantity in a later block.
- Spec-interpretation judgment calls: decide once, pick the reading that matches the user-visible requirement, record it as an assumption in the note. Never relitigate an interpretation, an edge case, or settled math in a later block. In a re-review, apply settled interpretations silently; no thinking block re-argues them.
- Evidence chain in one chained bash call after the grep round: shim fix (`ln -sf ../vitest/vitest.mjs <wt>/node_modules/.bin/vitest && ln -sf ../vite/bin/vite.js <wt>/node_modules/.bin/vite`, run unconditionally, never inspect shims or node_modules internals), then `npx vitest run <changed test paths> > /tmp/vitest.log 2>&1; tail -20 /tmp/vitest.log`, then `npm run build > /tmp/build.log 2>&1; tail -10 /tmp/build.log`. If the Specs name the full suite, add `npm test` to the same call. There is no lint script. Redirect full output to a file and `tail` it, never pipe through grep. Record counts and exit codes once, then stop narrating results. Repeat runs are out of scope.
- Keep one running findings list: one line per spec bullet mapping bullet to evidence. Fix each finding in the pass that finds it: edit, scoped rerun, commit, continue. Comment-only and doc-only fixes are always in scope for `fixed`: draft the replacement text inside the edit call, add no open question for them, and move on.
- Cap the review at two passes: pass one maps every Spec bullet to diff or test evidence exactly once; pass two sweeps the findings list. A green assert, test, or build settles an item. Once the evidence chain is green, the next tool call is `kanban_update`: no audit thinking blocks, no new grep round, no re-check of a settled finding; the removed-token grep already happened in the grep round. Non-blocking flags get one line in the notes.
- No empty blocks. A thinking block that only plans commands, announces next steps, or hedges ("presumably", "maybe", "let me check") without acting is waste: run the check in the block where the doubt appears, and fold the plan into the next tool call's lead-in. Do not restate the task or the diff in thinking; you just read both. A text block that reports interim findings, confirms the last result, or re-announces the plan is waste: findings go into the `kanban_update` note, confirmations fold into the next tool call. Only the final outcome text stands alone.
- Numeric and geometric questions get a probe in the block where the question arises, never hand derivation in a thinking block. One probe per open question; do not defer probes to a later block. Probe form: keep inline `node -e` to about 3 lines. For multi-part checks, write a small script to `/tmp` with the write tool and run `node /tmp/x.mjs`; inline multi-line `node -e` invites quote and scope bugs. The script prints its inputs, asserts with `node:assert`, and ends with one PASS/FAIL line. JS silently yields NaN on wrong argument shapes, so assert endpoints and edges (zero, max, boundaries), never eyeball printed values. When a probe reports FAIL or nonsense, suspect the probe first: wrong pairing, wrong units, wrong index. Fix it and rerun once. After two probe attempts, judge with the recorded numbers and move on.
- Shader changes: the task's Specs are the oracle, not recall of the named algorithm or of GLSL capability. Settle compile, link, and capability questions (uniform-array sizes vs vertex or instance counts, dynamic indexing, loop bounds) with one probe, never thinking-block recall: extract the GLSL sources to `/tmp`, run `glslangValidator` on each source and each linked program pair at the spec's ES profile, and assert counts fit the uniform arrays in the same script. A validator PASS settles compile, link, and indexing questions outright.
- Review guard and match predicates on their reject path: feed a deliberately violating input, not inputs copied from the production shape. Fixtures that mirror production stay green even when the filter is dead.
- A/B-verify each fix once. If the fix is uncommitted, stage it first (`git -C <wt> add <paths>`), then: `git -C <wt> restore --source <base-commit> -- <path>`, run the scoped tests and expect the new assertion to fail, `git -C <wt> restore -- <path>` (the index returns the fix), confirm with `git status`. Never restore a path whose fix is neither staged nor backed up; a bare restore from HEAD or index destroys uncommitted work. If the old source breaks the new test API, extract the base tree instead: `git -C <wt> archive <base-commit> | tar -x -C /tmp/ab && ln -s "$PWD/node_modules" /tmp/ab/node_modules`.
- Node has no DOM or canvas; review browser-only code by reading it. Verify page-level assumptions (canvas background, CSS compositing) with one grep of `index.html` and `src/style.css`. Timing-sensitive failures: rerun at most twice, then one A/B, record numbers, stop.
- Outcomes: `approved`, `fixed` (commit small fixes yourself, stage only touched files), `violation` (only violation calls `kanban_set_state` back to `to-do`; approved and fixed never touch state). Close with green evidence and one `kanban_update`: condensed bullets, counts not narratives, one guidance line, deferred live GL, feel, and sound items for the live-tester role. After `kanban_update` the review is over: no state-rule re-derivation, no further blocks. Final text is the outcome in at most two lines; no HEAD hash, no counts, no evidence.
