# Reviewer role guidance

- Read the task file first: Specs, Notes, and current state. Then check git once, inside the worktree: `git rev-parse --abbrev-ref HEAD`, `git status`, and `git diff <base>...HEAD` with `--stat` and the full diff. Read the full diff once here; later passes cite it, never re-run `git diff`.
- Tasks live in git worktrees under `.worktrees/<fix|feat>/<n>-<slug>`. The repo root is the main checkout, where `git branch` output can look conflicting. If the task does not name a base, diff `main...HEAD`.
- Repo layout: `src/main.js` wires the modules in `src/{audio,dice,input,math,physics,render,ui}`. Tests sit next to sources as `*.test.js`.
- Read every changed source and test file once, fully, before you judge anything. Truncated read output is display-only; continue with `offset`.
- Confirm the interfaces the change depends on once, early: grep the defining file for the imports, exports, and constants you will rely on. Before you design a probe, grep the `export` lines of the modules under test so you know what you can import. To find a field, read the file that uses it, not guessed greps.
- Worktree trap: `node_modules/.bin` shims are dereferenced copies that fail with `ERR_MODULE_NOT_FOUND`. Fix them BEFORE the first vitest or build call, never after a failure: `ln -sf ../vitest/vitest.mjs node_modules/.bin/vitest && ln -sf ../vite/bin/vite.js node_modules/.bin/vite`, or bypass with `node node_modules/vitest/vitest.mjs run <paths>` and `node node_modules/vite/bin/vite.js build`. Do not inspect node_modules internals; the fix stays untracked.
- Run the scoped tests (`npx vitest run <changed test paths>`) and `npm run build`. There is no lint script. Record test counts and exit codes.
- Never pipe test output through grep; the pattern eats the failure message. Redirect full output to a log and `tail` it, so one run carries both the counts and the failure context.
- Timing-sensitive tests (hard budgets like "N ms") fail under machine load. After a first unexpected failure, rerun at most twice to confirm intermittence, then decide with one A/B against the base, not more retries: `git archive <base> | tar -x -C /tmp/perfbase && ln -s "$PWD/node_modules" /tmp/perfbase/node_modules`, then run only the one test there. Once decided, record the numbers and stop; do not re-run either side.
- Do all numeric verification in one assert probe, not in prose. Algebra re-derived in a thinking pass is wasted work and gets truncated; the probe is the only place math gets checked. Design it in one pass, after the export grep: inputs, expected values, asserts.
- Derive each probe expected value from the parameter the code itself uses, with the same decomposition the code uses; never invert a target or reuse one raw input on two axes. Check cross-product and rotation signs before the first run.
- Probe setup must satisfy the constructors it calls (a custom shape needs an inertia tensor for `createBody`), and shared constants come from imports, not redefinitions. If an assert fails on the first run, suspect the probe's formula first, fix once, rerun; never re-derive settled math in a later thinking pass.
- Node has no DOM or canvas. Never run browser-only code in a Node one-off; review such code by reading it. Strip dead code from a probe; a loop that asserts nothing is wasted time.
- Cap yourself at two review passes: one after reading all files, one final. An item with a passing assert, test, or build counts as settled. An edge case you flag but do not block on gets one line in the notes, not a second investigation.
- Shell trap: quote `sed` ranges, as in `sed -n '50,70p'`. A malformed range prints nothing and costs a retry.
- Verdicts: "approved" needs no kanban state change, only notes. "Changes requested" is the only verdict that moves the state. Read the kanban tool docs once if unsure, not repeatedly.
- Write notes once, at the end. If a harness checkpoint forces a write mid-run, dump a one-line note marked "interim" and move on; overwrite it with the final notes. Do not deliberate about the conflict.
- Notes format: a condensed rewrite of the Notes section, plus one short guidance line for future reviewers. List accepted developer-documented interpretations as accepted.
- Do not fix code or commit. Record findings and stop. The `node_modules` symlink repair above is the only allowed untracked fix.
- Defer visual and runtime-only checks (live GL, feel, sound) to the live-tester role; note them as deferred.
