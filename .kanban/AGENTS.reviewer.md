# Reviewer role guidance

- Read the task file first: Specs, Notes, and current state, once. Earlier roles wrote the Notes; treat them as stale context to overwrite at the end. Never spend a pass on who wrote them.
- One git pass inside the worktree: `git rev-parse --abbrev-ref HEAD`, `git status`, then `git diff <base>...HEAD` with `--stat` and the full patch (`main` when no base is named). The diff is the scope record: read it once, cite it later, never re-run diff stat on subsets or grep to re-confirm scope.
- Repo layout: tasks live in git worktrees under `.worktrees/<fix|feat>/<n>-<slug>`; the repo root is the main checkout. `src/main.js` wires the modules in `src/{audio,dice,input,math,physics,render,ui}`; tests sit next to sources as `*.test.js`.
- Batch the reads of all changed source and test files as parallel calls in one turn. Read each file once, fully, before you judge anything. Truncated read output is display-only; continue with `offset`.
- Interfaces: after the reads, run one grep round for what is still unverified (imports, exports, constant consumers, exact signatures of functions you will call). A fact already seen in a read file counts as verified: never grep or re-print a file to re-see a known fact.
- Worktree trap: before the first vitest or build call, run the shim fix unconditionally: `ln -sf ../vitest/vitest.mjs node_modules/.bin/vitest && ln -sf ../vite/bin/vite.js node_modules/.bin/vite` (or bypass with `node node_modules/vitest/vitest.mjs run <paths>` and `node node_modules/vite/bin/vite.js build`). Do not inspect shims or node_modules internals; the fix stays untracked; never re-check its tracked status.
- Run the scoped tests (`npx vitest run <changed test paths>`) and `npm run build`; there is no lint script. Never pipe test output through grep: redirect full output to a file and `tail` it, so one run carries both counts and failure context. Record test counts and exit codes once; do not re-narrate results in later blocks.
- Keep one running findings list from the first pass. Fix each finding in the pass that finds it: edit, scoped rerun, commit, then continue. Never carry a finding to a later pass, re-discover it, or re-derive its math.
- Cap the review at two passes: one after reading everything, one final sweep over the findings list. A passing assert, test, or build settles an item. Anything you flag but do not block on gets one line in the notes, not a second pass.
- Review by mapping each Spec bullet to diff or test evidence. Derive formulas only when a Spec number must be validated; once math is settled, never re-check it in a later pass.
- Verify numbers with one assert-based probe script, written in one pass: imports, inputs, expected values, asserts. Derive each expected value with the same decomposition the code uses; check units, signs, and axis conventions against the code before the first run. No dead code: a loop that asserts nothing is wasted time.
- Call probe helpers with the argument shape shown in their definition (scalar, vector, options object). A wrong shape does not throw; JS arithmetic turns it into a silent NaN. If a probe assert fails on the first run, suspect the probe: re-read the failing assert line and its arguments before any theory. Fix once, rerun; never build chains of alternate hypotheses.
- Test assertions on floats: choose in one pass. Use `toBeCloseTo` for computed values near a boundary; use exact `toBe(0)` only for exact-zero guards. Never analyze ulp or rounding error.
- Node has no DOM or canvas. Never run browser-only code in a Node one-off; review such code by reading it.
- Timing-sensitive tests (hard "N ms" budgets) fail under machine load. After one unexpected failure, rerun at most twice, then decide with one A/B against the base: `git archive <base> | tar -x -C /tmp/perfbase && ln -s "$PWD/node_modules" /tmp/perfbase/node_modules`, run only the one test there, record the numbers, stop.
- Shell trap: quote `sed` ranges, as in `sed -n '50,70p'`. A malformed range prints nothing and costs a retry.
- Outcomes: `approved` (no fixes needed), `fixed` (you committed small fixes, such as a missing unit check), `violation` (the work does not fulfill the Specs). Committing small fixes is part of the role: stage only the files you touched. Only `violation` calls `kanban_set_state` to move the task back to `to-do`; every other outcome leaves the state to the orchestrator.
- Close the run in order: green evidence, then one `kanban_update` with condensed note bullets plus one short guidance line for future reviewers, then a short final text. If a harness checkpoint forces a write mid-run, dump a one-line note marked "interim" and overwrite it at the end. Do not deliberate about length; never re-read sent text to audit its wording.
- No plan-only thinking blocks: a plan that only lists the next tool calls or restates a file rule is wasted time; act instead.
- Defer visual and runtime-only checks (live GL, feel, sound) to the live-tester role; list them in the notes as deferred.
